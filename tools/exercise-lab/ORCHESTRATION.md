# 戦術演習の探索指示書

この指示書は、Codex や Claude Code が `exercise-lab` を使って戦術演習の編成を探索するときに読む。
オーケストレーターは候補を選び、試行結果とログをもとに次の仮説を立てる。試行・予算管理・集計・詳細再生には
ラボの CLI を使う。コマンドの構文、ラウンド指示の JSON、API の起動条件は
[README の実行手順](README.md#チャットから探索を進める)を参照する。

## 探索を始める

1. 指定された `evaluation.yaml` と `starts` の編成ライブラリを読み、敵、編成の狙い、目的指標、
   使用可能なプール、固定枠、ギア条件、一次探索と確認試行の予算を把握する。チャットで指定された
   確認事項も記録する。
2. 新規なら `search init` を実行し、返された `searchDir` と `initialCandidates` の編成ID・候補IDを控える。
   既存の探索を再開する場合は、そのディレクトリで `search status --trials` を実行し、
   開いたラウンド、完了済みの試行番号、残り予算を確認する。
3. 起点が複数ある場合は、共通の試行番号で各起点を評価する。起点ごとに変更の効果を調べるときは
   変更元を基準にし、最終順位を比べるときは候補間で共通の基準を使う。

## スコアアップのナレッジ

候補を選ぶときは、以下の知見を使う。使用可能なユニットとメモリーは探索設定に従い、効果は対象の敵に対する対応試行で確かめる。

- **メインアタッカーとサポーター。** メインアタッカーはバニー沙耶、コトハ、オルガナージャを優先候補とする。
  現時点で最もダメージを出しやすい編成は、メインアタッカー1人に純夏、翠蘭、エレーナ、めるを合わせ、
  バフとデバフをメインアタッカーの攻撃に集中させるハイパーキャリー。
- **敵の妨害への対応。** 敵の妨害でメインアタッカーの行動や支援が崩れる場合は、
  【省エネ主義の天才ハッカー】エヴィ・レーナルトや【愛を求めるトラブルメーカー】アニス・ベネットを
  サポーターの交代候補に入れ、妨害を回避できるか試す。元の編成と比較し、妨害対策によって
  メインアタッカーの攻撃や支援がどれだけ維持され、スコアがどう変わったかをログで確認する。
- **メモリーの優先順位。** メインアタッカーのダメージへの貢献が大きいメモリーから試す。
  める入りの編成では「取り戻した学園生活」も優先候補にする。めるのバフ付与回数を増やして間接的に
  ダメージを伸ばすため、差し替え前後でメインアタッカーへのバフ付与回数、付与のタイミング、スコア差を比較する。

## 一次探索を進める

1. **仮説を立てる。** 最初はメモリー差し替え、メモリー順、配置、ギアのうち一つだけを変え、
   変化を追いやすくする。ユニット交換は有効な実験で試す。
   `search candidates --parent <候補ID> --kind <memory|placement|gear|unit>` から候補を取り、
   編成の狙いと残り予算を踏まえて選ぶ。たとえば、キャリーへの攻撃バフを保てそうなメモリーや、
   行動順を維持できそうなギア変更を優先する。
2. **ラウンドを実行する。** 選んだ候補の `proposal` または登録済みの `candidateIds` を JSON に入れ、
   `search round` に渡す。新しい指示には新しい `id` を付ける。
   初回の試行数は `trials.screeningRuns` を目安にし、同じ比較に入れる候補には共通の `runIndices` を指定する。
   基準の結果が保存済みなら、`search status --trials` の `completedRunIndices` で新しい候補を評価する。
   追加試行では、その候補と seed で要求済みの番号を避け、新しい共通の番号を割り当てる。
3. **予算と停止状態を確認する。** 送信前に `budget.availableForScreening` を確認する。
   部分応答や再送も送信予算を消費する。停止時は `execution.evaluationStopReason` と `openRound` を確認し、
   開いたラウンドを `search resume` で続ける。送信数を絞る場合は `--max-runs-per-request` を使う。
   継続できず完了分を確定する場合は `--close-partial` を使い、未完了の試行があったことを記録する。
4. **比較する。** `compare --baseline <基準ID> --candidate <候補ID> --phase screening --json` で、
   目的指標の差、95%区間、`pairedRuns`、変更箇所を読む。順位を付ける候補には共通の試行番号の組を用意する。
   対応試行が不足して期待日次ベストが `null` なら、必要な候補へ追加試行を割り当てる。
   改善幅に対して区間が広い場合は、その不確かさも候補選びに反映する。

## ログを次の候補に使う

1. `representativeTrials` から、改善幅が大きい `largestGain`、悪化幅が大きい `largestLoss`、
   中央付近の `medianDelta` を選ぶ。期待日次ベストを調べるときは候補スコア上位の `upperTail` も使う。
2. `inspect` に `--phase`、`--candidate`、`--baseline`、`--run-index` を渡してペアを再生する。
   候補側の評価を特定するときは代表試行の `evaluationId` を `--evaluation-id` に渡す。
   ターン別・スキル別のスコア差、実際の行動順、対象選択時の攻撃力、バフ・デバフの付与先と消費者を確認する。
   イベントの前後関係は `tracePath` の詳細ログで追う。
3. ログで観測した事実と、それを説明する仮説をそれぞれ記録する。別の代表試行でも同じ現象が起きるか確かめ、
   有望な変更の組み合わせや、行動順・バフ対象を維持する調整を次の候補にする。組み合わせの効果は実際に評価する。

たとえばフルート演習の `saya-carry-manners` では、沙耶と翠蘭の行動順、翠蘭ASのデバフを消費したユニット、
エレーナEXの攻撃力比較とバフ先、めるのバフ付与先を確認する。攻撃ギアで沙耶の火力が上がった試行と、
速度順が変わってデバフを取り逃した試行があれば、速度を補うギア案を作って比較する。

## 確認試行と報告

1. 確認に進める候補がそろい、追加試行でその選定が変わる見込みが小さければ一次探索を終える。
   一次探索の予算を使い切った場合は、その時点の結果を使う。
   確認に進める候補は `trials.finalists` の範囲で選ぶ。
2. 選んだ候補と基準を `phase: confirmation` で評価し、共通の試行番号と `trials.confirmationRuns` を使う。
   `compare --phase confirmation --json` で、設定された目的指標の改善幅順に並べる。確認試行で得た結果から
   新しい候補を作った場合、その候補の確証には未使用の確認 seed を指定した探索を作る。
3. 最終報告には設定、基準編成、候補の変更箇所、目的指標の基準値と候補値、差、95%区間、対応試行数、
   判断の根拠となった試行参照を載せる。ギア案が複数あればユニットと付け替え内容を明示し、改善幅順に示す。
   対応試行が少ない候補や、差の区間がゼロをまたぐ候補は、その不確かさと合わせて報告する。

## 記録と指示書の更新

探索ディレクトリの `notes.md` に、各ラウンドの仮説、指示ID、候補ID、フェーズ、比較結果、代表試行の
`evaluationId` と `runIndex`、追跡に使った `tracePath`、次の判断を残す。再開時はこの記録と
`search status --trials` を照合する。

探索を終えたら、他の演習にも適用できる判断手順の改善を、この指示書の更新案にまとめる。
更新案には「何を変えるか」「次回どの判断に効くか」「根拠となった候補・試行」を付ける。
対象や編成に依存する知見は実験ノートに残す。指示書の更新時は、記載したコマンドと項目名を
README および CLI に照らし、変更理由を Git 履歴で追えるようにする。

### チャットの開始文

> `tools/exercise-lab/ORCHESTRATION.md` に従って、`tools/exercise-lab/configs/evaluation.yaml` の探索を進めてください。
> 編成の狙いをログで検証し、実験ノートを残してください。確認試行の結果を基準編成と比較し、改善候補とその根拠を報告してください。
