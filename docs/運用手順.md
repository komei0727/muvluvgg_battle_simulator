### 確定の根拠（REL-005の実測値）

測定環境はローカル開発機（darwin、10論理CPU）であり、Cloud Runの1 vCPU上では
絶対値が悪化する。したがって「余裕が何倍あるか」を判断材料にし、絶対値そのものを
SLOにはしない。

| 測定                                 | 実測値                                                                                                                        | 影響する設定                                            |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| 最大応答（1対1・99ターン・DETAILED） | `UNIT_AOI_GUARDIAN`で36,482イベント・11,761差分・**23.1 MB**。実行217ms、直列化27ms                                           | CPU／Memory、`SIMULATION_MAX_EVENTS`                    |
| 最大規模（5対5・99ターン・DETAILED） | 最悪5,952イベント・3.48 MB・実行108ms（14編成を走査）                                                                         | CPU／Memory                                             |
| 圧縮                                 | 23.1 MB → gzip **1.32 MB（5.7%）**を75msで生成                                                                                | 圧縮担当と閾値                                          |
| 実行保護の必要量                     | 全29編成（5対5ミラー14・混成15）でPS深度**4**（上限8）、1スコープ効果解決数**54**（旧上限50を超過）                           | `SIMULATION_MAX_PASSIVE_DEPTH`・`..._EFFECTS_PER_SCOPE` |
| production経路のpeak RSS             | コンパイル済みHTTP→Worker経路で全73ユニットの最悪戦闘を並行度2まで流し**840 MB**（基準237 MB＋増加603 MB。最大応答は24.1 MB） | CPU／Memory                                             |

個別の判断は次のとおり。

- **Container concurrency・Request timeout・`SIMULATION_TIMEOUT_MS`・`WORKER_MAX_QUEUE`・`SHUTDOWN_GRACE_MS`は据え置く。** 最悪の戦闘でも実行217ms・直列化27msで、30秒の実行期限に対して2桁の余裕がある。並行度を2から4へ上げてもスループットの伸びは3割に留まりレイテンシは1.7倍になるため、拡大する理由がない。実行中の戦闘を抱えたshutdownは猶予の1/180で完了し、待ち時間の上限は最悪の戦闘実行時間（実測445ms）で頭打ちになる。
- **Memoryを1 GiBから2 GiBへ増やす（CPU 1 vCPU・Minimum／Maximum 0／1は据え置く）。** コンパイル済みHTTP→Worker経路を配備値（Worker 1本・待機1枠）で組み、乱数を固定して**Catalog全73ユニットの最悪戦闘**を配備並行度2で流したところ、最大応答24.1 MB・process peak RSS **840 MB**（基準237 MB＋増加603 MB）だった（Node.jsのWorker Threadは同一プロセス内で動くため、この値はメインスレッドとWorkerの両方を含む）。1 GiBに対して余裕は15%しかない。V8は既定のold-space上限（64bitで約4 GB）までcontainerの制限を知らないため、超過してもGCで凌ぐのではなくOOM killになる。増量は費用と引き換えの可逆な措置であり、`REL-006`／Issue #197のメモリーメトリクスで実配備値を観測したうえで見直せる。なお測定環境にはVitestのoverheadが含まれる一方でcontainerのoverhead（Node本体・OS）は含まないため、絶対値そのものではなく「1 GiBでは余裕が無い」という差の大きさを判断根拠にしている。
- **`WORKER_MIN_THREADS`／`WORKER_MAX_THREADS`を1／1で明示する。** Piscinaは未設定時に`minThreads = max(floor(availableParallelism/2), 1)`・`maxThreads = availableParallelism * 1.5`を採る。`os.availableParallelism()`が見るのはhostのCPU数とaffinityであって、Cloud Runの1 vCPU（cgroup quota）ではない。未設定のままだと割り当てCPUを超える本数のWorkerが起動しうるため、CPU limitに合わせて固定する（`11_インフラストラクチャ設計.md`「CPU limitに合わせて`WORKER_MAX_THREADS`を設定し」）。Worker1本＋待機1枠は container concurrency 2 をちょうど受け切る（実測で拒否0件）。
- **`SIMULATION_MAX_EFFECTS_PER_SCOPE`を50から100へ引き上げる。** 5対5・99ターン・DETAILEDの全29編成（ミラー14・混成15）で必要量を二分探索すると、最大54件だった。**旧上限50はこれを下回っており**、混成編成のgolden 1件（`E2E-GOLDEN-PARTY-GUARD`が追跡していた組み合わせ）は暴走ではなく正常な戦闘でありながら`EXECUTION_LIMIT_EXCEEDED`（503）で落ちていた。実測値の約1.9倍へ引き上げ、当該編成は完走へ変わった。必要量はミラー編成1つだけを見ると40件と出るため、**上限を見直す際は必ず混成編成を含めて測り直す**こと。
- **`SIMULATION_MAX_EVENTS`（1000000）・`SIMULATION_MAX_PASSIVE_DEPTH`（8）・`SIMULATION_MAX_EFFECT_RUNTIME_COUNTER_DEPTH`（10）は据え置き、manifestへ明示する。** 実測の最悪値はそれぞれ36,482件（27倍の余裕）・深度4（2倍）で、引き下げる必要も引き上げる必要もない。値そのものより「配備時に何が効いているかが読める」ことを重視して宣言する。
- **圧縮は「アプリケーション層が担当し、閾値1 KiB、`Accept-Encoding`に応じてgzip／brを返す」と決定する。** Cloud Runは応答を自動圧縮しないため、担当はアプリケーション以外にない。23.1 MBが1.32 MBへ落ちる効果は大きく、生成コストは75ms（1 vCPUでは数倍）で実行期限に対して十分小さい。**この決定の実装（`@fastify/compress`の導入）は本Issueでは行っていない** — 新しいruntime依存の追加は`REL-006`／Issue #197が持つ依存脆弱性・supply chain検査と同じPRで扱うほうが安全なためで、#197の作業項目として引き継ぐ。

上限を将来変更する場合は、`mise run test:load`で baseline を取り直し、この表と
`deploy/cloud-run/service.json`の両方を更新する。

GitHub Pagesからの初期アクセスではscale-to-zero後のcold startが発生し得る。Catalog読込とWorker warm-upが完了してからlistenする既存起動順を維持し、不完全なreadinessでrequestを受け付けない。

## 起動

1. `.env.example`を参考に環境変数を設定する（`PORT`・`CATALOG_PATH`・`LOG_LEVEL`・
   `SHUTDOWN_GRACE_MS`など）。
2. `mise run build`でTypeScriptをコンパイルする。
3. `node apps/api/dist/main.js`で起動する（`mise run dev`は開発時の`tsx watch`版）。
4. `apps/api/src/bootstrap/index.ts`の`bootstrap()`が次を順に行う。
   - Catalog manifestから期待する`catalogRevision`を読む。
   - `SimulationWorkerPool.create()`でWorkerをwarm-upし、Catalogの読み込み・
     検証・リビジョン一致を確認する（失敗時はここで例外を投げ、HTTPポートを
     一切公開しない）。
   - `buildServer()`でFastifyインスタンスを構築し、`/health/live`・
     `/health/ready`・`GET /api/v1/battle-simulation-catalog`・`POST /api/v1/battle-simulations`を登録する。
   - SIGTERM/SIGINTハンドラーを登録する（`installShutdownSignalHandlers`）。
   - `listen()`してから起動ログ（`catalogRevision`・`workerMaxQueue`・
     `simulationTimeoutMs`）を1行出す。
5. Worker初期化に失敗した場合、`bootstrap()`は例外をrejectし、`main.ts`が
   `process.exit(1)`する。ポートは開かれない。

## OpenAPI文書とSwagger UI

`11_インフラストラクチャ設計.md`「OpenAPI」: `GET /openapi.json`は常に生成済みの
OpenAPI 3.0.3文書を返す。Swagger UI（`GET /docs`）は`NODE_ENV`が`production`
以外の場合だけ`bootstrap()`が有効化する——productionでは既定で公開しない
（`apps/api/src/bootstrap/index.ts`の`docsEnabled`、
`apps/api/src/presentation/http/build-server.ts`の`BuildServerOptions.docsEnabled`）。

1. `mise run dev`で起動する（`.env.example`の既定`NODE_ENV=development`のまま）。
2. ブラウザで `http://localhost:3000/docs` を開くとSwagger UIが表示される。
   `POST /api/v1/battle-simulations`の仕様を確認し、UIから最小戦闘リクエストを
   実行できる。
3. `http://localhost:3000/openapi.json` はSwagger UIの有効・無効に関わらず、
   同じOpenAPI文書を返す。
4. `NODE_ENV=production`で起動した場合、`GET /docs`は`404`を返す。

## ヘルスチェック

| エンドポイント      | 成功条件                                                                                 | 用途                                     |
| ------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------- |
| `GET /health/live`  | プロセスがHTTP応答可能であること。Catalog障害やPool飽和では失敗しない。                  | プロセスの生存確認（再起動要否の判定）。 |
| `GET /health/ready` | シャットダウン未開始、かつWorker Poolが健全（稼働中のCatalogリビジョン不一致が未発生）。 | ロードバランサーへのトラフィック可否。   |

`/health/ready`は`503`を返す際も`{"status":"not_ready"}`のような最小bodyのみを返す
——Catalogの中身・環境変数・エラーのスタックは含めない。

起動シーケンス上、`listen()`に到達する時点で必要ワーカー数のwarm-upと
Catalog検証は既に完了しているため、「準備未完了」を外部から観測できるのは
実質的に次の2状態だけになる。

- Graceful Shutdown開始後（`ShutdownState.markShuttingDown()`）。
- 稼働中にWorkerがCatalogリビジョン不一致を報告し、Pool全体が致命的状態に
  なった後（`SimulationWorkerPool.isHealthy`が`false`）。

## Graceful Shutdown

SIGTERMまたはSIGINTを受信すると、`runGracefulShutdown`が次を行う。

1. `ShutdownState.markShuttingDown()`——`/health/ready`が即座に失敗を返すようになる。
2. 以後の`POST /api/v1/battle-simulations`はUseCaseへ到達せず、
   `503 CAPACITY_EXCEEDED`（`Retry-After`付き）を返す。
3. `app.close()`（HTTP keep-alive接続のdrain）と`pool.shutdown()`
   （Worker Poolの停止）を同時に開始する。
   - `pool.shutdown()`は未開始タスクを即座にキャンセルし、実行中タスクを
     `SHUTDOWN_GRACE_MS`まで待ってから、残っていれば強制終了する
     （どちらの経路でも`EXECUTION_CANCELLED`として応答する）。
   - `app.close()`は、対応するHTTPハンドラーが完了・rejectし次第、drainを終える。
4. 両方の完了を待って`process.exit(0)`する。シャットダウン処理自体が失敗した
   場合はエラーをログへ記録し`process.exit(1)`する。

ロードバランサーのdrain猶予は`SHUTDOWN_GRACE_MS`より長く設定する。戦闘結果を
永続化しないため、シャットダウン中に中断した結果は復旧しない。

Cloud RunはSIGTERM後10秒でcontainerを強制終了し得るため、productionの `SHUTDOWN_GRACE_MS`は8000とする。8秒以内に完了しない実行中simulationはキャンセルし、不完全な戦闘結果を成功として返さない。

## Production ContainerとCloud Run service基盤

`#105`（`M45-INFRA-001`）が次を用意する。CI/CDへの配線（Artifact Registry push、
Cloud Run deploy、post-deploy smoke test、rollback）は`#106`（`M45-INFRA-002`）
のスコープ。

- [`Dockerfile`](../Dockerfile)：multi-stage build。production依存
  （`pnpm install --frozen-lockfile --prod`）、`tsc`でコンパイルした
  `apps/api/dist/`、`catalog/`（`CATALOG_PATH`の既定値に合わせ`/app/catalog`へ
  flattenして含める）だけをruntime imageへ含める。`node@sha256:...`
  （`node:24.18.0-bookworm-slim`、mise.tomlのNode.jsバージョンと一致）を
  `--platform=linux/amd64`で固定し、non-root user（`nodeapp`、uid/gid 1001）

- [`deploy/cloud-run/service.json`](../deploy/cloud-run/service.json)：
  「Cloud Run配備構成（初期値／M9確定値）」の初期値（CPU/Memory、min/max instance、concurrency、
  timeout、`WORKER_MAX_QUEUE`、`SHUTDOWN_GRACE_MS`、CORS origin）を宣言する
  Knative Service manifest（`gcloud run services replace`が読む形式）。
  値は`11_インフラストラクチャ設計.md`「M4.5 Cloud Run初期設定」の理由付き表を

  が自動で一致を検証する。適用コマンドと`region`/`project`の渡し方は
  [`deploy/cloud-run/README.md`](../deploy/cloud-run/README.md)を参照。
- `mise run test:container`（[`scripts/container-smoke-test.sh`](../scripts/container-smoke-test.sh)、
  Docker必須）：image build、non-root起動、`PORT`上書き・`0.0.0.0` bind、

## Cloud Run deploy

1. PRでformat、typecheck、lint、test、production build、container build、local container smoke testを成功させる。
2. main workflowがGitHub OIDC tokenを使い、Workload Identity FederationでGoogle Cloudの短期credentialを取得する。
3. commit SHAで識別できるimageをArtifact Registryへpushし、image digestを記録する。
4. 新Cloud Run revisionを既存trafficへ即時反映せずにdeployする。
5. 新revisionに対して `/health/live`、`/health/ready`、Catalog GET、最小simulation、GitHub Pages originのCORSを確認する。
6. 成功後にproduction trafficを新revisionへ移す。
7. Cloud Run service URLをGitHub Environmentの `VITE_API_BASE_URL`へ設定し、Pagesをbuild・deployする。
8. deployed PagesからCatalog取得と最小simulationを再確認する。

GitHubへGoogle Cloud service account JSON keyを保存しない。Workflowのprincipal条件はこのrepositoryとproduction environmentへ限定する。

### 実装（`#106` `M45-INFRA-002`）

- [`.github/workflows/pr.yml`](../.github/workflows/pr.yml)の`container` jobが、PRごとに
  `mise run test:container`（production container build + local Docker smoke test）を実行する
  （Cloud Runへはdeployしない）。
- [`.github/workflows/main.yml`](../.github/workflows/main.yml)の`deploy` jobが、`quality`
  job成功後だけ実行される。`google-github-actions/auth`でWorkload Identity Federationの
  短期credentialを取得し（`google-github-actions/setup-gcloud`でgcloud CLIへ引き継ぐ）、
  [`scripts/cloud-run/02-build-and-push-image.sh`](../scripts/cloud-run/02-build-and-push-image.sh)
  でimageをbuild・push、image digestを記録する。
- [`scripts/cloud-run/ci-deploy-candidate.sh`](../scripts/cloud-run/ci-deploy-candidate.sh)が、
  `gcloud run services replace`一回の呼び出しで、既存revisionへtraffic 100%を明示的に固定
  したまま、新revisionを`candidate` tag付き・traffic 0%で作成する（`gcloud run services
replace`は`--no-traffic`を持たないため、manifest自体の`spec.traffic`で宣言する。
  [`apps/api/src/infrastructure/deploy/cloud-run-manifest.ts`](../apps/api/src/infrastructure/deploy/cloud-run-manifest.ts)
  が該当ロジックをunit testで検証する）。traffic切替の隙間は生じない。「既存revision」は
  Serviceの`status.traffic`でpercentが厳密に100のrevisionだけを正とする
  （[`apps/api/src/infrastructure/deploy/cloud-run-traffic.ts`](../apps/api/src/infrastructure/deploy/cloud-run-traffic.ts)
  の`resolveCurrentRevisionName`）——`status.latestReadyRevisionName`は使わない。
  smokeに失敗して一度もpromoteされていないcandidateもReady状態にはなり得るため、それを
  「現在productionのrevision」と誤認して次回deployでtraffic 100%を割り当ててしまう。
- CIは初回Cloud Run deployを行わない——最初のrevisionは
  [`scripts/cloud-run/03-deploy-service.sh`](../scripts/cloud-run/03-deploy-service.sh)
  （一度限りの手動セットアップ）で事前に作成済みの前提とする。`gcloud run
services describe`の失敗（一時的なネットワーク障害等）やservice未作成により
  現在100% trafficを受けているrevisionを特定できない場合、それを「初回deploy
  （bootstrap）」として扱い新revisionへ即100% trafficを割り当てることは、Issue
  #106の安全条件「smoke test成功後にのみtrafficを確定する」に反するため、
  `ci-deploy-candidate.sh`・[`apps/api/src/infrastructure/deploy/render-cloud-run-manifest-cli.ts`](../apps/api/src/infrastructure/deploy/render-cloud-run-manifest-cli.ts)・`buildCandidateTrafficTargets`の3層でfail closedする。
- rollback先は「直近のReady revision」では選ばない。複数回連続でcandidateがsmokeに
  失敗すると、未promoteの失敗revisionがReadyのまま残り、`candidate` tagは常に最新の
  失敗revisionへ移るため、tagだけの除外でも古い失敗revisionを再選択し得る。代わりに、promote成功時にだけ
  更新される永続的な2つのtagで判定する——`stable`（現在100% trafficの、最後に
  promoteされたrevision）と`stable-previous`（直前にpromoteされていたrevision、
  1段階のrollback履歴）。[`scripts/cloud-run/ci-promote-traffic.sh`](../scripts/cloud-run/ci-promote-traffic.sh)
  がpromote成功時にこの2つのtagを回す——`--to-revisions`（traffic 100%切替）と
  `--update-tags`（tag rotation）は同一の`gcloud run services update-traffic`
  呼び出しにまとめる。2回の別呼び出しに分けると、traffic切替後にtag更新だけが
  失敗した場合、新revisionが既にproductionなのに`stable`が旧revisionを指した
  ままになり、以後のrollback先・次回promoteの履歴判定を誤る。
  `gcloud run services replace`はdeployのたびに`spec.traffic`全体を新しい
  desired stateとして適用するため、`ci-deploy-candidate.sh`は`stable`／
  `stable-previous`タグを毎回のmanifestへ明示的に再宣言し、deploy attempt
  （成功・失敗いずれでも）で失われないようにする
  （`buildCandidateTrafficTargets`のunit testが検証する）。
- candidateのCatalog GETから選択可能なUnitを探し、
  [`apps/api/src/infrastructure/deploy/simulation-smoke-request.ts`](../apps/api/src/infrastructure/deploy/simulation-smoke-request.ts)
  で最小simulation requestを組み立てる。選択可能なUnitが無い場合は`deploy` jobをここで
  失敗させる——simulation smoke testを黙ってskipしない。
- [`scripts/cloud-run/04-smoke-test.sh`](../scripts/cloud-run/04-smoke-test.sh)を
  `candidate` tag付きURLに対して実行する。live・ready・Catalog GET・最小simulationに加え、
  CORS preflight（OPTIONS）だけでなく実際のcross-origin GET/POSTでも
  `Access-Control-Allow-Origin`を確認する。失敗した場合はjobがここで停止し、
  [`scripts/cloud-run/ci-promote-traffic.sh`](../scripts/cloud-run/ci-promote-traffic.sh)
  （traffic 100%への昇格）は実行されない——新revisionへproduction trafficは流れない。
- 成功後、`deploy` jobがCloud Run service URLを`production` GitHub Environmentの
  `VITE_API_BASE_URL` variableへ書き込む（`gh variable set`。既定の`GITHUB_TOKEN`では
  repository/environment variableを書き換えられないため、Variables書き込みのみに
  絞ったfine-grained PATを`VARS_ADMIN_TOKEN` secretとして使う）。Pagesのbuild・deploy
  自体は`#99`（`M45-UI-007`）のスコープ。
- Workload Identity Pool／Provider・最小権限deploy service accountは
  [`scripts/cloud-run/00-bootstrap-ci-cd.sh`](../scripts/cloud-run/00-bootstrap-ci-cd.sh)
  （project IAM adminが一度だけ手動実行）で作成する。OIDC providerの`attribute-condition`は
  このrepositoryと`production` GitHub Environmentへ限定する。
- Cloud Run serviceはallUsersへ公開されている（unauthenticated invocation）ため、
  `deploy/cloud-run/service.json`の`spec.template.spec.serviceAccountName`で、
  project IAM roleを一切持たない専用runtime service account
  （`battle-sim-api-runtime@<project>.iam.gserviceaccount.com`、
  `00-bootstrap-ci-cd.sh`が作成）を明示する。指定を省略するとCloud Runはproject既定の
  Compute Engine service account（既定でroles/editorを持つ）をruntime identityとして
  使ってしまい、application・依存パッケージの侵害がProject Editor相当のGoogle Cloud
  credential奪取に直結する。この専用SAはGoogle Cloud APIを呼ばないため、project IAM role
  はゼロでよい。
- Billing budget alertとlog保持期間は
  [`scripts/cloud-run/00b-configure-billing-and-logging.sh`](../scripts/cloud-run/00b-configure-billing-and-logging.sh)
  （Billing Account Administratorが一度だけ手動実行）で設定する。

## Cloud Run rollback

1. 障害がUI、Cloud Run到達性、application、Catalog revisionのどこにあるかをRequest IDとrevisionで切り分ける。
2. 新revisionのtrafficを0へ戻し、直前にsmoke test成功済みのrevisionへ100%移す
   （[`.github/workflows/rollback-cloud-run.yml`](../.github/workflows/rollback-cloud-run.yml)を
   `workflow_dispatch`で手動実行する。`target_revision`省略時は、Serviceの
   `stable-previous` tag（promote成功時にだけ更新される、直前にpromoteされていた
   revisionの永続的な記録）が指すrevisionを自動検出する
   [`scripts/cloud-run/ci-rollback-traffic.sh`](../scripts/cloud-run/ci-rollback-traffic.sh)を使う。
   「直近のReady revision」は使わない——未promoteの失敗revisionもReadyになり得るため。`stable-previous` tagが無い
   （promote実績が1回以下、または既にrollback済み）場合はjobを失敗させるため、
   `target_revision`を明示する）。traffic切替・`stable`更新・`stable-previous`削除は
   同一の`gcloud run services update-traffic`呼び出しにまとめる。rollback後も
   `stable-previous`を残すと、次回の自動rollbackが「現在trafficを受けている
   revision（rollback直後のtarget自身）」を再び選び、no-opのまま成功扱いになって
   しまうため、rollback成功時に必ず`stable-previous`を削除する。より過去のrevisionへ
   さらにrollbackしたい場合は`target_revision`を明示する。
3. `/health/ready`、Catalog GET、最小simulationを確認する（rollback workflowが、
   main deployと同様にrollback先のCatalogから選択可能なUnitを探してrequestを
   組み立て、`04-smoke-test.sh`を自動で再実行する。選択可能なUnitが無い場合は
   rollback workflow自体を失敗させる——simulation smoke testを黙ってskipしない）。
4. API URL自体が変わらない場合はPagesを再deployしない。変更した場合だけGitHub Environmentを戻してPagesを再buildする。
5. 失敗したimage digest、Git SHA、Cloud Run revision、Catalog revision、diagnostic IDを障害記録へ残す
   （`deploy` jobの`GITHUB_STEP_SUMMARY`に記録済みの値を参照できる）。

maximum instancesは費用の絶対上限ではない。Google Cloud Billing budget alert、Cloud Run instance count、request count、5xx、latencyを確認し、想定外の利用時はservice停止またはinvocation方針の再検討を行う。

## GitHub Pages deploy

1. `deploy`（API）jobが成功または`run_api == 'false'`でskipされ、`quality`・`ui` jobが成功したcommitに対してのみ実行する（UI-only mergeはCloud Run deployをskipしたまま、直近production deployで書き込み済みの`VITE_API_BASE_URL`を使う）。
2. `production` GitHub Environmentの`VITE_API_BASE_URL`（実際のCloud Run service URL）と、GitHub Pagesのproject page base path（`/muvluvgg_battle_simulator/`）、`VITE_BUILD_REVISION`（deployしたGit SHA）を渡してUIをbuildする。
3. buildしたPages artifactを`actions/deploy-pages`でGitHub Pagesへdeployする。
4. deploy後、deployed Pages URLに対してPlaywright live smoke testを実行し、実Cloud Run APIとのCatalog GET・CORS preflight・ETag/304・最小1対1 simulationを確認する（Cloud Runがdeploy直後のsmoke testで既にwarmなため、cold start自体はここでは実証しない。下の`pages-live-smoke-cold-start.yml`の説明を参照）。

### 実装（`#99` `M45-UI-007`）

- [`.github/workflows/main.yml`](../.github/workflows/main.yml)の`pages-build`・`pages-deploy`・`pages-smoke`
  jobが該当する。gate jobのskipが「workspace未変更による正当なskip」か「上流失敗の巻き添え」かは
  `needs.*.result`だけでは区別できないため、その判定は`gate` jobのoutputs（`deploy_api` / `publish_ui`）
  へ集約されている——`publish_ui`は`ui`成功に加えて`quality`がsuccess/skippedであることを要求する
  （Full Quality Gate失敗commitを`ui`成功だけでPagesへ公開しない）。`pages-build`は
  `publish_ui == 'true'`と`needs.deploy.result`がsuccess/skippedであることを条件にし、
  `pages-deploy`・`pages-smoke`は前段jobの`result == 'success'`を明示condition化する
  ——`needs`だけではskipされた前段からartifactなしでdeployを試みてしまう。
- `pages-build`は`environment: production`で`vars.VITE_API_BASE_URL`（`deploy` jobが書き込み済みの
  実際のCloud Run service URL）を読み、CIの`ui` job（`https://ci-build-placeholder.invalid.example`
  固定）とは別にbuildし直す。`index.html`のCSP `content-security-policy` metaの`connect-src`は
  Vite組み込みのHTML env置換（`%VITE_API_BASE_URL%`）でこの値へ静的に展開される
  （05\_非機能・アクセシビリティ設計.md §11、動的文字列連結はしない）。
- `pages-deploy`は`environment: github-pages`（`actions/deploy-pages`が要求する既定のenvironment名。
  初回成功deployでGitHubが自動作成する）を使う。`concurrency: group: pages-deploy`で連続pushの
  deploy競合を防ぐ（GitHub Pages公式テンプレートと同じ設定）。
- `pages-smoke`は`apps/ui/playwright.live.config.ts`・`apps/ui/e2e-live/`（`mise run ui:e2e:live`）を
  実行する。`06_UIテスト戦略.md`§9「Live API E2Eは初期は別job」の通り他jobの成否をgateしない
  ——失敗しても`pages-deploy`まで完了したPages deployは維持される。`playwright.live.config.ts`は
  test timeoutを120秒、navigation timeoutを60秒へ拡張しているが、`deploy`（API）が実行された回は
  直前のCatalog／simulation smoke testでCloud Run instanceが既にwarmなため、`pages-smoke`単体では
  scale-to-zero後のcold startを実証できない。
- [`.github/workflows/pages-live-smoke-cold-start.yml`](../.github/workflows/pages-live-smoke-cold-start.yml)
  が深夜cron（`workflow_dispatch`でも手動実行可）で同じlive smoke testを独立実行する。cron時刻は
  scale-to-zeroの可能性を高めるだけで、外部trafficや直前の手動操作でinstanceが既にwarmだった場合と
  結果から区別できないため、test実行前後で`gcloud logging read`
  により`apps/api/src/bootstrap/index.ts`が`listen()`直後に1回だけ出す起動ログ
  （`"muvluvgg-battle-simulator started"`）がtest window内に記録されたことを直接確認する。見つから
  なければ「cold startを確認できなかった」としてjob自体を失敗させる——Issue #99受け入れ条件
  「scale-to-zero後のcold startを含むlive smoke testが成功する」は、この起動ログの実測でのみ
  成立とみなす。Cloud Loggingの取り込み遅延を考慮し、最大5分（20秒間隔×15回）poll/retryしてから
  失敗させる——Playwright終了直後の1回だけの検索では、実際はcold startが成功していてもログが
  まだ検索可能になっておらず誤検知し得るため。この
  `gcloud logging read`には`logging.logEntries.list`権限が必要で、
  [`scripts/cloud-run/00-bootstrap-ci-cd.sh`](../scripts/cloud-run/00-bootstrap-ci-cd.sh)が
  deploy用service accountへ`roles/logging.viewer`を付与する（既存の`roles/run.developer`には
  含まれない）。
  - `UI-E2E-LIVE-001`/`005`（[`apps/ui/e2e-live/catalog-cors.spec.ts`](../apps/ui/e2e-live/catalog-cors.spec.ts)）:
    deployed Pagesのdocument内から`fetch()`でCatalog GETを行い、`If-None-Match`付きの2回目の
    GETで304を確認する——`If-None-Match`はCORS safelisted headerではないため、実ブラウザが
    このoriginから本物のOPTIONS preflightを送る。CORS misconfigurationは`fetch()`自体の失敗
    として現れる。
  - `UI-E2E-LIVE-002`〜`004`（[`apps/ui/e2e-live/minimal-battle.spec.ts`](../apps/ui/e2e-live/minimal-battle.spec.ts)）:
    実Catalogが返す選択可能なUnitを`aria-label`の`を選択`suffixから汎用的に選び（display nameを
    hardcodeしない）、最小1対1を実行する。結果の具体的な勝敗やdamage値は固定せず、完了・
    Request ID表示・一覧APIとsimulation responseのCatalog revision一致だけを検証する
    （06_UIテスト戦略.md §6「乱数結果の具体値を固定しない」）。
- UI build revision（`VITE_BUILD_REVISION`）・API Catalog revision・Request IDは
  [`apps/ui/src/components/AppShell.tsx`](../apps/ui/src/components/AppShell.tsx)のfooterと

## GitHub Pages rollback

`actions/deploy-pages`は常にその回のworkflow runがuploadしたPages artifactをdeployするため、単純に
「過去のworkflow runを再実行する」操作は保存済みartifactの再配備にならず、現在の
`VITE_API_BASE_URL`（`production` environmentの現在値）や`github.sha`（`VITE_BUILD_REVISION`として
bundleへ埋め込まれる）で**再build**してしまう。revert commitのSHAは前回成功commitと必ず異なるため、
再buildしたcontentは前回成功時と一致し得ない（実測: 同一sourceでも`VITE_BUILD_REVISION`だけが
異なるとdist全体のcontent digestが変わることを実測で確認済み）。したがって「前回成功artifactへのrollback」は、rebuildではなく、保存済みの
静的ファイルそのものをそのまま再deployする経路で実現する。

- [`.github/workflows/main.yml`](../.github/workflows/main.yml)の`pages-build`が、`actions/deploy-pages`
  向けのPages artifactとは別に、同じ`apps/ui/dist`を`pages-dist`という名前の通常artifact
  （`retention-days: 90`）としても保持する。
- [`.github/workflows/pages-rollback.yml`](../.github/workflows/pages-rollback.yml)を
  `workflow_dispatch`で手動実行し、`source_run_id`（復元元にしたい過去の`main.yml`のrun ID）を渡す。
  このworkflowは指定したrunの`pages-dist` artifactを`actions/download-artifact`の`run-id`指定で
  downloadし、**rebuildせずそのまま**`actions/upload-pages-artifact`・`actions/deploy-pages`で
  再deployする——前回成功時と完全に同じ静的ファイルが配信される。別workflow runのartifactを
  downloadするには`GITHUB_TOKEN`に`actions: read`が必要（未指定のpermissionは`none`になるため
  明示しないと403になる）。通常deploy（`pages-deploy`）と
  同じ`concurrency: group: pages-deploy`を使い、rollbackと通常deployが同時に走って完了順次第で
  上書きし合うことを防ぐ。
- concurrency groupの共有は同時実行を防ぐだけで、実行順序までは保証しない——rollback開始前に
  別の`main.yml` runが既に`pages-build`まで進んでいれば、そのrunはrollback完了後に`pages-deploy`
  へ進み、復元した内容を上書きし得る。`main.yml`はAPI／UI両方を扱う共有workflowのため、in-flight
  runを自動cancelすると無関係なCloud Run deployまで巻き添えにしてしまう。そのため`pages-rollback.yml`
  は自動cancelの代わりに、実行前に`main.yml`の未完了（`status != "completed"`。`in_progress`／
  `queued`だけでなく`waiting`／`requested`／`pending`等も含む）runを`gh run list`で確認し、1件でも
  あればfail closedで停止する（pre-check）。加えて、deploy直後にも同じ確認を行い、rollback実行中に
  別runが割り込んでいた場合はwarning（post-check）として可視化する——完全な排他は`main.yml`側を
  変更しない限り保証できないため、「検証する仕組み」として扱う。`gh run list --status`は複数指定してもORにならず最後の値だけが有効になるため、
  statusでの絞り込みはせずjqの`select(.status != "completed")`で判定する。

手順:

1. 障害がPages配信自体か、Cloud Run APIかをUI build revision・Catalog revision・Request IDで切り分ける
   （Cloud Run側の障害は上の「Cloud Run rollback」に従う）。
2. GitHub Actionsの実行履歴（`main.yml`のrun一覧）から、直前に成功していた`pages-build`／
   `pages-deploy`を含むrunを見つけ、そのrun ID（run画面URLの末尾の数値）を控える
   （`pages-dist` artifactの保持期間である90日以内のrunに限る）。
3. `main.yml`のrunがin-progress／queuedで残っている場合は完了を待つ
   （`pages-rollback.yml`のpre-checkがそれを検出してfail closedで停止するため、
   このタイミングで気付ける）。
4. `pages-rollback.yml`を`workflow_dispatch`で実行し、`source_run_id`に手順2のrun IDを入力する。
5. deploy後、画面のfooterに表示されるUI build revisionが復元元commitのGit SHAと一致することを
   確認する（`pages-rollback.yml`はrebuildしないため、この値も含めて前回成功時のまま復元される）。
   `GITHUB_STEP_SUMMARY`にpost-check warningが出ている場合は、割り込んだrunの完了後に改めて
   Pages内容を確認し、上書きされていれば再度rollbackする。
6. 恒久的に戻す場合はmain上の当該commitをrevertし、通常のmain workflowでbuild・deployし直す
   ——`pages-rollback.yml`はPages配信を即座に戻すための応急処置であり、main branchのsource自体は
   変えない。revertを怠ると、次のmainへのmergeで問題のあるcommitが再度deployされてしまう。
7. API URL（`VITE_API_BASE_URL`）自体は変えていないため、Cloud Run rollbackとは独立してPagesだけを
   ロールバックしてよい。逆にCloud Run rollbackでURLが変わらない限り、Pagesの再deployは不要
   （運用手順.md「Cloud Run rollback」手順4と同じ判断基準）。
