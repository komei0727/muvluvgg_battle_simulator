# 戦闘ルール詳細

## 目的

本書は、[06\_戦闘状態遷移.md](./06_戦闘状態遷移.md) の各遷移から呼び出す判定・計算ルールを、実装とテストが可能な粒度で定義する。

各ルールには `R-領域-連番` 形式のルールIDを付ける。テストケース、ドメインイベントおよび後続の実装設計から、このIDを参照できるものとする。

## ルールの優先順位

競合する記述がある場合は、次の順に優先する。

1. [02\_仕様確認事項.md](./02_仕様確認事項.md) の決定事項
2. 本書の詳細ルール
3. スキル・効果定義に委ねられた項目の個別指定
4. [戦闘システム.md](./戦闘システム.md) の基本仕様
5. デフォルトルール

スキル・効果定義による個別指定は、ターゲット方式や効果量など、その定義に委ねられた項目だけを上書きする。最低1ダメージ、PSの1解決スコープ1回制限などの全体不変条件は、明示的に上書きを許可した仕様がない限り変更しない。

## 共通の数値規則

### R-NUM-01 割合の内部表現

- 設計書の100%を内部値 `1.0` として扱う。
- 25%加算は `+0.25`、5%減算は `-0.05` とする。
- ダメージの最終結果を求めるまで、途中値を丸めない。
- ダメージ以外のステータス計算値も途中で丸めず保持する。
- ステータス値の正本は、`Battle` が保持するIEEE 754 binary64値そのものとする。設計書や画面が示す10進表記は同じ値の表示であり、後段の計算がその10進値を推定・復元することはない。

### R-NUM-02 整数化

- 最終ダメージは全補正適用後に小数部分を切り捨てる。
- HP、AP、PP、EXゲージへ適用する `FormulaDefinition` の結果は、適用直前に小数部分を切り捨てる。
- 割合補正、DamageModifier、HealingModifier の倍率値は途中で丸めない。
- AP、PP、EXゲージを負数にしない。
- 回復量、シールド付与量、リソース増減量は適用直前に小数部分を切り捨てる。
- ブレイク強化（R-TEX-04）の強化後ステータスは、保存値（binary64）が表す厳密な有理数と整数のパーセントポイントを合成してから0方向へ切り捨てる。浮動小数の倍率を先に作って掛けない。
- 上記の帰結として、表示上129.2の保存値へ250%を適用した結果は322とする。保存値は10進の129.2をわずかに下回るため、厳密な積は323に達しない。誤差を吸収して323へ引き上げることはしない — 許容幅を設ける方式は、実際の端数（整数から数ULP下にある値）と演算誤差を区別できず、ステータス値に上限が無い以上どこかの領域で必ず取り違えるためである。

### R-NUM-03 確率判定

- 確率判定は `RandomSource` を通して行う。
- 会心率のステータス値自体には上限・下限を設けない。
- 会心判定時の実効会心率だけを0～100%へ補正する。
- 0%は必ず失敗、100%は必ず成功とする。

### R-NUM-04 Formula評価

- `FormulaDefinition` は数値を返し、状態変更を行わない。
- `SUM`、`MIN`、`MAX`、`CLAMP` などの合成Formulaは、子Formulaの評価結果を丸めずに合成する。
- `DAMAGE_DEALT_RATIO` と `DAMAGE_RECEIVED_RATIO` は、直前の確定済みダメージ結果を参照する。
- `MARKER_COUNT_SCALE` は評価時点の `MarkerState.stackCount` を参照する。
- Formula が参照する対象、binding、イベントpayload、直前結果が存在しない場合、その定義は戦闘開始前のCatalog検証またはpreflightで拒否する。

## 編成の検証

### R-FRM-01 編成人数

- 味方・敵それぞれ1～5体とする。
- 0体または6体以上の編成は戦闘開始前に拒否する。

### R-FRM-02 配置

- 各陣営の盤面は横3列、縦2列とする。
- 列は絶対左から左、中央、右とする。
- 行は相手陣営に近い側を前列、遠い側を後列とする。
- 同じ陣営内で同じ配置位置を重複させない。

### R-FRM-03 ユニット重複

- 同じ `UnitDefinitionId` を同一陣営へ複数指定できる。
- 各参加枠へ異なる `BattleUnitId` を割り当てる。
- スキル状態、HP、効果、イベントログは `BattleUnitId` 単位で管理する。

### R-FRM-04 メモリー指定

- 各編成に0～6件のメモリーIDを指定できる。
- 存在しないメモリーIDまたは7件以上の指定を拒否する。
- メモリーの発動条件を満たさなくても入力エラーにはせず、効果を適用しない。

### R-FRM-05 規定ターン数

- 1～99の整数とする。
- 範囲外の値を戦闘開始前に拒否する。

## 共通座標と配置

### R-POS-01 共通座標への変換

列座標：

| 列       |   x |
| -------- | --: |
| 絶対左列 |   0 |
| 中央列   |   1 |
| 右列     |   2 |

行座標：

| 陣営・行 |   y |
| -------- | --: |
| 敵後列   |   0 |
| 敵前列   |   1 |
| 味方前列 |   2 |
| 味方後列 |   3 |

### R-POS-02 前方

- 味方の前方はy座標が減る方向とする。
- 敵の前方はy座標が増える方向とする。
- 絶対左列は陣営の向きにかかわらずx座標が小さい側とする。

### R-POS-03 距離

使用者 `(x1, y1)` と対象 `(x2, y2)` のマンハッタン距離を次で求める。

```text
distance = |x1 - x2| + |y1 - y2|
```

## 編成ボーナス

### R-BON-01 通常属性の役判定

編成が5体の場合、クレバーを除く属性構成について次の最も高い役を一つ適用する。

| 優先順位 | 役             | 条件                 | 攻撃力 |   HP |
| -------: | -------------- | -------------------- | -----: | ---: |
|        1 | ファイブカード | 同属性5体            |   +25% | +25% |
|        2 | フォーカード   | 同属性4体            |   +15% | +20% |
|        3 | フルハウス     | 同属性3体と別属性2体 |   +15% | +15% |
|        4 | スリーカード   | 同属性3体            |   +10% | +10% |

条件を満たさない場合、通常属性の編成ボーナスは0とする。4体以下の編成では役判定を行わない。

### R-BON-02 コミカル

1. 各コミカルをクレバー以外の属性として割り当てた全候補を評価する。
2. `ファイブカード > フォーカード > フルハウス > スリーカード > 役なし` の順で最も高い候補を採用する。
3. 採用した役の補正だけを適用する。
4. コミカルをクレバーとして扱わない。

### R-BON-03 クレバー

クレバーの人数が条件を満たしたすべての段階を累積する。

| 人数条件 | 追加補正           |
| -------- | ------------------ |
| 1人以上  | 防御力+30%         |
| 2人以上  | 攻撃力+10%、HP+10% |
| 3人以上  | 会心率+15%         |
| 4人以上  | 攻撃力+15%、HP+15% |
| 5人以上  | 攻撃力+25%、HP+25% |

例としてクレバー3人の場合、防御力+30%、攻撃力+10%、HP+10%、会心率+15%をすべて適用する。

会心率+15%はパーセントポイント加算ステータスへの編成補正であり（R-STA-01）、基本会心率20%のユニットでは35%になる。防御力・攻撃力・HPの補正は割合補正ステータス側であり、従来どおり基本値へ乗算する。

## 基本ステータス強化

APIリクエストの強化指定がある陣営のユニットに限り、本領域のルールで強化後基本ステータスを算出し、R-STA-01の基本値として使用する。強化指定がない場合はユニット定義の基本ステータスをそのまま基本値とする（従来動作。既存リクエストの結果を変えない）。

### R-ENH-01 強化指定と適用範囲

1. 強化指定は、陣営単位の指定（学園レベル）とユニット単位の指定（現在レベル、ギアカスタム）からなる。
2. 陣営の強化指定があるとき、その陣営の全ユニットが強化計算の対象になる。強化対象のユニットにはタイプ装備・モジュール（R-ENH-03）を常に適用する。
3. ユニット単位の強化指定は、その陣営の強化指定があるときだけ許可する。陣営の指定なしにユニット単位の指定がある場合は、リクエスト不備として戦闘開始前に拒否する。
4. 既定値は学園レベル全系統1、現在レベル200、ギア0個とする。既定値の明示指定は無指定と同じ算出結果になる。
5. 強化の対象ステータスはHP、攻撃力、防御力、行動速度、会心率、会心ダメージボーナス、属性相性ボーナスの7種とする。AP、PP、EXゲージ最大値は強化しない。
6. 味方・敵陣営の強化指定は独立とする。

### R-ENH-02 学園レベル加算

1. 学園レベルはタイプ3系統（物理・EN・敏捷）と属性6系統の計9系統を持つ。各系統は1以上の整数で、上限を設けない。
2. 各系統はレベル1から開始し、1レベル上がるごとにHP→攻撃力→防御力→HP…のローテーションで1ステータスへ加算する。
3. レベル `L` の系統の加算回数は `n = L − 1` とし、HPへ `⌊(n + 2) / 3⌋` 回、攻撃力へ `⌊(n + 1) / 3⌋` 回、防御力へ `⌊n / 3⌋` 回加算する。
4. 1回あたりの加算量は次のとおりとする。

   | 系統             |  HP | 攻撃力 | 防御力 |
   | ---------------- | --: | -----: | -----: |
   | タイプ学園レベル | 120 |     90 |     50 |
   | 属性学園レベル   | 240 |    180 |    100 |

5. 各ユニットには、自身のユニットタイプに対応するタイプ系統と、自身の属性に対応する属性系統の加算値だけを適用する。
6. 例: 物理タイプ学園レベル50は `n = 49` で HP+2040（17回）／攻撃力+1440（16回）／防御力+800（16回）を全物理タイプのユニットへ加算する。アグレッシブ属性学園レベル50は HP+4080／攻撃力+2880／防御力+1600を全アグレッシブ属性のユニットへ加算する。

### R-ENH-03 タイプ装備・モジュール

1. タイプ装備は全ユニット共通の固定加算とする: HP+19320、攻撃力+14340、防御力+7980。
2. モジュールは全ユニット共通の固定加算（HP+3628、攻撃力+2721、防御力+1515）と、HP・攻撃力・防御力への割合補正9%を持つ。
3. どちらも強化対象のユニットへ常時適用し、個別のON/OFFを設けない（Q-ENH-04）。

### R-ENH-04 ギアカスタム

1. 1ユニットへ最大9個のギアを指定できる。
2. 各ギアは対象ステータス（R-ENH-01の7種のいずれか）、種別（ギアⅡ／ギアⅢ）、ランク（D／C／B／A／S）を持つ。
3. 補正割合（パーセントポイント）は次表のとおりとする。

   | 対象ステータス       | Ⅱ-D  | Ⅱ-C  | Ⅱ-B  | Ⅱ-A  | Ⅱ-S   | Ⅲ-D | Ⅲ-C  | Ⅲ-B  | Ⅲ-A  | Ⅲ-S  |
   | -------------------- | ---- | ---- | ---- | ---- | ----- | --- | ---- | ---- | ---- | ---- |
   | HP                   | 0.75 | 1.18 | 1.62 | 2.06 | 2.49  | 1   | 1.58 | 2.16 | 2.75 | 3.33 |
   | 攻撃力               | 0.75 | 1.18 | 1.62 | 2.06 | 2.49  | 1   | 1.58 | 2.16 | 2.75 | 3.33 |
   | 防御力               | 0.75 | 1.18 | 1.62 | 2.06 | 2.49  | 1   | 1.58 | 2.16 | 2.75 | 3.33 |
   | 行動速度             | 1.5  | 2.62 | 3.37 | 4.49 | 5.4   | 2   | 3.5  | 4.5  | 6    | 7.19 |
   | 会心率               | 1.5  | 2.62 | 3.59 | 4.49 | 5.25  | 2   | 3.5  | 4.8  | 6    | 7    |
   | 会心ダメージボーナス | 3.75 | 6.37 | 8.62 | 10.5 | 12.37 | 5   | 8.5  | 11.5 | 14   | 16.5 |
   | 属性相性ボーナス     | 3.75 | 4.87 | 5.43 | 6    | 6.37  | 5   | 6.5  | 7.25 | 8    | 8.5  |

4. 同一の対象ステータスのギアを複数指定でき、補正割合は単純加算する。
5. ステータスごとのギア合計割合は、表のパーセント値の合計を100で割った小数（R-NUM-01の内部表現）として算出式へ合成する。

### R-ENH-05 レベル増加

1. ユニット定義の基本ステータスはレベル200時点の値とする。
2. ユニット定義はレベル1あたりの成長値 `levelGrowth`（HP、攻撃力、防御力、行動速度）を任意フィールドとして持てる。成長値はユニットごとに固定の非負整数とする。
3. 現在レベル `L` を指定した場合、HP・攻撃力・防御力・行動速度へ `(L − 200) × 成長値` を加算する。`L < 200` の負方向も同式で扱う。
4. `L` は1以上の整数とし、上限を設けない。
5. `levelGrowth` を持たないユニットへ `L ≠ 200` を指定した場合は、リクエスト不備として戦闘開始前に拒否する。`L = 200`（または無指定）は `levelGrowth` を参照しない。

### R-ENH-06 強化後基本ステータスの算出

対象ステータスごとに次を計算する。

```text
HP／攻撃力／防御力 =
  (基本値 + タイプ学園加算 + 属性学園加算 + タイプ装備加算 + モジュール固定加算 + (L − 200) × 成長値)
  × (1 + 0.09 + ギア合計割合)

行動速度 =
  (基本値 + (L − 200) × 成長値) × (1 + ギア合計割合)

会心率／会心ダメージボーナス／属性相性ボーナス =
  基本値 + ギア合計割合
```

- `0.09` はモジュールの割合補正（R-ENH-03）であり、HP・攻撃力・防御力だけに掛かる。
- 途中値・最終値とも丸めない（R-NUM-01。全精度のままR-STA-01の基本値へ渡す）。
- 算出結果が負になる場合は0へ、最大HPが1未満になる場合は1へ切り上げる。
- 強化後基本ステータスはR-STA-01の基本値としてだけ使用する。編成補正・適性補正・戦闘中割合補正・メモリー固定値補正は既存規則のまま強化後の基本値へ合成する。
- 演習モードの原基準値スナップショット（R-TEX-04）も、強化後基本ステータスから算出した基礎戦闘ステータスを基準にする。

## 戦闘中ステータス

### R-STA-01 基本式

ステータスは補正の合成方法で2種類に分かれる。どちらに属するかはステータスごとに固定であり、補正の宣言側（編成補正・Catalog定義）では変えられない。

**割合補正ステータス**（HP、攻撃力、防御力、行動速度）

```text
戦闘中ステータス =
  基本値
  × (1 + 編成補正 - 適性補正)
  × (1 + 戦闘中割合補正)
  + メモリー固定値補正
```

**パーセントポイント加算ステータス**（会心率、会心ダメージボーナス、属性相性ボーナス）

```text
戦闘中ステータス =
  基本値
  + 編成補正
  + 戦闘中補正
  + メモリー固定値補正
```

- パーセントポイント加算ステータスは、それ自体がパーセンテージで表される値であり、補正もパーセンテージの加減算としてだけ与えられる。会心率20%のユニットへ「会心率5%上昇」が乗れば25%であり、21%（`20% × 1.05`）ではない。
- この分類は強化計算（R-ENH-06「会心率／会心ダメージボーナス／属性相性ボーナス = 基本値 + ギア合計割合」）および演習ブレイク強化（R-TEX-04「原基準値 + `n` パーセントポイント」）と同一である。基本値の算出から戦闘中の合成まで、3ステータスは一貫してパーセントポイントの加減算だけを受ける。
- R-BON-03 の「3人以上でクレバー会心率+15%」はパーセントポイント加算ステータスへの編成補正であり、基本会心率20%のユニットでは35%になる。R-BON-01〜03 の他の補正（HP・攻撃力・防御力）は割合補正ステータス側である。
- パーセントポイント加算ステータスは適性補正を受けない（R-STA-01の適性補正対象はHP・攻撃力・防御力だけであり、この3ステータスでは常に0である）。
- パーセントポイント加算ステータスへの戦闘中補正は、`APPLY_STAT_MOD` の `valueType: FIXED` としてだけ宣言できる。`RATIO` は割合乗算を意味するためこの3ステータスに対しては不正であり、Catalogロード時点で拒否する（`14_Catalog定義スキーマ.md`「APPLY_STAT_MOD」）。
- 会心率は加算の結果が負になり得る。実効値への切り上げ・切り下げはR-CRT-01が行い、本規則では負値のまま保持する。
- 適正外配置によるHP、攻撃力、防御力の適性補正は `0.05` とする。
- 適正外配置の影響を受けないステータスでは適性補正を0とする。
- 編成補正、戦闘中割合補正、戦闘中補正、メモリー固定値補正は対象ステータスごとに集計する。

### R-STA-02 重複あり効果

- 同種の重複ありバフ・デバフをすべて有効とする。
- 有効な効果量を符号付きで加算する。
- メモリーの割合補正を重複ありバフとして加算する。

### R-STA-03 重複なし効果

- `EffectKindKey` が同じ重複なし効果を一つのグループにする。
- グループ内で効果の強度が最も大きい1件だけを計算へ採用する。バフは正の効果量、デバフは弱化量の大きさで比較する。
- 同じ絶対値の候補が複数ある場合も計算結果は同じため、効果インスタンスは変更せず最初に付与されたものを代表として扱う。
- 採用されない効果も、期間経過や解除に備えて保持する。

### R-STA-04 再計算

次の状態変更後、影響を受ける戦闘中ステータスを再計算する。

- バフ・デバフの付与、更新、解除、失効
- メモリー効果の有効・無効条件の変化
- その他、ステータス補正条件の変化

行動速度が変化した場合は、現在の1行動とPS/Memory連鎖完了後に未行動者を並べ直す。

## 行動順

### R-ORD-01 行動可能判定

戦闘可能であり、次のいずれかを満たすユニットを新しい行動順キューの候補とする。

- APが1以上
- EXゲージが満タン
- 凍結などで阻害されていないチャージ効果が発動待ち

### R-ORD-02 並べ替え

次の比較キーを上から順に適用する。

1. 現在の行動速度：降順
2. 陣営：味方、敵
3. 行：前列、後列
4. 列：絶対左、中央、右

この比較によって行動順を一意にする。

### R-ORD-03 行動種別予約

- キュー生成時点でEXゲージが満タンならEXを予約する。
- 満タンでなければASを予約する。
- キュー生成後にEXゲージが満タンになっても予約を変更しない。
- 速度変化による並べ替えでも予約を変更しない。
- チャージ効果発動は実効行動決定時にAS／EX予約より優先する。

### R-ORD-04 速度変化

1. 現在の1行動とPS/Memory連鎖を完了する。
2. キューから処理済み・戦闘不能のユニットを除く。
3. 残った未行動者を `R-ORD-02` で並べ直す。
4. 各予約のAS／EX種別を維持する。

## AS・EX・待機の選択

### R-ACT-01 実効行動の優先順

1. 気絶中：待機。チャージ中ならチャージをキャンセルする。
2. 凍結中：待機。チャージを維持する。
3. 発動可能なチャージ効果あり：チャージ効果を発動する。
4. EX予約：EXスキルを使用する。
5. AS予約：`R-ACT-02` でASを選ぶ。

### R-ACT-02 AS選択

ASを定義順に評価し、最初に次の条件をすべて満たしたものを選ぶ。

- クールタイムが0
- 必要APを保有
- 発動条件を満たす
- 必要な対象候補が1体以上存在する
- 気絶、凍結などによって使用を禁止されていない

候補がなければ待機する。

### R-ACT-03 リソース消費

| 行動                     | 消費           | EXゲージ増加 |
| ------------------------ | -------------- | ------------ |
| AS                       | スキル定義のAP | 消費APと同量 |
| PS                       | スキル定義のPP | 消費PPと同量 |
| EX                       | EXゲージ全量   | なし         |
| 通常待機                 | AP 1           | 1            |
| AP 0・EX満タンで行動不能 | EXゲージ全量   | なし         |
| チャージ効果発動         | なし           | なし         |

AS・PS・EXのスキル定義コスト（AP／PP／EXゲージ）は1以上とする。コスト0のAS・PS・EXは存在しない（Catalog検証で拒否する）。

EXゲージ増加後はユニット固有の最大値で打ち止めとし、超過分を保持しない。

### R-ACT-04 リソース変更イベント

- AP、PP、EXゲージが変化した場合、変化後に `ResourceChanged` を発行する。
- 変化量が0の場合は `ResourceChanged` を発行しない。
- 消費と増加が同じ行動で発生する場合、消費を先に適用し、その後に増加を適用する。
- `MODIFY_RESOURCE` によるリソース変更も同じイベントを使用する。
- M7でリソース獲得量Modifier（`RESOURCE_GAIN_MOD`）が対象ユニットに有効な場合、基礎増加量（`ResourceChanged.baseDelta`）を算出した後、有効なModifierをすべて合成してから適用し、最後にcapacityで打ち止めてから `ResourceChanged`（`delta`に最終量を記録）を発行する。適用範囲は `R-ACT-03` のAP/PP消費に伴うEXゲージ増加だけとする（`APPLY_RESOURCE_GAIN_MOD` の `resource` は `EX_GAUGE` のみを取る）。前項の `MODIFY_RESOURCE` による一回限りの増減には適用しない。合成は、対象が保持する有効な `APPLY_RESOURCE_GAIN_MOD`（`rateDelta` は付与時点に一度だけ評価した符号付き割合）を全インスタンス合算し、倍率を `1 + 合計` とする（`R-DMG-04`・`R-HEAL-02` と同じ合成規約。stackingは `STACKABLE` のみのため `R-EFF-05` の最強選択は行わない）。合成後の要求増加量が負になる場合は0とする（Modifierは増加量を0まで減衰させられるが、既存リソースを減少させる経路にはしない）。丸めは倍率適用とcapacity打ち止めを済ませた最終適用点でただ一度だけ切り捨てる（`R-NUM-02`）。Modifierが存在しない場合はこの節の規則のみを適用するが、capacity打ち止めが発生する場合は`baseDelta`と`delta`が一致しない。
- capacity打ち止めによって`delta`が0になる場合（例：EXゲージが既に上限で正の`baseDelta`が全量破棄される場合）も「変化量が0の場合は`ResourceChanged`を発行しない」規則をそのまま適用するが、`ExtraGaugeOverflowDiscarded`は`delta`が0でも常に発行し、`baseDelta`を含む要求増加量・実増加量・破棄量を保持する。

## ターゲット候補

### R-TGT-01 候補生成

1. スキル定義の対象陣営、対象種別、発動条件で候補を絞る。
2. 戦闘不能者を対象にできる明示的な指定がない限り、戦闘不能者を除く。
3. 自分自身だけを対象とするスキルでは使用者だけを候補にする。
4. 候補が0体なら、そのASを発動不能とする。

### R-TGT-02 デフォルト順

次の比較キーを上から順に適用する。

1. 使用者からのマンハッタン距離：昇順
2. 対象側の行：前列、後列
3. 対象の列：絶対左、中央、右

### R-TGT-03 最も遠い

`R-TGT-02` の並び全体を逆順にする。

### R-TGT-04 隣接

- 基準対象と同じ陣営の盤面内で、上下左右1マスを候補とする。
- 陣営境界を越えない。
- 斜め位置を含めない。

### R-TGT-05 目の前

- 基準対象と同じ陣営の盤面内で、同じ列の1マス前を候補とする。
- 基準対象が前列の場合は候補なしとし、スキルを発動不能とする。
- 陣営境界を越えない。

### R-TGT-06 列優先

1. 指定列にいる候補を先に並べる。
2. 左右列指定では、指定列からの列距離が小さい順に別列を並べる。
3. 前後列指定では指定列、反対列の順に並べる。
4. 同じ列優先度の候補は `R-TGT-02` で並べる。
5. 必要数に達するまで上から選ぶ。

右列優先の列順は右、中央、左となる。左列優先は左、中央、右となる。

### R-TGT-07 対象数不足

- 選択可能な候補が必要数より少ない場合、存在する候補だけを対象にする。
- 候補が1体以上ならスキル自体は発動する。
- 候補が0体ならAS選択時に発動不能として次のASを評価する。

### R-TGT-08 ステルス

1. 通常の対象順を決定する。
2. 第一優先対象がステルスを持つ場合に限り、ステルスを消費する。
3. その対象を候補順の最後へ移動する。
4. 移動後に代替対象が存在しない場合は、ステルスを消費したうえで元の対象へ発動する。
5. 第一優先対象でないステルス所持者は順序を変更しない。
6. 自分自身を対象とする自分のスキルには適用しない。
7. 条件によって対象が1体に限定されている場合は適用しない。

ステルス適用後に代替対象がいない場合も、スキルは不発にしない。

### R-TGT-09 TargetSelector 評価順

`TargetSelectorDefinition` は次の順で評価する。

1. `kind` に基づき初期候補を作る。
   - `SELF`: 使用者または効果発動者。
   - `TRIGGER_SOURCE`: trigger event の source。
   - `TRIGGER_TARGET`: trigger event の target。
   - `SELECT`: `side` で指定された陣営のユニット。
   - `BINDING_DERIVED`: `base` の対象から `area` または派生条件で候補を作る。
2. `includeDefeated: true` でない限り、戦闘不能者を除外する。
3. `filters` を定義順に適用する。`AND` / `OR` / `NOT` は入れ子条件として評価する。
4. `area` が指定されている場合、候補を範囲で絞る。
5. `order` を上から順に比較キーとして適用し、候補順を一意にする。
6. `count` が `ALL` でない場合、候補順の先頭から指定数を選ぶ。
7. 候補が0件かつ `fallback` がある場合、`fallback` を評価する。

`order` が省略された場合は `DEFAULT` とし、`R-TGT-02` と同じ距離、前列、絶対左列の順を使う。

### R-TGT-10 TargetBinding

- `EffectSequence` の開始時に、定義順で `targetBindings` を評価する。
- 評価結果は同じ `EffectSequence` 内の `TargetReference.kind: BINDING` から参照する。
- binding の評価後に戦闘状態が変化しても、同じ sequence 内の当該 binding は再評価しない。
- ただし、参照時点で対象が戦闘不能になっている場合、その `EffectAction` が戦闘不能者を対象にできる明示指定を持たない限り、その対象への適用をスキップする。
- `TargetBindingId` が存在しない参照は Catalog 検証で拒否する。

## スキル解決

### R-SKL-01 効果順

- `SkillDefinition.resolution.effectSequence` の `targetBindings` を定義順に評価する。
- `EffectSequence.steps` を定義順に解決する。
- 各 `EffectStep` と `EffectAction` の前後に必要なドメインイベントを発行する。
- 各イベントに対するPS/Memory候補の扱いは `R-ATM-01` に従う（検出は即時、発動は効果処理完了後の後段フェーズまで保留）。
- 使用者が戦闘不能になった場合、未解決効果を中断する。
- 解決済みの効果を巻き戻さない。

### R-SKL-02 複数対象

- `ACTION` step の対象が複数いる場合、bindingの対象順に処理する。
- 対象ごとの効果適用後に発生したイベントのPS/Memory候補は `R-ATM-01` に従って検出・保留する。
- 使用者が途中で戦闘不能になった場合、残りの対象へ効果を適用しない。

### R-SKL-03 複数ヒット

- 各ヒットを独立したダメージイベントとして処理する。
- 暗闇によるスキル単位のMISS結果は全ヒットで共有する。
- MISSでなければ、対象固有の特別な回避、会心、ダメージ、シールド、戦闘不能をヒットごとに解決する（各イベントのPS/Memory候補は `R-ATM-01` に従い検出・保留する）。
- 使用者が途中で戦闘不能になった場合、残りのヒットを中断する。

### R-SKL-04 クールタイム設定

- スキル使用開始時にクールタイムを設定する。
- 設定した行動・ターンの終了時には減らさない。
- 次回以降の自身の行動終了またはターン終了で1ずつ減らす。
- 残数が0になった後の次の行動機会から使用できる。

### R-SKL-05 チャージ

- チャージ開始時に元スキルのコストを消費し、クールタイムを設定する。
- チャージ開始を一つの行動として完了する。
- 次の発動可能な行動機会に、AS／EX予約より優先してチャージ効果を発動する。
- チャージ効果発動ではAP・EXゲージを消費しない。
- チャージ効果発動を別の一つの行動とする。
- 気絶付与時にチャージをキャンセルする。
- 凍結中はチャージを維持し、解除後の次の行動機会に発動する。

### R-SKL-06 ACTION step

ACTION stepは、step全体を一度だけ評価する`stepCondition`（step-wide gate）と、`target`が解決した対象ごとに個別評価する`targetCondition`（per-target filter）という、独立した2つのconditionスコープを持つ（`stepCondition`/`targetCondition`スキーマ、CAP_EFFECT_STEP_CONDITION_SCOPE、RES-004-CONDITION-SCOPE、Issue #230）。

1. `stepCondition`を評価する。省略時は`TRUE`とする。
2. `stepCondition`がfalseの場合、その step 全体をスキップする（`EffectStepSkipped`。R-SKL-08の対象0件`SKIPPED`とは異なり、この場合は直前結果を一切記録しない）。
3. `target` で参照される対象集合を取得し、`targetCondition`（省略時は`TRUE`）を対象ごとに個別評価して、条件を満たさない対象だけをこの step の `actions` の適用対象から除外する。対象集合全体が条件を満たさなかった場合は、対象0件のACTION step（R-SKL-08）として扱う（`EffectStepSkipped`にはならない）。
4. 対象集合の順序に従って、残った各対象へ `actions` を定義順に適用する。
5. 1つの `EffectAction` 適用後に発生したイベントのPS/Memory候補は、`R-ATM-01` に従い検出して保留キューへ積み、次の action へ進む（発動は効果処理完了後の後段フェーズ）。

`stepCondition`には`TARGET_STATE`/`TARGET_HAS_MARKER`を含められない（対象ごとに真偽が変わりうるこの2 kindは`targetCondition`専用のスコープであり、参照先の`TargetReference`を問わず拒否する）。`targetCondition`には`TRUE`/`AND`/`OR`/`NOT`/`TARGET_STATE`/`TARGET_HAS_MARKER`/`EVENT_PAYLOAD`（CAP_TRIGGER_PAYLOAD_IN_RESOLUTION、Issue #247 M7-001D、後述）のみを許可し、含まれる`TARGET_STATE`/`TARGET_HAS_MARKER`はすべてこのstep自身の`target`と同じ`TargetReference`を参照しなければならない（Catalogロード時点で拒否する）。この2つのスコープはCatalogスキーマ上独立したフィールドのため、`stepCondition`のTARGET_SET_COUNTと`targetCondition`のTARGET_STATE/TARGET_HAS_MARKERは同じACTION stepで自由に併用できる — 実行時は`stepCondition`を1回評価してから、満たされた場合だけ`targetCondition`を対象ごとに評価する、常に単一の経路をたどる（量化の位置に依存した意味論の揺れは生じない）。

`stepCondition`に`TARGET_SET_COUNT`（`CAP_EFFECT_STEP_SET_CONDITION`、RES-004集合条件、Issue #227）を含む場合、`target`（`TargetReference`）が解決する対象集合を、対象ごとにではなく集合全体として評価する — Area/TargetFilterによる絞り込み後の集合（例：敵右列・左列の`OR`フィルタで絞り込んだ`TargetBinding`）に対し、生存している（戦闘不能でない）要素数を`op`/`value`で比較する。`op: GTE, value: 1` は「1体以上存在する」（EXISTS）、`op: LT, value: 1` は「1体も存在しない」（NONE）を表し、他の`op`/`value`の組み合わせで任意のしきい値比較（COUNT）も表現できる。`targetCondition`と同様、条件評価時点（先行stepの適用や前段フェーズのPS/Memory発動の後）の最新Battle stateを反映する必要があるため、`TARGET_SET_COUNT`を含む`stepCondition`は常にstep全体を一度だけ評価する（対象ごとの個別評価は行わない）。`targetCondition`に`TARGET_SET_COUNT`を含めることはできない（stepCondition専用のスコープ）。

（移行方針、Issue #230）ACTIONの単一`condition`フィールドは廃止した（既存のCatalog定義・テストは`stepCondition`/`targetCondition`へ機械的に移行済み。2フィールド間の互換シムは設けない — 本リポジトリがCatalogスキーマとデータの両方を単独で管理しているため、破壊的な一括移行を選んだ）。`BRANCH`には`target`が無く元々対象別スコープが存在しないため、単一の`condition`フィールドのまま変更していない（次項）。

`stepCondition`・`targetCondition`・`BRANCH`の`condition`は`EVENT_PAYLOAD`を含められる（CAP_TRIGGER_PAYLOAD_IN_RESOLUTION、Issue #247 M7-001D）。この`EVENT_PAYLOAD`は`triggers[].condition`が参照するもの（トリガー自体の発動可否を判定する、`trigger-condition-evaluator.ts`）とは独立に、PS発動を引き起こしたトリガーイベント自身のpayloadを、発動後の`resolution.steps`側から参照する — これにより、同一の発動契機イベントに対し、無条件で実行する一部stepと、そのイベントのpayloadしきい値で条件付けたい別のstepとを、単一のPS活動内で共存させられる（例: `UNIT_TARISA_TROUBLEMAKER`の`SKL_TARISA_TROUBLEMAKER_PS1` — 「自身が敵に攻撃するたびに発動。自身に『負けん気』を1つ付与し攻撃力を上昇させる（無条件）。そのスキルによって与えることのできたダメージが10以下だった場合、『負けん気』を3つ解除する（`DamageApplied`イベントの`calculatedDamage`フィールドで条件付け）」）。`EVENT_PAYLOAD`を含む`stepCondition`はCatalog preflight時点では確定できない（`LAST_RESULT`/`TARGET_SET_COUNT`と同じ理由 — トリガーイベントのpayload自体が実行時にしか存在しない）ため、常にDeferredStepPlanへ回して実行時にJIT評価する。`targetCondition`にも`EVENT_PAYLOAD`を含められ、値自体は対象によらず一定（トリガーイベントのpayload）だが`TARGET_STATE`/`TARGET_HAS_MARKER`とANDで組み合わせて「対象がXである、かつトリガーイベントのpayloadがYである」という対象ごとのfilterを表現できる。トリガーイベントを持たない解決スコープ（AS/EX active skill）は、`EVENT_PAYLOAD`を含む`EffectStep`を持つとCatalog構築時点で拒否する（`EVENT_PAYLOAD_REQUIRES_PS_SKILL`、`catalog-integrity.ts`）——スキーマだけではAS/EXでも`EVENT_PAYLOAD`を受理できてしまい、preflightを通過した後に実行時（`evaluateEffectStepCondition`）で初めて例外になる不整合を避けるため。

### R-SKL-07 BRANCH / RANDOM_BRANCH / REPEAT

- `BRANCH` は `condition` が true なら `thenSteps`、false なら `elseSteps` を定義順に解決する。`BRANCH`は`target`を持たないため、その`condition`は常にR-SKL-06の`stepCondition`と同じstep-wideスコープであり、per-target filterの概念はもとから存在しない（Issue #230でACTIONにだけ2スコープへの分離を導入した）。`condition`が`TARGET_SET_COUNT`を含む場合も、R-SKL-06と同じ規則（対象集合全体・最新Battle state）で評価する（`CAP_EFFECT_STEP_SET_CONDITION`、Issue #227）。対象別条件（`TARGET_STATE`/`TARGET_HAS_MARKER`、対象ごとに真偽が変わる評価）と`TARGET_SET_COUNT`（step全体で1回だけ評価する評価）は、単一のbooleanへ還元する意味論が本質的に異なるうえ、`BRANCH`の評価器は対象ごとの文脈（`EffectStepTargetContext`）を持たないため、同じ`condition`ツリーに`AND`/`OR`/`NOT`で混在させることはできない（Issue #227。`TARGET_STATE`/`TARGET_HAS_MARKER`が参照する`TargetReference`が何であるかは問わない）。混在した場合、Catalogロード時点で明示的に拒否する（`MIXED_STEP_TARGET_SET_CONDITION`。Issue #230以降、この検証は`BRANCH`の`condition`だけを対象とする — ACTIONは`stepCondition`/`targetCondition`という独立フィールドへ分離済みのため、この混在自体が構造的に起こり得ない）。
- `BRANCH`の`condition`に含まれる`TARGET_STATE`/`TARGET_HAS_MARKER`（Issue #230）: `BRANCH`は対象ごとの評価コンテキスト（`EffectStepTargetContext`）を持たないため、これらの参照する`TargetReference`が解決する対象は高々1体でなければならない — `SELF`/`TRIGGER_SOURCE`（常に1体）、または`selector.kind: SELECT`かつ`count: 1`の`BINDING`（`fallback`を持つ場合は、再帰的に辿った先すべてが同じ条件を満たす場合だけ）（0〜1体）だけを許可し、その1体（0体ならfalse）を直接評価する。複数体に解決されうる参照（`TRIGGER_TARGET`、`count`が`1`以外または`"ALL"`の`BINDING`、`BINDING_DERIVED`によるarea絞り込み、`LAST_ACTION_TARGETS`/`LAST_DAMAGED_TARGETS`）は、EXISTS/ALL等の量化規則を定めていないため、Catalogロード時点で明示的に拒否する（`BRANCH_TARGET_STATE_UNBOUNDED_REFERENCE`）。この量化が必要な設計（例:「隣接する敵のうち、呪いを4スタック以上持つ対象それぞれ」）は、`BRANCH`ではなくACTIONの`targetCondition`（自身の`target`を参照する対象別filter）で表現する。
- `RANDOM_BRANCH` の `WEIGHTED_ONE` は weight に応じて1分岐だけを選び、選択結果をドメインイベントへ記録する。
- `RANDOM_BRANCH` の `INDEPENDENT` は branch 定義順に確率判定を行い、成功したbranchのstepsを定義順に解決する。
- `RANDOM_BRANCH` の乱数消費順はCatalog定義順とする。
- `REPEAT` は指定回数だけ `steps` を繰り返す。繰り返し途中で使用者が戦闘不能になった場合、残りの繰り返しを中断する。

### R-SKL-08 直前結果

- `LAST_RESULT` Condition と `DAMAGE_DEALT_RATIO` / `DAMAGE_RECEIVED_RATIO` Formula は、同じ解決スコープ内の直前に確定した `EffectAction` 結果を参照する。
- `BRANCH` や `REPEAT` の内側で発生した結果も、次の step から直前結果として参照できる。
- MISS、付与拒否、対象不在などで効果が適用されなかった場合も、結果種別を持つ直前結果として記録する。
- 直前結果は `criticalHitCount`（直前のACTION step**全体**で実際に適用された会心ヒット数）も持つ。`targetUnitIds` が「そのEffectAction適用1件の対象」であるのに対しこれは step 全体のスコープを持ち、`lastActionTargetUnitIds`／`lastDamagedTargetUnitIds` と同じ粒度である（`POST_DAMAGE_CRITICAL_BRANCH`／`DMG-003`／Issue #196）。「この攻撃で会心攻撃が発生した場合」はAOEでも「その攻撃のどこかで会心が出たか」を意味するため、最後に処理した対象1体では表せないためである。MISS・対象戦闘不能でスキップされたヒットは会心判定自体を行わないため数えず、DAMAGE以外のEffectActionは常に0とする。
- 対象0件のACTION stepは、`SKIPPED`の直前結果を記録する。この時の`effectActionKind`/`effectActionDefinitionId`は、R-SKL-06 #4（対象ごとにactionsを定義順で適用する）と一貫させるため、そのstepの`actions`定義順で最後の`EffectActionReference`を採用する（対象が1件以上いた場合に最後に処理されるactionと同じもの）。

### R-SKL-09 クールタイム操作（`COOLDOWN_MANIPULATION`）

Issue #129。`EffectAction`から他スキルのクールタイムを短縮・リセットする。

- `EffectSequence`の定義順で操作を実行し、後続の`EffectAction`から変更後のクールタイム状態が観測できるようにする。
- `RESET`は対象スキルの残数を0にする。`REDUCE`は`amount`だけ減らし、0未満にはしない。
- 対象スキルがREADY（未登録、または残数が既に0）の場合、残数は変化しないためno-opとし、`CooldownReduced`/`CooldownCompleted`を発行しない。
- `R-SKL-04`の設定scope（設定した行動・ターンでは自然減算しない）は自身の行動・ターン終了時の減算にのみ適用され、`COOLDOWN_MANIPULATION`による明示操作は対象スキルが今回の行動・ターンで設定されていても適用する。
- 実際に残数が変化した場合は`CooldownReduced`と`StateDelta`を記録し、0になった場合は続けて`CooldownCompleted`も記録する。
- ACTION単位・TURN単位のどちらの対象スキルに対しても、対象スキル自身が持つ`unit`を維持したまま残数だけを変更する。
- 対象スキルは操作元の`EffectAction`を保有するUnitと同じUnitが所有するスキルに限る（Catalog検証で拒否する）。
- `R-ACT-02`「クールタイムが0」の判定は、この操作によって変更された残数を参照する。`R-PS-04`の発動直前再確認も同じ判定を再利用できる境界とする（PS候補エンジン自体はM6スコープ）。

## PS発動

### R-PS-01 発動タイミング照合

1. Battle Engineがドメインイベントを発行する。
2. PS Skill の `TriggerDefinition` のイベント種別と条件を照合する。
3. 発生源、対象、陣営、スキル種別などを `ConditionDefinition` で評価する。所有者から見た対象のFormation位置関係（例：目の前）と、現在のroot／parentイベントが示すBattle／Turn phase（開始・終了処理中かどうか）も、この`ConditionDefinition`評価に含める。陣営の判定（`sourceSelector`/`targetSelector`）は所有者自身を含む `ALLY` と、所有者自身を除く `OTHER_ALLY` を区別する — 「**他の**味方が〜した際に発動」は前者では表せず、自分の行動が自分のPSを呼んでしまう。
4. 条件を満たしたPSを同じイベントの候補グループにする。

PSの発動タイミングは固定一覧に限定せず、新しいドメインイベントへ対応づけられるものとする。

位置関係条件（`TRIGGER_POSITION_RELATION`）は、対象が戦闘不能または不在になった場合に不成立として扱う。除外タイミング条件（`TRIGGER_EXCLUSION_TIMING`）は、root/ancestorイベントがBattle開始・Turn開始・Turn終了の解決スコープに属する場合だけ不成立とし、同じeventTypeが通常の行動解決中に発生した場合は候補化する。固定のeventType分岐でこれらを実装せず、`ConditionDefinition`から評価する。

被弾量を最大HP比で照合する条件（`DAMAGE_MAX_HP_RATIO`。raw原文の例:「自身が敵からの攻撃1ヒットで、最大HP×15%以上のダメージを負った際に発動」）は、発火イベントのpayloadが持つ被弾量field（例: `HitPointReduced` の `hitPointDamage`）を `TRIGGER_TARGET`（被弾ユニット）の最大HPで割った比率を `op`/`value` と比較する。`EVENT_PAYLOAD` のリテラル比較では最大HP相対の閾値を表せないため、比率の算出を評価器が担う。判定素材はシールド吸収後に実際へHPを減らした量であり（`hitPointDamage` の定義）、fieldが数値でない場合と対象を解決できない場合は不成立とする。この条件は trigger条件（`TriggerDefinition.condition`。Skillの `triggers[]`・`counterUpdates[].trigger`・Memoryの trigger を含む）専用で、それ以外の配置 — skillType・Memoryを問わずすべての resolution step 位置、`activationCondition`、`expiration.conditions` — は Catalogロード時に拒否する（`DAMAGE_MAX_HP_RATIO_REQUIRES_TRIGGER` — `EVENT_PAYLOAD` と違い EffectStep 評価器がこの条件を処理しないため、ロードを通すと resolution step は発動中の解決が、AS/EX の `activationCondition` は行動選択が例外で停止する）。

### R-PS-02 候補順

候補グループ内を次の順で並べる。

1. 所有者の現在行動速度：降順
2. 味方陣営、敵陣営
3. 前列、後列
4. 絶対左、中央、右
5. 同じユニットではPS定義順

### R-PS-03 同時発動制限

- 同じイベントで候補になった、同時発動制限を持つPSだけを一つの制限グループにする。
- 先制攻撃候補を通常候補より優先し、その中で `R-PS-02` が最上位となるPS一つだけを候補に残す。
- 除外されたPSは発動済みとして記録しない。
- 別の発動タイミングで再度条件を満たした場合は、1解決スコープ1回制限に抵触しない限り候補になれる。

### R-PS-04 発動直前確認

候補を処理する直前に次を再確認する。

- 所有者が戦闘可能
- 所有者がチャージ中でない
- 必要PPを保有
- クールタイムが0
- 発動条件が現在も成立
- 現在の解決スコープで未発動

いずれかを満たさなくなった候補を破棄する。

### R-PS-05 発動と再入防止

1. `BattleUnitId + SkillDefinitionId` を発動済み集合へ追加する。
2. PPを消費し、消費量と同量だけEXゲージを増やす。
3. クールタイムを設定する。
4. `PassiveActivated` を発行する。
5. `EffectSequence` を `R-SKL-01` から `R-SKL-08` に従って解決する。
6. 完了したら `PassiveResolved` を発行する。

発動済み集合への追加をPP消費やイベント発行より先に行い、再入を防ぐ。

### R-PS-06 新規候補の処理順序

- 新しい候補グループの処理時機は `R-ATM-01`〜`R-ATM-02`（スキル効果処理の割り込み制御）に従う。
- スキル効果処理の**外**（前段・後段フェーズ、行動外トップレベルイベント）で新しい候補グループが生じた場合、既存の未処理候補より先に処理する（候補スタックの先頭へ積み、解決後に元のグループの続きへ戻る）。
- スキル効果処理の**中**で生じた候補グループは、その効果処理の保留キューへイベント発生順に積み、後段フェーズで解決する。保留キューの解決は、未処理の親候補（この発動を誘発したイベントの残り候補）より先に完了させる。
- 新しいグループ内でも `R-PS-02` を適用する。

### R-PS-07 1解決スコープ1回

- ユニットの1行動では、同じPSを1回だけ発動できる。
- ターン開始・終了など行動外では、そのトップレベルイベントの解決スコープで1回だけ発動できる。
- 解決スコープ終了時に発動済み集合を破棄する。

### R-PS-08 先制攻撃

- 同じイベントの候補グループでは、先制攻撃特性を持つPSを通常のPS候補より先に処理する。
- 先制攻撃候補が複数ある場合は `R-PS-02` の行動速度、陣営、配置、定義順を適用する。
- 先制攻撃は発動条件、発動直前確認、同時発動制限、1解決スコープ1回制限を無視しない。
- 先制攻撃PSから新しい候補が生じた場合も `R-PS-06`（`R-ATM-01`〜`R-ATM-02`）に従って処理する。
- 先制攻撃候補をすべて処理した後、同じ候補グループに残る通常候補へ戻る。

## Memory発動

### R-MEM-01 triggeredEffects 候補化

1. Battle Engineがドメインイベントを発行する。
2. 編成に指定された Memory の `triggeredEffects` をAPI指定順に走査する。
3. `TriggerDefinition.eventType` と `ConditionDefinition` を評価する。
4. 条件を満たした triggeredEffect を同じイベントのMemory候補グループにする。

Memory triggeredEffects はPP、クールタイム、先制攻撃、1解決スコープ1回制限を持たない。

### R-MEM-02 候補順

Memory候補グループ内を次の順で並べる。

1. APIリクエストで指定された Memory の順序。
2. 同一 Memory 内の `triggeredEffects` 定義順。

同じイベントでPS候補とMemory候補が両方存在する場合、PS候補を先に解決し、その後Memory候補を解決する（保留キュー内の候補グループでも同じ順序を保つ）。スキル効果処理の外でPS解決中に新しいMemory候補が発生した場合は、その新しい候補を現在のPS候補グループより後、未処理の親Memory候補より前に積む。効果処理中に発生したMemory候補は `R-ATM-01` の保留キューに入り、同じイベントから検出されたPS候補の後に解決する。

### R-MEM-03 戦闘開始時Memory

- 戦闘開始時Memoryは `BattleStarted` イベントで候補化する。
- `BattleStarted` に対するMemory効果は、初回ターン開始前、行動順キュー生成前に解決する。
- `APPLY_STAT_MOD` を含む Memory の `triggeredEffects` は、通常スキル由来の `APPLY_STAT_MOD` と同じく `AppliedEffect` として保持し、`CombatStatCalculator` で再計算する。
- このルールはM7のMemory発動エンジン実装（`BattleStarted` イベント処理）の責務であり、`FormationFactory` による初期 `BattleParty` 生成では `triggeredEffects` を解決しない。`FormationFactory` はMemory補正を一切計算せず、開始ステータスは編成ボーナスと配置適性のみで確定する。

### R-MEM-04 Memory EffectSequence

Memory の `EffectSequence` はスキルと同じく `R-SKL-01` から `R-SKL-08` に従って解決する。ただし使用者はMemoryを指定した陣営を source side とし、対象参照の `SELF` は使用できない。具体的な発生源 BattleUnit が必要なEffectActionをMemoryから使用する場合は、Catalog検証またはpreflightで拒否する。

## スキル効果処理の割り込み制御

1回の `EffectSequence` 解決（AS/EXの即時解決、チャージ解放、PSの発動、Memory triggeredEffectの発動）を「1回のスキル効果処理」と呼ぶ。本節は、スキル効果処理とPS/Memory発動の相対順序を定める。従来の「効果1件ごとの即時割り込み」（旧R-PS-06・旧R-ACTN-01 #6）は本節の規約へ置き換える。

### R-ATM-01 効果処理のアトミック性

- 1回のスキル効果処理の途中に、他のスキル効果処理（PS/Memoryの発動）を開始しない。
- 効果処理中に発行されたFACTイベントに対するPS/Memory候補は、**検出のみ即時**に行い（`R-PS-01`〜`R-PS-03`・`R-MEM-01`〜`R-MEM-02`。検出は各イベント発行時点の状態で照合する）、**発動はその効果処理の完了まで保留**する。保留した候補グループは、当該効果処理に紐づくキューとしてイベント発生順に保持する。
- 状態保守はこれまでどおりイベントごとに即時確定する: RuntimeCounter更新（`R-EFF-11`）、期間・消費・特殊失効（`R-EFF-04`〜`R-EFF-08`）、linked groupカスケード（`R-EFF-09`）、付与者戦闘不能によるMarker解除（`R-EFF-10`）、ステータス再計算（`R-STA-04`）。保留するのはPS/Memoryの**発動**だけである。
- 保留した候補を発動する直前には、`R-PS-04`（発動直前確認）とMemory候補の再確認（`08_ドメインイベント.md`「発動直前の再確認」）を必ず行う。保留中に前提が崩れた候補（所有者の戦闘不能、PP不足、発動条件の不成立など）はこの再確認で破棄する。
- スキル効果処理の外（行動外トップレベルイベント、前段・後段フェーズ）で発行されたイベントの候補は、従来どおり検出後直ちに解決する。

### R-ATM-02 解決フェーズ

1回のスキル使用は次の3フェーズで処理する。

1. **前段フェーズ**（効果処理の開始前）: `SkillUseStarting`（AS/EXのみ）とその候補解決 → 対象束縛の解決（`R-SKL-01` #1、`TargetsSelected`） → `SkillUseStarted` とその候補解決 → 攻撃前観測（`R-ATM-03`）とその候補解決。ここで発動する各PS/Memoryは、それぞれ1回のスキル効果処理としてアトミックに完結する。
2. **効果処理フェーズ**: `EffectSequence` を最後まで解決する。`R-ATM-01` に従い、発生した候補は保留キューへ積む。
3. **後段フェーズ**（効果処理の完了後）: 完了イベント（`SkillUseCompleted`／`SkillUseInterrupted`／`ChargeReleaseCompleted`／`ChargeReleaseInterrupted`／`PassiveResolved`／`PassiveInterrupted`／`MemoryResolved`）を発行した後、保留キューをイベント発生順に解決し、続いて完了イベント自身の候補を解決する。

- 効果処理が使用者戦闘不能で中断した場合（`R-SKL-01`）も、後段フェーズの保留解決は行う。発生済みイベントへの反応を中断が消すことはない。
- 保留候補から発動したPS/Memoryも同じ3フェーズで処理する（PSの前段フェーズは `PassiveActivated` とその候補解決、および攻撃前観測。Memoryは `MemoryTriggered` と攻撃前観測）。その効果処理中に生じた候補は**その発動自身の保留キュー**へ入り、当該発動の後段フェーズで解決してから、親のキューの次の候補へ進む。これにより旧R-PS-06の深さ優先（新しい候補を既存の未処理候補より先に処理する）を、効果1件単位からスキル効果処理単位へ粗くした形で維持する。
- PS深度・効果解決数の実行ガード（`11_インフラストラクチャ設計.md`「SimulationExecutionGuard」）は従来どおり1解決スコープ単位で数える。深度はネストした発動（保留キュー排出の入れ子）の深さと読み替える。

### R-ATM-03 攻撃前観測

「攻撃される直前に発動」（`UnitBeingAttacked`）のPS/Memoryを、攻撃スキルの効果処理開始前に発動させるための観測規則。`UnitBeingAttacked` のヒット単位発行（旧R-DMG-05 #1）を置き換える。

1. `DAMAGE` EffectActionを含む `EffectSequence` は、前段フェーズ（対象束縛の解決後、効果処理フェーズの開始前）に、DAMAGEの対象として解決された各ユニットへ `UnitBeingAttacked` を1回ずつ発行し、その候補を直ちに解決する。
2. 観測対象は、前段フェーズ時点で解決可能な対象参照から**構造的に**決める: DAMAGEを適用しうるstep（`BRANCH`／`RANDOM_BRANCH`／`REPEAT` の内側を含む）の対象参照のうち、`BINDING`（束縛が解決した対象）・`SELF`・`TRIGGER_SOURCE`／`TRIGGER_TARGET` が解決するユニットとする。条件・分岐によって実行時には実際に攻撃されない対象も、束縛が解決していれば観測対象に含める。
3. 観測の発行順は次で一意に決める: `EffectSequence.steps` の定義順に走査し（`BRANCH` は `thenSteps`→`elseSteps`、`RANDOM_BRANCH` はbranch定義順、`REPEAT` は `steps` 定義順の構造順。乱数・条件は消費・評価しない）、各stepでは対象参照が解決した対象順（束縛順、`R-SKL-02`／`R-TGT-10`）で列挙し、**初出順に重複を除去**する（`TargetsSelected` の `targetUnitIds` 収集と同じ規約）。同じ対象へは最初の出現でだけ発行する（複数のDAMAGE step・複数ヒットがあっても対象ごとに1回）。
4. 発行の直前に戦闘不能である対象へは発行しない（`R-ACTN-01` #2と同じ扱い。先行する観測のPSが対象を戦闘不能にした場合を含む）。
5. 各観測の候補解決後、使用者の生存を再検証する。使用者が戦闘不能になった場合は残りの観測を発行せず、効果処理フェーズへ進まずスキル使用を中断する（`SkillUseInterrupted`／PSは `PassiveInterrupted`。どのACTIONも未開始のため `unresolvedEffectCount: 0` の中断になり得る — Q-SKL-03）。観測**対象**が戦闘不能になった場合は残りの観測と効果処理を続行する（DAMAGEの適用可否は `R-ACTN-01` #2が処理する）。
6. `LAST_ACTION_TARGETS`／`LAST_DAMAGED_TARGETS` 参照の対象、および挑発・肩代わり（`DamageRedirected`）・リンクダメージ・反射によって効果処理中に初めてダメージを受けるユニットは、観測対象に含めない。「攻撃される直前」は、そのスキルが対象に取ったユニットに対してだけ成立する。
7. payloadの `damageTypes` は、その対象へ向き得る全DAMAGE定義の `damageType` の集合とし、前段フェーズまでに捕捉済みの追撃ライダー（`R-FUP-01`）が追加するダメージの型も含める。`EVENT_PAYLOAD field: "damageType"` を参照するtrigger条件は、集合のいずれかの要素で比較が成立すれば真とする（`14_Catalog定義スキーマ.md`「EVENT_PAYLOAD」の別名規約）。
8. 命中・会心・ダメージ量は観測時点で未確定のため、payloadへ含めない（ヒット結果に依存する条件はFACTイベント側で表現する）。

### R-ATM-04 効果処理中TIMINGイベントのトリガー禁止

- 効果処理フェーズの内部で発行されるTIMINGイベント（`EffectStepStarting`・`EffectActionStarting`・`DamageWillBeApplied`）は、PS/Memoryの発動契機（`TriggerDefinition.eventType`）に使用できない。Catalogロード時の整合性検証で拒否する。これらは監査・診断用の観測イベントとして発行自体は継続する。
- 効果処理の外で発行されるTIMINGイベント（`SkillUseStarting`・`UnitBeingAttacked`・`ActionCompleting`・`TurnCompleting`）は引き続き発動契機に使用できる。

## EffectAction解決

### R-ACTN-01 共通

1. EffectAction が参照する定義の実在と形の妥当性は、Catalogロード時の整合性検証が保証する。
2. EffectAction の対象が戦闘不能であり、かつ戦闘不能者を対象にできる明示指定がない場合は適用しない。
3. EffectAction の payload に含まれる `FormulaDefinition` を評価する。
4. EffectAction の種類に応じて HP、リソース、`AppliedEffect`、`MarkerState`、`ShieldState` を変更する。
5. 状態変更後、対応するドメインイベントを発行する。
6. イベントに対するPS/Memory候補を `R-ATM-01` に従って検出・保留してから、次のEffectActionへ進む（発動は効果処理完了後の後段フェーズ）。

### R-ACTN-02 即時効果

- `DAMAGE` は `R-HIT-*`、`R-CRT-*`、`R-DMG-*`、`R-SHD-*` に従って解決する。
- `HEAL` は `R-HEAL-*` に従ってHPを回復する。
- `MODIFY_RESOURCE` は対象リソースへ整数化済みFormula結果を適用し、0以上かつ現在最大値以下に丸める。
- `MODIFY_RESOURCE` の `DISTRIBUTE` は、Formula結果を対象ごとの適用量ではなく「対象間で分け合う総量」として扱う。総量を、同一 EffectStep 内で**この EffectAction 参照が**実際に適用される対象数で等分し、その取り分を `ADD` と同じ規約で現在値へ加算する。等分の端数は対象ごとに切り捨て（R-NUM-02）、余りは再配分せず破棄する。R-SKL-06 #4 に従い同じ EffectAction を1つの ACTION step から複数回参照した場合、各参照がそれぞれ独立に総量を分配する（参照間で総量を分け合わない）。`HEAL` の `distribution: EVEN` と同じ分配規約だが、分母の定義だけが異なる — `HEAL` は戦闘不能の対象を回復しないため常に除外し、`MODIFY_RESOURCE` は戦闘不能者を対象にできる明示指定がある対象へ実際に適用するためそれを分母に含める。
- `REMOVE_EFFECTS` は対象カテゴリ、解除数、優先順に従って `AppliedEffect` または `MarkerState` を解除する。

### R-ACTN-03 継続状態の付与

- `APPLY_STAT_MOD`、`APPLY_DAMAGE_MOD`、`APPLY_HEALING_MOD`、`APPLY_STATUS`、`APPLY_SHIELD`、`EFFECT_IMMUNITY`、`APPLY_DEATH_SURVIVAL`、`APPLY_TARGET_REDIRECT`、`APPLY_COVER`、`APPLY_REFLECT`、`APPLY_DAMAGE_LINK`、`MODIFY_RESOURCE_CAPACITY` は `AppliedEffect` として保持する。
- `APPLY_MARKER` は `MarkerState` として保持する。Marker に関連する継続効果がある場合は linkedEffectGroup で関連づける。
- 新規付与が無効効果によって拒否された場合、状態を変更せず、付与拒否イベントを記録できる。
- 付与後、影響するステータス、シールド、行動速度、対象選択条件を再評価する。
- `MODIFY_RESOURCE_CAPACITY` はリソースの**上限**を効果期間中だけ変更する（`MODIFY_RESOURCE` の現在値への一回限りの加減算とは別物、G-09／M7-002A・Issue #255）。付与時点に `formula` を一度だけ評価して効果インスタンスへ固定し、付与・失効・解除のたびに R-STA-04 と同じ再計算契機で、戦闘中不変の基準上限から現在の上限を合成し直す。合成規約は次のとおりで、`SET` 同士以外は付与順に依存しない。
  1. 有効な `SET` は基準そのものを置き換える。複数ある場合は付与順で後のものが勝つ（互いに排他な「その値にする」指定であり、合成できる量ではないため）。
  2. 有効な `ADD` を 1 の結果へ合算する。
- 上限が下がった結果として現在値が可動域 `[0, 新上限]` の外へ出た場合は、その場で切り下げる。上限が上がっても現在値は追随しない（R-ACT-04）。
- AP / PP / EXゲージ の上限は `BattleUnit` が持つゲージ最大値であり、`resource: HP` の上限は `MAXIMUM_HP` 戦闘中ステータスそのものであるため、後者は `APPLY_STAT_MOD` と同じ再計算・同じ状態差分へ合流する（R-STA-04）。

## 命中判定

### R-HIT-01 通常命中

- 通常の命中率・回避率を設けない。
- 暗闇または特別な回避効果がなければ必ず命中する。

### R-HIT-02 特別な回避効果

- 対象が有効な回避効果を持つ場合、その効果定義に従って回避を判定する。
- 攻撃が必中なら回避効果自体を発動させない。必中は攻撃側の効果定義による指定と、使用者が持つ必中効果（R-HIT-05）のどちらでも成立する。
- 対象がチャージ中なら自身の回避効果を発動させない。

### R-HIT-03 暗闇

1. スキル使用ごとに1回、使用者に付与された暗闇を付与順に取得する。
2. 各暗闇の指定確率でMISS判定を行う。
3. いずれか一つの暗闇でMISSになった場合、そのスキル全体をMISSとして扱う。
4. 複数対象・複数ヒットでも同じ判定結果を使用する。
5. 暗闇同士の確率を加算・乗算して一つの確率にまとめない。
6. 必中を持つスキルにも適用する。

MISSの場合、対象へのダメージと効果を適用しない。ただしMISSを契機とするPSは、対応するイベント定義があれば発動候補になれる。

### R-HIT-04 Nヒット回避

- 対象が有効なNヒット回避効果を持つ場合、被ヒットごとに、その効果定義に従って回避を判定する。
- 判定の順序、確率の扱い、対象攻撃種別の絞り込み、必中とチャージ中の不発は R-HIT-02 と同じとする。
- 回避が成立した被ヒットは、回避を成立させた効果インスタンス自身の被ヒット消費を1消費する。R-EFF-07 の `INCOMING_HIT` は命中が確定した被ヒットで消費するが、Nヒット回避は自身が回避した被ヒットで消費する。この消費は回避を成立させたインスタンスだけを対象とし、同じ対象が持つ他の被ヒット消費条件付き効果は消費しない。
- 逆に、回避が成立しなかった被ヒットでは、その回避効果の被ヒット消費を減らさない。確率判定に失敗した場合、必中（R-HIT-05）で発動しなかった場合、チャージ中で発動しなかった場合、対象攻撃種別が一致しなかった場合のいずれも同じとする。命中が確定した被ヒットによる R-EFF-07 の消費対象にも含めない。
- 消費回数が0になった時点で即時に失効させる（R-EFF-07）。
- 残り消費回数を持たない場合は、効果期間が続く限り被ヒットのたびに回避する。

### R-HIT-05 必中付与

- 使用者が有効な必中効果を持つ場合、その使用者の攻撃は、攻撃側の効果定義が必中を指定していなくても必中として扱う。
- 必中として扱う攻撃は、R-HIT-02 の回避効果も R-HIT-04 のNヒット回避も発動させない。
- 暗闇（R-HIT-03、R-STS-04）には影響しない。必中の攻撃にもMISS判定を行う。
- 必中効果は固有の消費契機を持たない。効果期間と消費は R-EFF-01・R-EFF-07 の一般規則に従う。

## 会心判定

### R-CRT-01 実効会心率

```text
実効会心率 = min(100%, max(0%, 戦闘中会心率))
```

戦闘中会心率はパーセントポイントの加減算で合成されるため（R-STA-01）、デバフの合計が基本値を超えると負になる。`max(0%, …)` はその到達可能な負値を実効0%へ切り上げる。

### R-CRT-02 会心倍率

会心が発生した場合、次の倍率を使用する。

```text
会心倍率 = 100% + 会心ダメージボーナス
```

会心が発生しない場合の倍率は100%とする。

会心ダメージボーナスは既定値50%（Q-CAT-05）を**含んだ**ユニットステータスであり、ギア（R-ENH-06）・戦闘中補正（R-STA-01・Q-STA-04）はいずれもこの値へパーセントポイントで加算される。したがって無強化ユニットの会心倍率は `100% + 50% = 150%` になる。[戦闘システム.md](./戦闘システム.md) の「150% + 会心ダメージボーナス%」はこの既定値込みの結果を指す表現であり、上式の基準へ150%を採ると既定値が二重に加算される（Q-DMG-09）。

### R-CRT-03 会心保証・会心不可

会心判定に用いる実効会心モードは、その `DAMAGE` 定義が宣言する会心モード（`DamagePayload.critical.mode`）と、**使用者**が保持する会心状態効果（`APPLY_STATUS` の `CRITICAL_GUARANTEE`／`CRITICAL_PREVENTION`）から次の順で決める。

1. 宣言が `PREVENTED`、または使用者が有効な `CRITICAL_PREVENTION` を保持する場合は `PREVENTED` とする。
2. そうでなく、宣言が `GUARANTEED`、または使用者が有効な `CRITICAL_GUARANTEE` を保持する場合は `GUARANTEED` とする。
3. それ以外は `NORMAL` とし、R-CRT-01 の実効会心率で判定する。

- どちらの状態効果も**保持者自身の攻撃**に働く。防御側が保持していても、その対象へ向かう攻撃の会心には影響しない（必中付与＝R-HIT-05 と同じ「保持者の攻撃側に働く」規約）。
- 会心不可を会心保証より優先するのは、会心不可が「会心の発生自体を禁じる」制限であり、会心保証は「発生を確定させる」緩和にすぎないためである。この順序により、会心の項を持たないサブユニット追加ダメージ（R-SUB-02 の `PREVENTED` 固定）が、使用者の会心保証によって会心し始めることもない。
- 実効会心モードは、会心判定時点（R-DMG-05 #2）の使用者の最新状態から解決する。`CriticalCheckResolved` はこの実効値を `mode` として通知する。
- 会心状態効果は固有の消費契機を持たない。効果期間と消費は R-EFF-01・R-EFF-07 の一般規則に従う（R-HIT-05 と同じ）。
- 解除カテゴリ（R-EFF-02）は、会心保証を `BUFF`、会心不可を `DEBUFF` とする。会心不可は保持者の攻撃を弱化する効果だからである。ただし R-STS-01 の `STATUS` は付けない — 会心不可は定義済みの状態異常ではなく、「状態異常解除」「状態異常無効」の対象にならない。

### R-ATR-02 属性倍率

- 有利属性でない場合は100%とする。

## ダメージ計算

### R-DMG-01 基本ダメージ

```text
実効防御力 = 防御側の戦闘中防御力 × (1 - defenseIgnoreRate)
基礎ダメージ = max(0, 攻撃側の戦闘中攻撃力 - 実効防御力)

計算ダメージ =
  基礎ダメージ
  × スキル威力
  × 属性倍率
  × 会心倍率
  × 与ダメージ倍率
  × 被ダメージ倍率
  × Action内追加ダメージ倍率
```

`FormulaDefinition.kind: SKILL_POWER` は、スキル威力として上式へ入る。`damageModifiers` はその `DAMAGE` EffectAction だけに適用する Action内追加ダメージ倍率として扱う。

### R-DMG-02 最終化

1. 全倍率適用後に小数部分を切り捨てる。
2. ダメージ無効効果がある場合も結果を1とする。
3. 計算結果が1未満の場合も1とする。
4. 最終ダメージを0未満にしない。

最低1ダメージは、ダメージを発生させる攻撃にだけ適用する。ダメージ効果を持たないスキルから1ダメージを発生させない。

### R-DMG-03 防御貫通

- 防御貫通は、そのDAMAGE定義自身が持つ静的な `piercing`（`DamagePayload.piercing`）と、攻撃側が保持している `APPLY_PIERCING_MOD` 由来の一時的な貫通（`AppliedEffect.piercing`、`TEMP_PIERCING_GRANT`／`DMG-003`／Issue #196）の合成とする。合成は率ごとに独立で、「無視されずに残る割合の積」から `1 - Π(1 - 各無視率)` とする（定義域 [0, 1] で閉じ、付与順に依存しない）。
- `defenseIgnoreRate` は基本ダメージ式で参照する防御力を割合で無視する。
- `shieldIgnoreRate` は最終ダメージのうち、シールドを経由せずHPへ直接適用する割合を表す。
- `damageReductionIgnoreRate` は被ダメージ軽減効果のうち、軽減方向の補正だけを割合で無視する。
- いずれも `0` なら通常処理、`1` なら全量無視とする。
- `shieldIgnoreRate` によるHP直接適用量は `floor(最終ダメージ × shieldIgnoreRate)` とし、残りをシールド適用対象とする。

### R-DMG-04 DamageModifier

- 与ダメージ補正は攻撃側に有効な `APPLY_DAMAGE_MOD direction: OUTGOING` を集計する。
- 被ダメージ補正は防御側に有効な `APPLY_DAMAGE_MOD direction: INCOMING` を集計する。
- `damageType` が指定されている補正は、対象のダメージタイプと一致する場合だけ適用する。
- 補正値は符号付き割合として加算し、倍率は `1 + 合計補正` とする。
- 倍率が0未満になる場合は0として扱う。
- `damageReductionIgnoreRate` は、被ダメージ補正のうち負の補正だけに適用する（`負の補正値 × (1 - damageReductionIgnoreRate)`）。正の被ダメージ補正と与ダメージ補正は変化させない。
- `APPLY_DAMAGE_MOD` の `stacking.mode` は `STACKABLE` のみのため、保持している全インスタンスが常に有効となる（`R-EFF-05` の最強選択は行わない。`R-HEAL-02` と同じ）。
- `payload.condition` を持つ補正は、ヒットごとにその条件を評価し、成立したヒットにだけ加算する（`DMG-002`／Issue #192、`14_Catalog定義スキーマ.md`「APPLY_DAMAGE_MOD」の`condition`）。条件は補正の保持者（`EFFECT_OWNER`）とそのヒットの相手（`OPPONENT`）だけを参照する。補正値そのもの（`formula`の評価結果）は付与時点のsnapshotだが、条件は評価時点の状態で判定する。
- `payload.damageThreshold` を持つ補正はこの合成に参加せず、`R-DMG-07` が入射ダメージ確定後に独立倍率として適用する。
- 集計はヒットのダメージ計算時点（`R-DMG-05` #5）の最新状態から行う。前段フェーズの攻撃前観測（`R-ATM-03`）で発動したPSが付与した軽減・ガード効果はここに含まれる。`DamageWillBeApplied` payloadの倍率は監査用のsnapshotであり、計算に使う確定値は `DamageCalculated` payloadが持つ。

### R-DMG-05 ダメージイベント順

`UnitBeingAttacked` はヒット単位では発行しない — 効果処理開始前の攻撃前観測（`R-ATM-03`）が対象ごとに1回発行する。`DAMAGE` EffectAction は対象ごと、ヒットごとに次の順で処理する。

1. 命中判定を行う。`R-EFF-07` の `NEXT_OUTGOING_ATTACK`／`NEXT_INCOMING_ATTACK` 消費は従来どおり各ヒットの命中判定前に行う（観測イベントの前段フェーズへの移動は消費タイミングを変えない）。
2. MISSでなければ会心判定を行う。
3. `DamageWillBeApplied` を発行する（監査用snapshot。PS/Memoryの発動契機には使用できない、`R-ATM-04`）。
4. 防御介入系状態を `R-INT-01` の順で評価する。
5. ダメージを計算し、`DamageCalculated` を発行する。
6. シールド、サブユニット、HPへ適用し、`DamageApplied` を発行する。
7. HPが0になった場合は `UnitDefeated` を発行する。
8. リンクダメージ、反射などの追加ダメージがある場合は、各ルールに従って追加イベントを発行する。

各FACTイベントのPS/Memory候補は `R-ATM-01` に従い検出・保留する。

### R-DMG-06 攻撃時追加ダメージ

`APPLY_ATTACK_DAMAGE_BONUS` は、保持者が行う `DAMAGE` EffectAction の各ヒットへ固定量を加算する継続効果（`R-ACTN-03`）とする。

1. `formula` は付与時点に一度だけ評価し、結果を加算量として `AppliedEffect` へ固定する（`APPLY_STAT_MOD` と同じ付与時snapshot規約。毎ヒットの再評価は行わない）。
2. 攻撃側が保持する有効な全インスタンスの加算量を合算し、`R-DMG-01` の計算ダメージ（凍結解除増幅 `R-STS-03` を適用した後の丸め前の値）へ加算する。加算後に肩代わり軽減（`R-INT-02` 第2項）を適用し、最終切り捨て・最低1ダメージ（`R-DMG-02`、Q-DMG-01「計算の途中では丸めない」）は全体でただ一度だけ行う。
3. 対象にダメージ無効効果がある場合は、加算後も結果を1とする（`R-DMG-02` #2）。
4. MISS・回避が成立したヒットには加算しない。
5. 加算は `DAMAGE` EffectAction のヒット計算（`R-DMG-05` #5）でのみ行う。確定済みダメージを転写するリンクダメージ（`R-LNK-02`）・反射（`R-INT-03`）、継続ダメージ（`R-DOT-01`）、サブユニットの追加ヒット（`R-SUB-02` の除外条項）では加算しない。

### R-DMG-07 閾値付き被ダメージ軽減

`APPLY_DAMAGE_MOD` の `payload.damageThreshold {op, formula}`（`direction: INCOMING` でだけ宣言できる。raw原文の例:「自身の現在HPの20%を**超える**ダメージのみ3ヒットまで50%減少させる」）は、入射ダメージの大きさで適用可否が決まる被ダメージ補正を表す。

1. `damageThreshold` を持つ補正は `R-DMG-04` の通常合成に参加しない。通常合成は入射ダメージ確定前に行われるため、閾値の判定素材が存在しないからである。
2. 判定素材は `R-DMG-02` #1 の切り捨てまで確定した入射ダメージとする（`R-DMG-02` の `damageThreshold` 付きダメージ無効と同じ）。`formula` はヒットごとに評価し直し、評価対象は補正の保持者自身（`CURRENT_HP_RATIO` の `source: TARGET` が保持者=被弾側を指す）とする。
3. 保持する有効なインスタンスのうち、`damageType` の絞り込み・動的条件（`payload.condition`）を満たし、判定素材が `op`/`formula` の比較で真になるものの補正値を加算し、独立倍率 `max(0, 1 + 合計補正)` を判定素材へ乗算する。再切り捨て・最低1ダメージは通常規則どおり適用する。成立が0件のヒットではダメージを変化させない。
4. `damageReductionIgnoreRate`（`R-DMG-03`）は、通常合成と同じく負の補正値だけへ `(1 - rate)` を掛ける。
5. ダメージ無効（`R-DMG-02` #2）は本規則の軽減**後**の値を判定素材とし、成立すれば最終結果を1へ上書きする（無効化は常に最後の砦）。
6. 消費条件 `consumption {kind: INCOMING_HIT}` を併せ持つ場合、消費は「実際に軽減を適用したヒット」でだけ、適用したインスタンスに限って行う（`R-HIT-04` のNヒット回避と同じ消費契機の反転）。閾値を満たさないヒットや、`R-EFF-07` の命中確定一括消費では残数を失わない。消費はそのヒットの `DamageApplied`（幻惑時は `DamageConvertedToHeal`）の**後**に行う（`R-EFF-07` の一括消費と同じ順序）。消費・失効イベントのPS/Memory候補は `R-ATM-01` に従い検出・保留する。
7. 適用範囲は `R-DMG-04` と同じで、`DAMAGE` EffectAction のヒットとサブユニットの追加ヒット（`R-SUB-02`）に乗る。確定済みダメージを転写するリンクダメージ・反射、継続ダメージには乗らない。

## 回復計算

### R-HEAL-01 即時回復

1. `FormulaDefinition` を評価する。
2. `HEAL` の `payload.distribution` が `EVEN` の場合、評価結果を「総回復量」とみなし、同じ EffectStep 内でこの EffectAction が適用される対象数で等分する。既定の `NONE` では対象ごとに評価結果の全量を回復する。分母は適用直前の生存状況から求め、戦闘不能の対象は（`includeDefeated` の有無にかかわらず、本ルールが回復しないため）除外する。
3. `R-HEAL-02` の HealingModifier 倍率を適用する。
4. 回復量を適用直前に小数部分切り捨てで整数化する（`R-NUM-02`、切り捨ては1回だけ）。
5. 回復量が0未満の場合は0とする。
6. 対象のHPを最大HPを超えない範囲で増加させる。
7. `HealApplied` を発行する。

`overheal` は初期実装では `DISCARD` のみとし、最大HPを超えた分は破棄する。

`FormulaDefinition.kind: SKILL_POWER` は `14_Catalog定義スキーマ.md` の定義どおり「攻撃力を基礎にしたスキル威力倍率」であり、回復量は `回復者の攻撃力 × power` とする（`R-DMG-01` と同じ規約。ただし回復には防御側が存在しないため、ダメージ側の「攻撃力 - 防御力」に相当する減算は行わない）。それ以外のFormula種別（`MAX_HP_RATIO`、`DAMAGE_DEALT_RATIO` など）は `DAMAGE` と同じく評価結果そのものが回復量になる。

戦闘不能の対象は回復しない（本ルールは蘇生規則を持たない。蘇生は `APPLY_DEATH_SURVIVAL` の責務）。この場合 `HealApplied` を発行しない。

### R-HEAL-02 HealingModifier

- 与回復量補正は回復者に有効な `APPLY_HEALING_MOD direction: OUTGOING` を集計する。
- 被回復量補正は対象に有効な `APPLY_HEALING_MOD direction: INCOMING` を集計する。
- 補正値は符号付き割合として加算し、倍率は `1 + 合計補正` とする。
- 倍率が0未満になる場合は0として扱う。
- 回復量Formulaの結果に HealingModifier 倍率を適用し、その後で整数化する。

集計方法は `R-DMG-04` の与/被ダメージ補正と同じである。`APPLY_HEALING_MOD` の `stacking.mode` は `STACKABLE` のみのため、保持している全インスタンスが常に有効となる（`R-EFF-05` の最強選択は行わない）。

### R-HEAL-03 継続回復

- `APPLY_CONTINUOUS_HEAL` は `AppliedEffect` として保持する。
- 指定された eventType と対象条件を満たしたとき、`R-HEAL-01` と同じ手順で回復する。
- 継続回復のDuration消費は `R-EFF-*` に従う。

回復量Formulaは付与時点のスナップショットではなく発火のたびに評価し直す（`MAX_HP_RATIO`／`MISSING_HP_RATIO` は発火時点の対象HPを、`SKILL_POWER` は回復元の現在の攻撃力を基礎にするため）。回復元は当該 `AppliedEffect` の付与者とする。

`timing` は `{eventType: ActionStarted, targetSelector: EFFECT_OWNER}`（保持者自身の行動開始時に保持者を回復する）だけを実装する。これは `06_戦闘状態遷移.md` の `START_EVENT` #2「行動開始を契機とする効果」に相当し、#3のPS連鎖を経て #4「行動者が戦闘不能になった場合は、本体スキルを実行せず `COMPLETING` へ進む」の判定対象になる（AS/EX・待機・チャージ開始・チャージ発動の4経路すべて）。production Catalogの継続回復定義はすべてこの組み合わせを使う。他の組み合わせは「付与は成功するが一度も発火しない」silent partial implementationになるため、Catalogロード時点で拒否する（`11_インフラストラクチャ設計.md` のCatalog整合性検証）。

### R-HEAL-04 回復リンク

`APPLY_HEALING_LINK` は「保持者が得られる回復効果を、指定した割合だけ転送先へ移し替える」継続効果であり、`AppliedEffect` として保持する（`R-ACTN-03`）。転送先（`payload.transferTo`）と転送率（`payload.transferRate`）は付与時点に解決して当該インスタンスへ固定する。

`R-HEAL-01` #6（対象のHPを増やす）を次の手順へ置き換える。

1. `R-HEAL-01` #5 までで確定した回復量を「転送前回復量」とする。
2. 保持者に有効な回復リンクを付与順（`R-TGT-10` と同じ定義順・付与順の規約）に評価する。各リンクの転送量は `切り捨て(転送前回復量 × 転送率)` とし（`R-NUM-02`）、その時点の未転送残量を上限とする。転送量の合計が転送前回復量を超えることはない。
3. 転送後に残った量だけを、保持者の最大HPを超えない範囲で保持者のHPへ増加させ、`HealApplied` を発行する。
4. `HealApplied` のPS/Memory候補は、発行時点（転送を適用する**前**）の状態で検出する（`R-ATM-01`。発動は効果処理完了後の後段フェーズ）。これにより `HealApplied` に反応する候補の照合は転送前のHPを観測し、続く転送は検出後の最新状態に対して適用される。
5. 各転送先へ、対応する転送量をそのまま適用する。転送先では回復量Formulaと HealingModifier（`R-HEAL-02`）を再計算しない（`R-LNK-02`「リンク先では属性、会心、ダメージ増減効果を再計算しない」と同じ規約）。最大HP上限と `overheal: DISCARD` は転送先自身へ適用する。
6. 転送先ごとに `HealingTransferred` を発行し、**次の転送へ進む前に**その候補を検出する（`R-ATM-01`）。転送量が0のリンクでは発行しない。

次の境界条件を持つ。

- **再リンク禁止**: 転送によって生じた回復からさらに転送を発生させない（`R-LNK-03` と同じ）。これにより相互リンク・循環リンクは常に有限回で停止し、preflightでの拒否を必要としない。
- **自己リンク**: 転送先が保持者自身の場合は転送を発生させず、その分を保持者へ留める（恒等）。`HealingTransferred` も発行しない。
- **複数リンク**: 保持者が複数の回復リンクを持つ場合、#2 の順序と上限によって決定的に処理する。転送率の合計が1を超えても保持者の回復量が負になることはない。
- **転送先が戦闘不能（#2 の割り当て時点）**: そのリンクは成立せず、対応する分を保持者へ留める（`R-HEAL-01` は蘇生規則を持たない。蘇生は `APPLY_DEATH_SURVIVAL` の責務）。
- **転送途中のPS/Memory発動は存在しない**: `R-ATM-01` により、#4（`HealApplied`）・#6（`HealingTransferred`）の候補は検出のみ行われ、発動は効果処理完了後の後段フェーズまで保留される。#2 の割り当てから #5 の適用までの間にPS/Memoryの発動が挟まって転送先・使用者を戦闘不能にする経路は存在しないため、転送先の戦闘不能判定は #2 の割り当て時点（上項）の1回で足り、使用者の戦闘不能による未解決効果の中断は `R-SKL-01` の一般規定（各 `EffectAction` 開始時の再検証）だけが担う。
- **リンクの失効**: #3〜#5 の間の即時の状態保守（特殊失効条件 `R-EFF-08` 等 — `R-ATM-01` が保留するのは発動だけで、状態保守はイベントごとに即時確定する）でリンク自体が失効しても、#2 で確定した転送は取り消さない（転送量はすでに保持者の回復量から差し引かれている）。
- **保持者が戦闘不能**: `R-HEAL-01` により回復自体を行わないため、転送も発生しない（`HealApplied` も `HealingTransferred` も発行しない）。
- **回復量0**: 転送量も0になり `HealingTransferred` を発行しない。`HealApplied` 自体は `R-HEAL-01` に従い発行する。
- **保持者の最大HP上限**: 上限判定は転送後の残量に対して行う。転送された分は保持者のoverhealとして破棄されない。

継続回復（`R-HEAL-03`）は `R-HEAL-01` と同じ手順を共有するため、同じ転送規則に従う。

## シールドとHPへの適用

### R-SHD-01 シールドプール

- 物理シールド、ENシールド、タイプなしシールドを別々に保持する。
- 同じタイプのシールド付与値を加算する。
- 個別消滅条件を持つ付与元は `AppliedEffect` として保持し、有効な合計値を算出する。

`DMG-004`（Issue #194）で次を確定した。

- シールド量は `R-NUM-02` に従い付与直前に切り捨てて整数化し、負のFormula結果は0とする。プール合計はインスタンスの残量の総和であり、独立した実体を持たない。
- プール内でどのインスタンスから先に減らすかは本ルールが規定しない。`R-EFF-02` #3 と同じ既定（付与順の古い順）を採る。
- 残量が0になったインスタンスは「個別消滅条件」の成立として失効させ、`EffectExpired`（`reason: SHIELD_DEPLETED`）を発行する。この失効は `R-EFF-09` の `linkedEffectGroupId` カスケードを他の失効契機と同じ経路でたどる。
- 吸収・漸減は、プール1つを単位に「減少 → `ShieldConsumed` → 候補検出（`R-ATM-01`） → 枯渇分の失効」を完了させてから次のプール・次の適用先へ進む（`08_ドメインイベント.md`「ShieldConsumed payload」）。
- 付与量が0（Formula結果が負値、または切り捨てで0）の付与も、その時点で残量0であるため同じ理由で失効させる。ただし失効の実行はその `EffectAction` の中ではなく、**その `EffectSequence` 解決の最後**とする。同じ ACTION step の後続 `EffectAction` が同じグループの子効果を付与しうるため（`R-SKL-06` #4）、付与直後に親を失効させると `R-EFF-09` のカスケードが子を収集できず、後から付与された子だけがグループの親を失って残ってしまう。
- `APPLY_SHIELD.decay` を宣言したシールドは、`R-EFF-04` の行動単位期間と同じ完了契機で残量を `切り捨て(付与時最大値 × ratio)` だけ減らす（`ratio > 0` なら最低1）。減少は `ShieldConsumed`（`reason: DECAY`）として記録する。`R-EFF-04` #2「付与された当該行動では減らさない」はこの漸減には及ばない — 残り回数ではなく効果量そのものの変化であるため。

### R-SHD-02 適用順

ダメージを次の順に適用する。

1. `shieldIgnoreRate` 分をHPへ直接適用する。
2. 残りをダメージタイプに対応するタイプありシールドへ適用する。
3. さらに残った分をタイプなしシールドへ適用する。
4. さらに残った分をサブユニットへ適用する。
5. さらに残った分をHPへ適用する。

対応しないタイプありシールドへダメージを適用しない。

### R-SHD-03 超過ダメージ

- シールド値を超えた残りを次の適用先へ渡す。
- HPを0未満にせず、超過分を破棄する。
- HPが0になった時点で戦闘不能処理を行う。

`R-SHD-02` #1 の按分は `R-NUM-02` に従い切り捨て、端数はシールド側（後段）へ残す。これにより「タイプありシールド吸収量＋タイプなしシールド吸収量＋HPダメージ量＋超過破棄量＝計算ダメージ」が常に厳密に成立する（`08_ドメインイベント.md` の不変条件 #6）。

## サブユニット

### R-SUB-01 シールド効果

- 通常シールドをすべて適用した後にサブユニットがダメージを受ける。
- 毒、炎上など、通常シールドで受けられないダメージはサブユニットでも受けない。
- サブユニットの残HPをシールド表示値へ合算できるが、内部状態は通常シールドと分ける。
- シールド解除・シールド無視の対象とする。

### R-SUB-02 追加効果

- 所持者の攻撃対象ごとに追加ダメージを1ヒット加える。
- 複数対象への攻撃では、各対象へ1ヒットずつ加える。
- 追加デバフが定義されている場合も対象ごとに適用する。
- 追加ダメージでは通常の防御力減衰を行わない。

サブユニット追加ダメージは次の式で算出する。

```text
追加ダメージ = サブユニット所持者の攻撃力 + 付与者の攻撃力 × スキル倍率 - 対象の防御力
```

最終ダメージの小数切り捨てと最低1ダメージは通常のダメージ規則に従う。

追加ダメージは `戦闘システム.md`「サブユニットについて」が明示するとおり**1ヒットとして扱う**。したがって R-SKL-03 の「MISSでなければ、対象固有の特別な回避、会心、ダメージ、シールド、戦闘不能をヒットごとに解決する」が追加ヒットにもそのまま適用され、`HitConfirmed`・`CriticalCheckResolved`・`DamageWillBeApplied` を通常ヒットと同じ順で発行し（`UnitBeingAttacked` は R-ATM-03 の攻撃前観測が対象ごとに1回発行済み）、R-HIT-04 のNヒット回避と R-EFF-07 の `OUTGOING_HIT`／`INCOMING_HIT` 消費の対象にもなる（`DMG-005`／Issue #190）。

通常ヒットと異なるのは**ダメージ計算の基本式だけ**である。上記の防御力減衰の除外に加え、会心は `PREVENTED` 固定（計算式に会心の項が無く、Catalog にも会心モードの宣言が無い）、貫通は持たない（同じく対応する項が無い）。属性相性の倍率も 1 になる — 上の計算式が属性の項を持たないためである。命中特性（`accuracy`）は追加ダメージの契機になった攻撃から引き継ぐ。

一方、基本式の**外側**にある補正はそのまま適用する。R-DMG-04 の与／被ダメージ補正（`APPLY_DAMAGE_MOD`）と R-DMG-02 のダメージ無効がこれに当たる。どちらの規則もダメージの出どころを限定しておらず、R-DOT-01 が継続ダメージについて「ダメージ軽減・増加、属性相性の影響を受けない」と明示的に除外しているのと対照的に、R-SUB-02 が除外するのは防御力減衰だけだからである。これにより `DamageWillBeApplied` が通知する補正倍率のsnapshotと `DamageCalculated` の確定値が一致する。

凍結の解除・増幅（R-STS-03）と `APPLY_ATTACK_DAMAGE_BONUS` の加算は追加ヒットでは行わない。前者は「新たな攻撃スキルによるダメージ」、後者は保持者自身の `DAMAGE` EffectAction を契機とする規則であり、同じ攻撃の中で二重に数えないためである。

「所持者の攻撃対象ごと」が数えるのは攻撃が誰を狙ったかであり、その攻撃自身のヒットが通ったかではない。元のヒットが回避されていても追加ヒットは発生し、追加ヒット自身の命中判定で改めて回避されうる。

追加デバフ（第3項）は追加ダメージの適用が完了した**後**に付与し、その直前に使用者・対象の生存を再検証する。追加ダメージ自身が対象を倒した場合（R-ACTN-01 #2）や、反射（R-INT-03）等の派生ダメージで使用者が戦闘不能になった場合（R-SKL-01）には付与しない（`DamageApplied`／`UnitDefeated` のPS/Memory候補は `R-ATM-01` により保留されるため、連鎖が効果処理の途中で使用者を倒す経路は存在しない）。

追加ヒットの解決中に使用者が戦闘不能になった場合、その EffectAction は `EffectActionCompleted.resultKind: INTERRUPTED` として報告し、同じ `EffectStep` の残りと後続 step も解決しない（R-SKL-01）。追加ヒットは元の DAMAGE EffectAction のヒット列に含まれないため、中断はヒット数ではなく独立した中断フラグとして報告する（HEAL の転送中断と同じ扱い）。

混乱（`R-CFS-02` のダメージ倍率）と幻惑（`R-DTH-01` の回復変換）は追加ダメージには働かない。`DMG-009`（Issue #193）はこれを実装上の帰結として記録し、規則側から統合すべきかを M8 完了監査へ委ねていた。監査の結論は**現状維持**であり、ここで明示的な境界として確定する。どちらのルールも「保持者が使う `DAMAGE` EffectAction」を対象に規定されているのに対し、本ルールは追加ダメージを「サブユニット自身が与えるもの」として — 上の計算式が保持者の攻撃力と付与者の攻撃力を別項として持つとおり — 保持者のスキルによる攻撃とは別の出どころとして扱う。会心が `PREVENTED` 固定で貫通も属性相性も持たないのと同じ理由で、保持者が受けている「自分の攻撃の作り替え」も追加ダメージには及ばない。

## 追撃（攻撃ライダー）

### R-FUP-01 追撃効果

`APPLY_FOLLOW_UP_ATTACK`（Issue #474、raw原文「当該攻撃に威力Xのダメージ…を追加する」、production定義: `SKL_SUIRAN_CHAOS_PS3`／`SKL_CHIYURU_MAZE_PS2`／`SKL_FEE_ACTOR_PS1`）は、保持者の次のAS/EXスキル使用の攻撃に**相乗りする追撃**を表す継続効果（R-ACTN-03）とする。

1. 効果は保持者へのバフとして付与する（重複可。複数保持していればその数だけ追撃が増える）。`duration.consumption` は `NEXT_OUTGOING_ATTACK` を必須とする — 「相乗りする攻撃」と「このバフを消費する攻撃」を構造的に同一へ保つためであり、Catalog factoryが他の期間表現を拒否する。
2. 相乗りの対象は**AS/EXスキル使用の攻撃だけ**とする。捕捉はヒットが命中判定へ到達した時点（R-EFF-07の `NEXT_OUTGOING_ATTACK` 消費と同じ到達点）で行い、その時点で保持していたバフとその攻撃の対象を記録する。PS/MemoryのEffectSequenceやチャージ解放の攻撃はバフを消費するが追撃は発生させない。
3. 追撃はスキル使用の**全stepの解決が終わった後・`SkillUseCompleted` 発行前に1回だけ**解決する。元攻撃が複数の `DAMAGE` EffectActionを持つ場合もスキル使用につき1回であり、命中・会心の集計（下記）はスキル使用内の全 `DAMAGE` EffectActionを合算する（サブユニット追加ヒット＝R-SUB-02は集計に含めない）。使用者の戦闘不能で中断（`SkillUseInterrupted`）したスキル使用では追撃を行わない（R-SKL-01）。
4. 命中判定を独自に行わない。元攻撃が1発でも命中（`applied`）していれば追撃は**必中**として扱い（回避効果・Nヒット回避を発動させず、乱数を消費しない）、1発も命中しなかった場合は追撃自体を行わない（バフの消費は#2の到達点で既に済んでいる）。
5. 会心判定を独自に行わない。元攻撃のいずれかのヒットが会心なら追撃も会心、1発も会心でなければ非会心とする（どちらも乱数を消費しない）。会心倍率はR-CRT-02のとおり**保持者**の会心ダメージボーナスから求める。使用者が保持する会心不可（R-CRT-03 #1）はこの継承より優先される。
6. 追撃は「保持者の攻撃対象ごとに1ヒット」（R-SUB-02第1項と同じ規約。複数 `DAMAGE` EffectActionにまたがる場合は対象の重複なし和集合）を、捕捉順のバフごとに加える。既に戦闘不能な対象は飛ばし（R-ACTN-01 #2）、追撃の解決中に使用者が戦闘不能になった場合は残りを中断する（R-SKL-01）。この中断は外側のスキル使用結果へ伝播し、`SkillUseCompleted` ではなく `SkillUseInterrupted` を発行する — 完了契機のPS/Memoryや `SKILL_USE` 単位の期間減算を、中断したスキル使用で誤って走らせないためである。追撃はEffectActionのヒット列に属さないため、この場合の `unresolvedEffectCount` は0のままになる（R-SUB-02のサブユニット追加ヒット中断と同じ扱い）。
7. ダメージ計算は通常の基本ダメージ式（R-DMG-01。攻撃側=**保持者**の攻撃力・属性・相性ボーナス、対象の防御力減衰、`payload.damage.formula` のスキル威力）を用いる。バフの**付与者のステータスは一切参照しない**。貫通は持たない。凍結の解除・増幅（R-STS-03）・攻撃時追加ダメージ（R-DMG-06）・混乱（R-CFS-02）・サブユニット追加ダメージ（R-SUB-02）は追撃には適用・誘発しない — いずれも「同じ攻撃の中で二重に数えない」R-SUB-02と同じ境界である。与/被ダメージ補正（R-DMG-04）・閾値付き軽減（R-DMG-07）・ダメージ無効（R-DMG-02）・防御介入（R-INT-01）・リンク・反射は通常ヒットと同じに適用する。
8. 追撃は通常ヒット観測列（R-DMG-05）を通る1ヒットとして扱い、被ヒット消費条件（R-EFF-07）の対象になる。攻撃前観測（R-ATM-03）の `damageTypes` には捕捉済みライダーが追加するダメージの型を含める。追撃のイベントのPS/Memory候補は R-ATM-01 に従い検出・保留する。保留候補から発動したPSが新しい追撃バフを付与しても、同じ攻撃で連鎖的に追撃は増えない（バフ列は解決前に確定済み — R-SUB-02のサブユニット列と同じ規約）。
9. `payload.onHitEffect`（任意。`APPLY_STAT_MOD` または `APPLY_CONTINUOUS_DAMAGE` への参照）は、追撃ヒットの適用が完了した**後**に、そのヒットが適用された対象へ付与する。付与の直前に使用者・対象の生存を再検証し、追撃自身が対象を倒した場合や反射等の派生ダメージで使用者が戦闘不能になった場合には付与しない（R-SUB-02第3項の追加デバフと同じ規約）。付与は各kindの通常経路（免疫判定・毒統合・CombatStat再計算）を通り、付与の帰属先（`sourceUnitId`）はバフの付与者とする。Formula評価の `SKILL_SOURCE` はダメージ計算と同じく**保持者（攻撃者）**で評価する。

## 防御介入とリンクダメージ

### R-INT-01 防御介入順

`DamageWillBeApplied` 後、ダメージ確定前に防御介入系状態を次の順で評価する。

1. `APPLY_TARGET_REDIRECT`: 攻撃対象の引き寄せ、挑発。
2. `APPLY_COVER`: 肩代わり。
3. `APPLY_DAMAGE_LINK`: 継続リンク状態。
4. `APPLY_REFLECT`: 反射。
5. `APPLY_DEATH_SURVIVAL`: 致死耐え。

`DMG-006`（Issue #188）が #1・#2・#4・#5 を、`DMG-007`（Issue #187）が #3 の `APPLY_DAMAGE_LINK` を `R-LNK-01`〜`R-LNK-03` とともに実装した。実装上、#1 と #2 は防御側そのものを差し替えるためこの評価点で確定させ、#3・#4・#5 は成立の判定だけをこの評価点で行う。

- #3 のリンクは、`R-LNK-01` が「対象へ算出された最終ダメージをリンク元の量とする」「シールド・HPへの振り分け前の量を使用する」と定めるとおり、元ダメージの適用が完了してから、その `DamageApplied.calculatedDamage` を基準に発生させる。#4 との相対順序はこの評価順のまま保つ（リンクが先、反射が後）。
- #4 の反射は、`R-INT-03` 第1項が「元ダメージの確定後」と定めるとおり、元ダメージの適用が完了してから発生させる。
- #5 の致死耐えは「致死かどうか」がHPへ適用する量の確定時点で初めて決まるため、成立判定と適用をHP適用時点で行う。#4 との相対順序は保たれる — 反射は耐えた結果を含む元ダメージの適用後に初めて発生するためである。

引き寄せ（#1）と肩代わり（#2）の状態は**攻撃側**が保持する（production定義 `SKL_KARINA_DOWNER_PS1`／`SKL_EVIE_ECO_PS1`／`SKL_LUNA_HUNGRY_PS1` はいずれも攻撃してくる敵＝`TRIGGER_SOURCE` へ付与する）。反射（#4）と致死耐え（#5）は保持者自身が受けるダメージに働くため、防御側が保持する。

### R-INT-02 肩代わり

- 肩代わりが成立した場合、以後のダメージ計算とシールド適用の防御側を肩代わり者へ変更する。
- 元の攻撃対象を参照する後続効果は、EffectAction定義で明示されていない限り、最終的にダメージを受けた対象を参照する。
- 複数の肩代わり候補がある場合の優先順は実装時に具体化する。

第3項の優先順を `DMG-006`（Issue #188）で**付与順の古い順**（先に成立した介入が優先され、以降の候補はその攻撃には作用しない）へ具体化した。同じ行動の中で後から発動したPSが既に成立している介入を横取りせず、結果が後続のPS発動順に依存しないためである。引き寄せ（`R-INT-01` #1）と致死耐え（#5）にも同じ規約を適用する。

肩代わり者が戦闘不能の場合は成立しない（`R-ACTN-01` #2）。肩代わり者が引き寄せ後の攻撃対象自身である場合、防御側は変わらないが `guardRate` の軽減だけは成立する（`ACT_EVIE_ECO_PS1_COVER` の「攻撃を自身に引き寄せ、50%をガードし肩代わりする」）。軽減は最終切り捨ての前に掛ける（`Q-DMG-01`）。

### R-INT-03 反射

- 反射は元ダメージの確定後、元ダメージの適用結果を巻き戻さずに発生する。
- 反射ダメージは新しいダメージとして扱うが、反射からさらに反射を発生させない。
- 反射ダメージは `isReflectedDamage=true` を持つ。

`DMG-006`（Issue #188）の実装では、反射ダメージの適用が防御介入の評価自体を通らないことで第2項を満たす（再反射だけでなく、反射ダメージに対する引き寄せ・肩代わりも起きない）。反射量は `APPLY_REFLECT.formula` の評価結果へ `R-DMG-02` の切り捨てと最低1ダメージだけを適用し、属性相性・会心・与被ダメージ補正は掛けない — 第1項が反射量を「元ダメージからの割合」としてのみ規定し、反射元のスキル威力でも攻撃でもないためである（`R-DOT-01` の継続ダメージと同じ扱い）。ダメージタイプは元ダメージから引き継ぎ、貫通は持たない。

第1項が禁じるのは「元ダメージの適用結果を巻き戻すこと」であり、反射元が元ダメージで戦闘不能になった場合まで反射を成立させることは要求しない。保持者が戦闘不能になっていれば反射は発生させず、反射先が戦闘不能な場合も同様である（`R-ACTN-01` #2）。

### R-LNK-01 リンク元

- 対象へ算出された最終ダメージをリンク元の量とする。
- シールド・HPへの振り分け前の量を使用する。
- 元ダメージの物理／ENタイプと、シールド適用可否を引き継ぐ。

### R-LNK-02 適用

- リンクされた全対象へ、リンク元と同量のダメージをそれぞれ発生させる。
- 対象数で分割しない。
- リンク先では属性、会心、ダメージ増減効果を再計算しない。
- リンク先ごとに対応するシールドとHPへ適用する。
- 元ダメージが毒・炎上などシールド対象外なら、リンク先でもシールド対象外とする。

### R-LNK-03 再リンク禁止

- リンクダメージに `isLinkedDamage=true` を付ける。
- `isLinkedDamage=true` のダメージから新たなリンクを発生させない。

#### リンクダメージの実装（`DMG-007`／Issue #187）

`R-LNK-02` 第1項の「リンク元と**同量**」は、直後の第2項「対象数で分割しない」と対になる規定（リンク先が複数あっても各リンク先が等量を受ける／件数で割らない）として読む。production 定義が持つ割合（`SKL_SUIRAN_CASINO_AS1` の50%、`SKL_DOROTHEA_PIONEER_PS1`／`SKL_CHIZURU_DOMESTIC_PS1` の35%）は `APPLY_DAMAGE_LINK.payload.linkRate` が表し、保持者が複数のリンクを持つ場合も各リンクが自分の `linkRate` をそれぞれ独立に適用する。

リンク量には `R-DMG-02` の最終切り捨てと最低1ダメージだけを適用する。属性相性・会心・与／被ダメージ補正を再計算しないのは `R-LNK-02` 第3項そのものであり、反射（`R-INT-03`）と同じ扱いである。適用は通常ヒットと同じ経路（`applyConfirmedDamageSteps`）を通るため、`R-LNK-02` 第4項「リンク先ごとに対応するシールドとHPへ適用する」はリンク先自身のシールド・サブユニット・致死耐えがそのまま働くことで満たす。

第2項の再リンク禁止は、リンクダメージの適用経路が防御介入の評価（`R-INT-01`）自体を通らないことで満たす — 再リンクだけでなく、リンクダメージに対する引き寄せ・肩代わり・反射も起きない（`R-INT-03` 第2項の実装と同じ構造）。これにより相互リンク・循環リンクは常に1往復で停止し、preflightでの拒否を必要としない。

次の場合はリンクを成立させない。

- リンク先がリンク元自身（自己リンク）: `R-LNK-02` 第1項が求めるのは「リンクされた**全対象へ**」の発生であり、リンク元自身へ二重に適用することではない（`R-HEAL-04` の自己リンクを恒等として扱うのと同じ規約）。`SKL_SUIRAN_CASINO_AS1` が raw 原文どおり「自身と自身以外の味方全体」へ付与しても、自身の分は恒等になり何も発生させない
- リンク元が元ダメージ（または反射等の派生ダメージ）で戦闘不能になった場合、およびリンク先が戦闘不能な場合（`R-ACTN-01` #2）

継続ダメージ（`R-DOT-01`〜`R-DOT-04`）はリンクを発生させない。`R-INT-01` が介入の評価点として定める `DamageWillBeApplied` を継続ダメージは発行せず、この適用経路自体を通らないためである（`R-INT-01` #5 の致死耐えが継続ダメージの対象外であるのとまったく同じ理由）。したがって `R-LNK-01` 第3項／`R-LNK-02` 第5項が引き継ぐと定める「シールド適用可否」は、現行の到達経路では常に「適用可」である。リンク先へはこの可否をそのまま引き渡す実装にしてあり、将来この規則の適用範囲が広がっても引き継ぎ規約は変わらない。

## 継続ダメージ

### R-DOT-01 共通

- 付与時に付与者の攻撃力をスナップショットとして記録する。
- 付与後の攻撃力変化や付与者の戦闘不能は計算へ影響しない。
- 付与対象の行動開始時に発生する。
- ダメージ軽減・増加、属性相性の影響を受けない。
- 効果定義の物理／ENダメージタイプを使用する。
- 各継続ダメージの最終結果で小数部分を切り捨て、ダメージが1未満なら最低1とする。

### R-DOT-02 固定継続ダメージ

- スナップショット攻撃力と効果定義の倍率から固定ダメージを算出する。
- 対応するタイプありシールド、タイプなしシールド、HPの順で適用する。

### R-DOT-03 炎上

- 最大3つまで保持する。
- 各炎上は付与時攻撃力、効果量、期間を保持する。
- 対象が炎上を3つ保持している場合、各炎上インスタンスが発生させるダメージをそれぞれ2倍にする。
- 2倍処理は各インスタンスの最終結果を算出する前に適用し、合計値を後から2倍にしない。

### R-DOT-04 毒

```text
割合ダメージ = 現在HP × 毒効果率
上限ダメージ = 付与時攻撃力 × 100%
毒ダメージ = min(割合ダメージ, 上限ダメージ)
```

- 毒ダメージはシールドとサブユニットで受けない。
- 既存の毒へ再付与した場合、効果期間は長い方、効果量は大きい方を引き継いだ一つの毒を残す。
- 期間と効果量は別々の付与元から採用できる。

#### 継続ダメージ種別とシールド適用可否（`DMG-008`／Issue #189）

`R-DOT-02`〜`R-DOT-04` は算出式・重複規則・シールド適用可否がそれぞれ異なるため、Catalogは `APPLY_CONTINUOUS_DAMAGE.payload.continuousDamageKind`（`FIXED` / `BURN` / `POISON`、省略不可）で種別を明示する。省略時の既定値を置かないのは、「炎上として書いたつもりの定義が固定継続ダメージとして黙って別規則で解決される」近似を作らないためである。

シールドを適用するのは `FIXED`（`R-DOT-02` 第2項）だけである。炎上・毒は `R-SUB-01`「毒、炎上など、通常シールドで受けられないダメージはサブユニットでも受けない」と `R-LNK-02`「元ダメージが毒・炎上などシールド対象外なら、リンク先でもシールド対象外とする」が明示するとおり、通常シールドで受けられないダメージである。

`R-DOT-03` の「最大3つまで」は種別単位で数える（`戦闘システム.md`「炎上は３回まで重複し、同一のキャラクターが炎上を３回受けたとき」は付与元スキルを区別しない）。`R-EFF-05` の `stacking.max` が `EffectKindKey` 単位であるのとは異なる。上限到達時は付与自体を行わず、`EffectActionCompleted.resultKind: SKIPPED` を記録する。

`R-DOT-04` の再付与統合は `Q-EFF-10`「再付与によって既存インスタンスの期間を上書きしない」に対する毒固有の例外であり、`R-STS-02`（気絶）と同じ位置づけである。「効果量」は毒ダメージそのもの、すなわち `min(割合ダメージ, 上限ダメージ)` を尺度として比較する — 割合と上限のどちらか一方だけを別の付与元から採ることはしない（`R-DOT-04` が別々の付与元から採用してよいと述べているのは「期間」と「効果量」の2つであり、効果量を構成する2値をさらに分解してよいとは述べていない）。統合は新規インスタンスを追加せず、`EffectMerged`（`reason: POISON_REAPPLY`）で表す。

この比較には2つの前提がある。どちらも10%毒と20%毒というproduction Catalogに実在する組み合わせで成立を破りうる。

第一に、両候補を**統合時点の対象HP**で評価し直した値で比較する。各インスタンスに保存された割合ダメージ（`AppliedEffect.magnitude`）同士を比べてはならない — 保存値はそれぞれ自分の付与時点のHPで評価されており、評価時点が揃わないと大小関係が実際の毒ダメージと逆転しうる。例えば現在HP 1000で10%毒（保存値100）を受けた後、現在HP 300で20%毒（保存値60）を受けると、保存値では10%毒が残るが、次回発生時の実ダメージは同じ現在HP 300に対して30対60であり20%毒の方が大きい。

第二に、比較尺度は上記の `毒ダメージ = min(割合ダメージ, 上限ダメージ)` そのもの、すなわち**丸め前**の値である。`R-DOT-01` の「小数部分を切り捨て、ダメージが1未満なら最低1とする」は各継続ダメージの**最終結果**へ発生時に適用する共通規則であり、効果量の定義には含まれない。丸めた後で比較すると、最低1へ引き上げられる小さな値どうしが同値に潰れて大小関係が失われる — 例えば現在HP 9では10%毒が0.9、20%毒が1.8で効果量は20%毒の方が大きいが、どちらも最終ダメージは1になるため同値と判定され、10%毒が残ってしまう。その後HPが100へ回復すると、残った10%毒は10ダメージ、採用すべきだった20%毒なら20ダメージであり、差が顕在化する。

なお `戦闘システム.md` の炎上節は「ダメージ計算は効果を付与したキャラクターのその時点の攻撃力から計算されます」と書くが、`R-DOT-01`・`Q-EFF-07`・`05_ドメインモデル.md` がいずれも付与時スナップショットを規定するため、ルール側を正本として**付与時スナップショット**を採る。

継続ダメージの発生は `DamageApplied` ではなく専用の `ContinuousDamageApplied` として記録する。`R-STS-03`「解除対象となるダメージは新たに攻撃スキルによってダメージを受けたときに限り、炎上や毒などによるダメージ…では解除されません」が攻撃ダメージとの区別を要求するためである。

#### 継続ダメージとダメージpipelineの境界（`DMG-011`／Issue #186）

継続ダメージは `R-DMG-05` のダメージpipelineの**外側**で解決する。`DMG-006`（Issue #188）と `DMG-007`（Issue #187）はこれを実装上の帰結として記録し、規則側から確定させるかどうかを M8 完了監査へ委ねていた。監査の結論は**現状維持**であり、次を本ルールの明示的な境界として確定する。

- 致死耐え（`R-INT-01` #5、`APPLY_DEATH_SURVIVAL`）は継続ダメージには働かない。
- リンク（`R-INT-01` #3、`R-LNK-01`〜`R-LNK-03`）と反射（#4）、引き寄せ（#1）・肩代わり（#2）も同様に継続ダメージからは発生しない。

根拠は `R-INT-01` の条文そのものである。同ルールは介入の評価点を「`DamageWillBeApplied` 後、ダメージ確定前」と定めており、継続ダメージはこのイベントを発行しない。介入を継続ダメージへ及ぼすには評価点の新設が必要であり、それは `R-DOT-01` 第4項「ダメージ軽減・増加、属性相性の影響を受けない」— 継続ダメージを他ユニットの状態から独立させる規定 — と正面から衝突する。原文（`戦闘システム.md`）にも継続ダメージへ介入する記述は無い。

この境界は `R-LNK-01` 第3項／`R-LNK-02` 第5項が引き継ぐと定める「シールド適用可否」の適用範囲も同時に決める。現行の到達経路（通常ヒットと `R-SUB-02` の追加ヒット）はいずれもシールド適用可であるため、`LinkedDamageGenerated.shieldApplicable` は常に「適用可」になる。両条項が想定する「毒・炎上などシールド対象外の元ダメージ」は、上の境界がある限り発生しない。引き継ぎ規約自体は実装済みのまま残すため、将来この境界を動かす場合も変えるのは評価点だけで済む。

## 状態異常

### R-STS-01 共通

- 状態異常はデバフの一種とする。
- デバフ解除・デバフ無効の対象とする。
- 状態異常解除・状態異常無効は、状態異常として定義された効果だけを対象とする。

#### 状態異常として定義された効果（`RES-004-STATUS-CONDITION`／Issue #224）

「状態異常として定義された効果」は [`01_ユビキタス言語.md`](./01_ユビキタス言語.md)「状態異常」（「特殊な振る舞いを持つデバフ。気絶、炎上、毒、凍結、暗闇が定義されている」）と [`戦闘システム.md`](./戦闘システム.md)「3. 状態異常について」が列挙する 5 種であり、実装上は 2 つの `EffectActionDefinition.kind` にまたがる。

| 状態異常         | 定義kind                  | 種別値                                                      |
| ---------------- | ------------------------- | ----------------------------------------------------------- |
| 気絶・凍結・暗闇 | `APPLY_STATUS`            | `STATUS_AILMENT_KINDS`（`STUN`/`FREEZE`/`BLIND`）           |
| 炎上・毒         | `APPLY_CONTINUOUS_DAMAGE` | `STATUS_AILMENT_CONTINUOUS_DAMAGE_KINDS`（`BURN`/`POISON`） |

`APPLY_CONTINUOUS_DAMAGE` の `FIXED`（固定継続ダメージ）はどちらの正本も名前付きの状態異常として定義していないため含めない（`R-DOT-02` のシールド適用可否も炎上・毒とは異なる）。`APPLY_STATUS` のうち `STEALTH`/`EVASION`/`DAMAGE_IMMUNITY` 等は対象自身に有利な状態であり、状態異常ではなく `BUFF` として扱う。

この 2 つの値集合が `STATUS` カテゴリ（`R-EFF-02` #2 の分類）の全体であり、状態異常解除・状態異常無効（`REMOVE_EFFECTS`／`EFFECT_IMMUNITY` の `categories: ["STATUS"]`）と、「対象が状態異常にある場合」という総称の照会（`ConditionDefinition.TARGET_HAS_EFFECT` の `categories: ["STATUS"]`）はいずれも同じ集合を見る。Catalog 側が状態異常の種別を列挙してはならない — 列挙は必ず取りこぼしうる近似になるためである。個別の種別を問う条件（「対象が毒状態だった場合」等）は `continuousDamageKinds`／`TARGET_STATE.field: HAS_STATUS` で明示的に絞り込む（`R-EFF-02` の照会粒度 #2・#3）。

### R-STS-02 気絶

- AS、PS、EXスキルを新たに使用できない。
- 指定回数のアクティブ行動機会を待機すると解除する。
- APがあれば待機でAPを1消費する。
- AP 0・EX満タンならEXゲージを全量消費して待機する。
- 再付与時は残り回数が長い方を一つだけ残す。
- 付与時にチャージをキャンセルする。

### R-STS-03 凍結

- AS、PS、EXスキルを使用できない。
- 行動機会では待機する。
- 指定期間の経過、または新たな攻撃スキルによるダメージで解除する。
- 継続ダメージやデバフだけのスキルでは解除しない。
- 再付与時に期間延長や増幅率加算を行わない。
- チャージをキャンセルしない。
- 解除後の次の行動機会にチャージ効果を発動する。

攻撃スキルによるダメージで凍結を解除する場合、解除契機となったダメージを凍結効果定義の増幅率だけ増加させる。スキルに具体の増幅率が記載されていない場合は `+50%` を既定値とする。

### R-STS-04 暗闇

- AS、PS、EXスキルに適用する。
- 必中を無視してMISS判定を行う。
- 複数の暗闇を付与順に独立して処理する。
- 暗闇同士の確率を合算しない。

## 混乱と幻惑

混乱・幻惑は `APPLY_STATUS` の `CONFUSION` / `DAMAGE_TO_HEAL` が表す、保持者が行う攻撃そのものを作り替える効果である。`R-HIT-04`／`R-HIT-05`（M7-018、Issue #272）・`R-CRT-03`（DMG-003A、Issue #295）と同じく、production定義（`SKL_OLGA_VETERAN_EX`「鉄の女」、`SKL_TATIANA_SAGE_AS1`「遅効の毒針」）だけが存在してRule定義が無かったものを `DMG-009`（Issue #193）が明文化した。

どちらも `01_ユビキタス言語.md`「状態異常」と `戦闘システム.md`「3. 状態異常について」が列挙する定義済みの状態異常（気絶・炎上・毒・凍結・暗闇）には含まれない。したがって `R-STS-01` の `STATUS` カテゴリには属さず `DEBUFF` としてだけ分類し、状態異常解除・状態異常無効の対象にはならない（デバフ解除・デバフ無効の対象にはなる）。会心不可（`R-CRT-03`）とまったく同じ扱いである。

### R-CFS-01 混乱の対象振り替え

- 混乱を保持するユニットがASを使用する場合、そのスキルの `EffectSequence` のうち **`DAMAGE` EffectAction を適用する `ACTION` step が対象に指定する TargetBinding** だけ、`TargetSelector.side` を反転（`ALLY`↔`ENEMY`）して評価する。
- 反転は `R-SKL-01` #1 のTargetBinding評価時に一度だけ行う。反転後の候補生成・順序・件数不足の扱い（`R-TGT-01`〜`R-TGT-09`）は通常どおりとする。
- 反転後の候補には使用者自身も含む。`R-TGT-01` は `side: ALLY` から使用者を除外せず、`R-TGT-02` のデフォルト順は使用者からのマンハッタン距離が昇順であるため、単体攻撃は使用者自身へ向かう（距離0）。混乱が指すのは陣営であり、その中の対象順は通常の規則がそのまま決める。
- `fallback` selectorも再帰的に反転する。`side` を持たないselector（`SELF`、派生元だけを持つ `BINDING_DERIVED` 等）は反転しない。
- 反転する selector が `kind: BINDING_DERIVED` で `base` が**別の TargetBinding** を指す場合、その base binding の selector も同じ規則で再帰的に反転する。baseを基準にする `area`（`SAME_ROW_AS_BASE`／`SAME_COLUMN_AS_BASE`／`ADJACENT_ORTHOGONAL`／`DIRECTLY_AHEAD_OF_BASE`／`BEHIND_BASE`）はいずれも基準ユニットと**同じ陣営**の候補だけを採るため、base を元の陣営に残すと反転後の候補が常に0件になり「逆陣営に攻撃を行う」が成立しないためである。この追随は `fallback` ツリーの中に現れる `BINDING_DERIVED` にも及ぶ — `fallback` 自体を再帰的に反転する以上、その基準だけが元の陣営に残ると降りた先で同じ0件になる。base binding が非攻撃stepにも使われている場合、その適用対象も反転後の対象になる（最終項と同じ理由 — 対象集合はbinding単位で一度だけ確定する）。
- 反転するのは `ALLY` と `ENEMY` だけとする。`side: ALL`（両陣営）はそのまま残す — 既に両陣営を覆っており「逆陣営」も自分自身になるためで、`ALLY` へ倒すと本来の全ユニット対象が味方だけへ狭まる。
- ASだけに適用する（原文「アクティブスキルで攻撃する際」）。EX・PS・Memoryは反転しない。ASのチャージ解放（`R-SKL-05`）は同じASの攻撃であるため反転する。
- 攻撃以外のEffectAction（バフ・回復など）が同じTargetBindingを共有する場合、その適用対象も反転後の対象になる。対象集合はbinding単位で一度だけ確定する（`R-SKL-01`）ため、同一bindingを攻撃と非攻撃で分けることはできない。

### R-CFS-02 混乱時のダメージ

- 混乱を保持するユニットがASで行う `DAMAGE` は、`R-DMG-01` の計算ダメージへ混乱倍率 `1 - damageReductionRate` を掛ける。
- 混乱倍率は与ダメージ倍率（`R-DMG-04`）とは独立した専用の倍率とし、`DamageCalculated` payloadが個別に公開する。混乱を保持しない攻撃では常に `1` とする。
- 攻撃側の戦闘中攻撃力が防御側の実効防御力**以下**の場合、`R-DMG-01` の基礎ダメージ `max(0, 攻撃力 - 実効防御力)` の代わりに `攻撃力 × lowAttackBaseDamageRate` を基礎ダメージとする。
- 基礎ダメージの差し替えは、基礎ダメージが攻撃力と実効防御力の差から求まる場合（`FormulaDefinition.kind: SKILL_POWER`）だけに適用する。それ以外のFormula種別は評価結果そのものが基礎ダメージであり差分値を用いないため対象外とする（`R-DMG-01` の `SKILL_POWER` 限定と同じ理由）。
- どちらもASの `DAMAGE` EffectActionだけに適用する。継続ダメージ（`R-DOT-*`）・反射（`R-INT-03`）・リンクダメージ（`R-LNK-*`）・サブユニット追加ダメージ（`R-SUB-02`）には適用しない。
- 複数の混乱を保持する場合は付与順で最初の1件だけを適用する（倍率も基礎ダメージ差し替えも重複させない）。

### R-DTH-01 幻惑

- 幻惑を保持するユニットが行う `DAMAGE` EffectActionは、`R-DMG-05` #1〜#5を通常どおり処理する（命中判定・会心判定・防御介入の評価・ダメージ計算と `DamageCalculated` の発行を含む）。
- #7の適用では、シールド・サブユニット・HPへダメージを適用する代わりに `floor(最終ダメージ × healRate)` を防御側のHPへ回復として適用し、`DamageApplied` の代わりに `DamageConvertedToHeal` を発行する。
- 変換後の回復には回復量補正（`R-HEAL-02`）を適用せず、回復リンク（`R-HEAL-04`）も発生させない。本来のダメージ量からの変換であって回復Formulaの評価ではないためで、`R-LNK-02` 第3項（リンク先で属性・会心・ダメージ増減を再計算しない）と同じ規約である。最大HPを超える分は破棄する。
- ダメージを適用しないため、#8の `UnitDefeated`、#9のリンクダメージ（`R-LNK-*`）・反射（`R-INT-03`）はいずれも発生しない。凍結解除（`R-STS-03`）の契機にもならない。
- 変換されたヒットは、`R-SKL-08` が参照する直前DAMAGE結果として `0` を記録する（ダメージを与えていないため）。
- `DAMAGE` EffectActionだけを変換する。継続ダメージ（`R-DOT-*`）・反射・リンクダメージ・サブユニット追加ダメージ（`R-SUB-02`）は変換しない。
- 使用スキルの種別を問わない（AS・EX・PS・チャージ解放のいずれも変換する）。原文が「ダメージ効果を回復効果へと変換する」とだけ規定し、`R-CFS-01` のような使用スキル種別の限定を持たないためである。
- 複数の幻惑を保持する場合は付与順で最初の1件だけを適用する。
- 混乱と幻惑を同時に保持する場合は、`R-CFS-02` の混乱倍率と基礎ダメージ差し替えを適用して確定した最終ダメージを変換元とする（混乱はダメージ計算に、幻惑は適用段階に働くため順序は一意に決まる）。

## 効果期間と解除

### R-EFF-01 期間単位

効果定義は次の期間単位と初期回数を持つ。

- 行動単位：付与対象自身の行動終了時に減らす。
- ターン単位：ターン終了時に減らす。
- 戦闘単位：戦闘終了まで保持する。
- ヒット単位：指定された与ヒットまたは被ヒットで減らす。
- スキル使用単位：指定されたスキル使用で減らす。

効果インスタンスごとに、残り回数、期間単位、owner、付与された行動ID、付与されたターン番号を保持する。`consumption`、`expiration`、`linkedEffectGroupId` は、回数による効果期間とは別に保持する。

### R-EFF-02 解除

1. 解除スキルの対象カテゴリを確認する。
2. バフ、デバフ、状態異常、シールドなど一致する効果を抽出する。バフ／デバフはR-EFF-05に従い符号付き効果量から判定し、状態異常はR-STS-01によりデバフも兼ねる。
3. 解除数や優先順が定義されている場合はその指定に従う。解除数の上限（`REMOVE_EFFECTS.maxRemovals`、`REMOVE_MARKER.count`）だけが指定され優先順が未指定の場合は、付与順の古い順から採用する。
4. `EffectRemoved` を発行する。R-EFF-09により、解除した効果と同じ `linkedEffectGroupId` を持つ子効果を連動解除する（子を先に、親を最後に、`cascaded: true`／`reason: LINKED_GROUP_CASCADE`）。
5. ステータス、シールド、行動速度を再計算する。

#2 の分類（バフ／デバフ／状態異常／シールドなど）は、解除・免疫（`R-EFF-03`）だけでなく、**対象が何らかのバフ・デバフ・状態異常を保持しているかを照会する条件**（`ConditionDefinition.TARGET_HAS_EFFECT`、M7-001E／Issue #248）も同じ軸を使う。分類の正本は1つとし、付与時点に確定した分類を効果インスタンス自身が保持する（`AppliedEffect.categories`）。分類は定義の種別と付与時点の符号付き効果量だけから決まり、付与後は変化しない。

`STATUS` カテゴリの範囲は `R-STS-01`「状態異常として定義された効果」が定める 5 種であり、`APPLY_STATUS`（気絶・凍結・暗闇）と `APPLY_CONTINUOUS_DAMAGE`（炎上・毒）にまたがる（`RES-004-STATUS-CONDITION`／Issue #224）。炎上・毒は `Marker` ではなく `AppliedEffect` として保持されるため、この照会でのみ判定でき、`TARGET_HAS_MARKER` では代替できない。

照会は次の粒度を持つ。

1. カテゴリ（`BUFF` / `DEBUFF` / `STATUS` / `DAMAGE_MOD` / `SHIELD` / `SUBUNIT`）のいずれかに一致する効果を1つ以上保持しているか。
2. 個別の状態異常種別（気絶・凍結・暗闇など）を保持しているか — これは `TARGET_STATE.field: HAS_STATUS` が担い、対象が保持する状態種別への存在量化として評価する。
3. 継続ダメージの種別（毒・炎上、`R-DOT-01`〜`04`）を保持しているか。
4. どの能力値（`StatKind`）に対するバフ／デバフを保持しているか。

`MarkerState` は `AppliedEffect` ではないため、この照会の対象外とする（`TARGET_HAS_MARKER` が担う）。

### R-EFF-03 無効

- 無効効果が有効な間は、対象カテゴリの新規付与を拒否する。
- すでに付与済みの効果を解除するかどうかは、無効効果の定義に明示する。
- 付与拒否もドメインイベントとして記録できるものとする。

### R-EFF-04 行動単位期間の減算

1. 対象自身の行動終了時に、その対象へ付与された行動単位効果を取得する。
2. 効果の付与行動IDが現在の行動IDと同じ場合は減らさない。
3. 次回以降の対象自身の行動終了時に、各効果インスタンスの残り回数を1減らす。
4. 対象以外のユニットの行動では減らさない。
5. 残り回数が0になった時点で即時に失効させ、`EffectExpired` を発行する。
6. 失効後、影響するステータス、シールド、行動速度を再計算する。

### R-EFF-05 重複効果の期間

- 重複あり効果は、同種であっても効果インスタンスと残り期間を個別に保持する。
- 重複なし効果も、既存効果を上書きせず個別に保持する。
- 重複なし効果では、その時点で最も強い1件だけを計算へ採用する。
- 採用中の最強効果が失効・解除された場合、残っている同種効果を再評価する。
- 残存効果があれば次に強い1件を即時に有効化する。
- 次点効果の残り期間は、非採用中も通常どおり個別に減算する。
- 重複あり／重複なしは効果定義が `stacking.mode`（`STACKABLE` / `NON_STACKABLE`）として宣言する。同種の単位は `EffectKindKey` である。
- 効果定義は `stacking.max` として重複上限（同時に保持できる同種インスタンス数）を持てる。宣言しない場合は上限なしとする。
- 対象が同種インスタンスを上限数保持している場合、それ以上の付与を行わない。既存インスタンスの残り期間・効果量も変更しない。
- 上限到達による不付与は、効果免疫（`R-EFF-03`）による拒否より先に判定する。免疫の残り無効化回数を、1件も追加できない付与で消費させないためである。

`stacking.max` は `APPLY_MARKER` の `stack.max`（`R-EFF-10`）に対応するが、`AppliedEffect` は重複数を単一インスタンスの可変スタック数ではなくインスタンス数そのものとして保持するため、上限を超える値へ丸める（clamp する）先を持たない。そのため上限到達時は付与自体を行わない。

### R-EFF-06 ターン単位期間の減算

1. ターン終了時にターン単位効果を取得する。
2. 効果の付与ターン番号が現在のターン番号と同じ場合は減らさない。
3. 次のターン終了時から、各効果インスタンスの残り回数を1減らす。
4. 残り回数が0になった時点で即時に失効させ、`EffectExpired` を発行する。
5. 失効後、影響するステータス、シールド、行動速度を再計算する。
6. 重複なしの最強効果が失効した場合は、残存する次点効果を即時に有効化する。

### R-EFF-07 消費条件

- `NEXT_OUTGOING_ATTACK` は、効果ownerが次に攻撃を行い、命中判定まで到達した時点で消費する。
- `NEXT_INCOMING_ATTACK` は、効果ownerが次に攻撃対象になったヒットの観測開始時（命中判定の前、`R-DMG-05` #1）に消費する。`UnitBeingAttacked` の発行位置は攻撃前観測（`R-ATM-03`）へ移動したが、消費はヒット単位のこの位置のまま変えない。
- `OUTGOING_HIT` は、効果ownerの攻撃ヒットがMISSでなく確定した時点で消費する。
- `INCOMING_HIT` は、効果ownerへの攻撃ヒットがMISSでなく確定した時点で消費する。ただしNヒット回避（R-HIT-04）だけは消費契機が逆の例外で、自身が回避を成立させた被ヒット（MISS）で消費し、命中が確定した被ヒットでは消費しない。
- `STATUS_BLOCKED` は、効果ownerへの状態付与が無効化された時点で消費する。
- 消費回数が0になった時点で即時に失効させ、`EffectExpired` を発行する。

同じイベントで時間制限と消費条件の両方が成立する場合、消費条件を先に評価し、その後に時間制限を評価する。どちらかで失効した効果は二重に失効処理しない。

### R-EFF-08 特殊失効条件

- `expiration.conditions` は関連するドメインイベント発行後、PS/Memory候補の抽出前に評価する。
- 条件が成立した効果は即時に失効させ、`EffectExpired` を発行する。
- 特殊失効後、影響するステータス、シールド、行動速度、TargetSelector結果を再評価する。

### R-EFF-09 linkedEffectGroup

- 同じ `linkedEffectGroupId` を持つ `AppliedEffect` と `MarkerState` は親子連動グループとして扱う。
- グループの親効果が失効・解除された場合、同じグループの子効果とMarkerも同時に失効させる。
- 子効果だけが消費条件で失効した場合、親効果は維持する。
- 同時失効では、子効果を先に失効させ、最後に親効果を失効させる。
- 失効イベントは各インスタンスごとに発行する。各インスタンスの失効イベント（と、それに続くCombatStat再計算）を発行し、そのPS/Memory候補を検出してから、次のインスタンスへ進む（`R-ATM-01`。発動の時機は解決コンテキストに従う — 効果処理中なら保留、外なら即時）。まとめて除去してからイベント列を発行すると、子効果の失効を契機とするPS/Memory候補の照合が、イベント順ではまだ存在するはずの親効果・親Markerを既に失効済みとして観測してしまう。この規約は5入口すべてに適用する — 期間満了（行動単位・ターン単位）、消費（ダメージ解決内の`OUTGOING_HIT`/`INCOMING_HIT`等を含む）、`REMOVE_EFFECTS`/`REMOVE_MARKER`、凍結解除、付与者の戦闘不能（`removeOnSourceDefeated`、R-EFF-10、M7-020）。またこの規約は**評価経路を問わない** — トップレベルでも進行中のスキル効果処理の内部でも、同じ粒度で発行・検出する。
- 同時失効の順序はロールを第1キーに決める（`CHILD`→ロールなし→`PARENT`）。同じグループが複数の`PARENT`を持つ場合も、すべての`CHILD`をすべての`PARENT`より先に失効させる。この順序は、カスケードで巻き込まれたメンバーだけでなく、同じ除去バッチで自身の期間満了・消費によって同時に失効するメンバー（`seeds`）にも適用する。両者は単一の除去バッチとして一度だけ整列する — 別々に整列すると、カスケードで巻き込まれた`PARENT`が`seeds`側の`CHILD`より先に失効し得る。同じロール階層内では、カスケードで巻き込まれた側を`seeds`より先に置く（ロールを持たないグループではこれが唯一の親子情報になる）。
- グループ内の親子は`DurationDefinition.linkedEffectGroupRole`（`PARENT`/`CHILD`）で明示する。カスケード可否は失効理由（消費/時間制限/特殊失効）では判定しない — `PARENT`の失効は理由を問わず全体へカスケードし、`CHILD`単独の失効はカスケードしない。どちらもロールを持たないグループは対称にカスケードする（EFF-003）。ロールは`AppliedEffect`同士だけのグループにも、`AppliedEffect`と`MarkerState`が混在するグループにも同じ意味で適用する（M7-013）。
- 実装は`AppliedEffect`と`MarkerState`をひとつのグループとして扱う単一の収集関数（`model/linked-effect-group.ts`の`collectLinkedGroupCascade`）と、カスケード分の除去・イベント発行を担う単一の共通実装（`effects/linked-group-cascade.ts`）を持つ。失効（`expireEffects`）・解除（`removeEffects`）・Marker除去（`removeMarkers`／`removeMarkersSteps`／`reduceMarkerStack`）・凍結解除（`removeFreezeEffectSteps`）の4経路すべてがこれを共有する。カスケードで巻き込まれたメンバーは、`AppliedEffect`なら起点に応じて`EffectExpired`または`EffectRemoved`、`MarkerState`なら`MarkerRemoved`を`reason: LINKED_GROUP_CASCADE`／`cascaded: true`で発行する（M7-013、Issue #267）。
- カスケードは`dispellable`を問わない。`dispellable: false`（`REMOVE_EFFECTS`では解除できない）と宣言された子効果も、親の失効・解除には連動して失効する（production Catalogの`TARISA_TROUBLEMAKER_PS1_LINK`／`AOI_ELEGANT_AS1_KOUYOU_LINK`がこの形をとる）。

### R-EFF-10 Marker

- `APPLY_MARKER` の `ADD` は既存Markerのスタック数へ加算する。
- `KEEP_EXISTING` は既存Markerがある場合は変更せず、存在しない場合だけ新規付与する。
- `REFRESH` はスタック数を維持し、Durationを再設定する。
- `REPLACE` は既存Markerを新しい定義内容で置き換える。
- スタック数は0未満にせず、`stack.max` がある場合は上限を超えない。
- Marker が0スタックになった場合は解除し、`EffectRemoved` または `EffectExpired` を発行する。
- Marker の付与、更新、解除後は、Markerを参照するCondition、Formula、TargetSelectorの評価結果が変わり得る。
- `duration.removeOnSourceDefeated: true` を宣言したMarkerは、付与者（`MarkerState.sourceUnitId` ＝直近の付与者）が戦闘不能になった時点でスタック数を問わず解除し、`MarkerRemoved`（`reason: SOURCE_DEFEATED`、`cascaded: false`）を発行する（`MARKER_REMOVAL_ON_SOURCE_DEATH`、M7-020／Issue #279）。評価は`UnitDefeated`発行後、PS/Memory候補の抽出前に行う（R-EFF-08と同じ規約）。解除は同じ`linkedEffectGroupId`を持つ子効果へR-EFF-09のカスケードでそのまま連なる。

この解除契機は`MarkerState`だけが持つ。`AppliedEffect`は付与者の戦闘不能を判定する失効機構を持たず（`expiration.conditions`のConditionにもユニットの戦闘不能を判定するkindが無い）、`APPLY_MARKER`以外の`DurationDefinition`へ宣言しても評価されないため、`catalog-integrity.ts`が`UNSUPPORTED_SOURCE_DEFEATED_REMOVAL`としてCatalogロード時点で拒否する。R-MEM-04によりMemoryの`triggeredEffects`由来の付与は`sourceUnitId`を持たない（`sourceSide`だけを持つ）ため、この契機は成立しない — 原文が指すのは「付与した本人が倒れた」であって「陣営の誰かが倒れた」ではなく、代替の付与者を推測しない。

### R-EFF-11 RuntimeCounter

- RuntimeCounter は定義されたスコープ内で管理する。
- カウンター更新は、対象イベントの状態変更が確定した後、PS/Memory候補抽出の前に行う。
- `RUNTIME_COUNTER` Condition は更新済みの値を参照する。
- 更新は公開値（`value`）が変化した場合だけでなく、内部端数（`carry`、累計ダメージ閾値Counter専用）だけが変化した場合も`RuntimeCounterChanged`を発行する（Issue #143: `value`不変・`carry`不変の更新だけ何も発行しない）。可変状態の変化が必ずイベント列から追跡できるようにするため。
- 解決スコープ終了時にリセットするcounterは、PS/Memory候補スタックが空になった後、破棄してから`RuntimeCounterReset`を発行する。`RuntimeCounterReset`自身の候補解決によって同じスコープへcounterが再生成・更新された場合は、候補スタックが再び空になるたびに破棄・発行・候補解決を繰り返し、リセット対象counterが残らなくなってから解決スコープを終了する。この反復はPS発動済みGuard（`R-PS-07`）を経由しないため、実装は反復回数へ決定的な上限を設け、超過時はエラーとして検出する（`counterUpdates`が自身の`RuntimeCounterReset`を再生契機にする誤ったCatalog定義を想定）。
- Battle単位のcounterは戦闘終了まで保持する。

M6では`SkillRuntime`スコープ（PS発動条件用の最小範囲）だけを実装する。`Battle`／`BattleUnit`スコープは、それらを必要とするproduction Catalog定義が現れるまでFeature Complete必須対象に含めず、Catalogロード時点で明示的に拒否する（Issue #143：当初M6の対象としていたが、実装・検証コストに見合う対象行が現状ないためスコープを縮小した）。必要な定義を追加する際は、そのproduction経路と同じTaskで実装・検証する。

`AppliedEffect`スコープ（効果インスタンス自身が所有する汎用Counter管理）はM7のEFF-005（Issue #162）で実装した。`DurationDefinition.counterUpdates`（`scope: APPLIED_EFFECT`のみ許可）が更新契機を宣言し、同じ`DurationDefinition`の`expiration.conditions`（R-EFF-08）が`RUNTIME_COUNTER` Conditionでそのcounterを参照できる（`RUNTIME_COUNTER`参照は同じ`DurationDefinition`の`counterUpdates`に宣言されたcounterだけを許可する、`SkillDefinition.counterUpdates`と同じ「参照は宣言必須」規則）。`AppliedEffect`スコープのcounterはresolutionScope単位のリセット（`resetScope: RESOLUTION_SCOPE`、`RuntimeCounterReset`）を持たない — 効果インスタンス自身の失効がcounterの破棄を兼ねるため、`RuntimeCounterReset`は発行しない。`MarkerState`も`AppliedEffect`と同じ`DurationState`（`EffectDurationState`）を再利用するためモデル上は`counterUpdates`を宣言できるが、Marker自身のconsumption/expiration機構が別途未実装（`CAP_MARKER`のUNSUPPORTED\*MARKER*DURATION）のため、`counterUpdates`もCatalogロード時点で明示的に拒否する。`EffectSequence`スコープ（`EffectSequence`自身は状態を持たないため専用の保持先が要る汎用Counter管理）はM7のEFF-006（Issue #212）で実装した。`EffectSequence`の実行時識別子には既存の`SkillUseId`（1回の解決を一意に識別する既存の実行時識別子）を再利用し、`BattleUnit.effectSequenceCounters`（`SkillUseId`→`RuntimeCounter`の2段キー）が実行時値を保持する。`EffectSequence.counterUpdates`（`scope: EFFECT_SEQUENCE`のみ許可）が更新契機を宣言する。`AppliedEffect`スコープと異なり、この解決自身が完了した時点（正常終了・中断のいずれでも）で必ずcounterを破棄し`RuntimeCounterReset`を発行する（`resetScope`宣言による選択の余地がない — `EffectSequence`は解決単位を超えて状態を持てないため）。`this.activeEffectSequenceResolutions`（`PassiveActivationRuntime`が保持する一時レジストリ）からエントリを先に削除してから破棄・発行するため、`RuntimeCounterReset`自身を再誘発契機にする誤ったCatalog定義があっても無限ループが原理的に起こらない（`SkillRuntime`スコープの反復回数上限とは異なる安全策）。`RuntimeCounterChanged`／`RuntimeCounterReset`は他スコープと同じくPS/Memory候補抽出の対象になり、`resolvePassiveChain`への注入（`applyEffectSequenceRuntimeCounterUpdates`）とPS自身のEffectSequence解決（`activatePassiveCandidate`）の両方から届く。利用するproduction定義は現状存在しないため、明示的Scenario（`passive-activation-service.test.ts`のRuntimeCounter EFFECT_SEQUENCEスコープdescribe）で検証した。`Battle`／`BattleUnit`スコープ（利用するproduction定義が存在しないためFeature Complete必須対象外）とは異なり、`EffectSequence`スコープは`13*実装計画.md`のM7完了条件が要求する対象であり、本Issueの実装によりR-EFF-11はルールCoverage台帳上で完了した。M6ではさらに次を扱う。

- `RUNTIME_COUNTER` Condition は `modulo` を持てる。`value MOD modulo == 0` を満たした更新でだけ成立する（N回ごと発動、`RUNTIME_COUNTER_MODULO`）。
- 累計ダメージ閾値Counterは、対象の最大HP比の閾値で加算する。1回の更新で閾値を複数回超えた場合はその回数だけ条件を成立させ、閾値未満の端数は次回の更新へ繰り越す（`CUMULATIVE_DAMAGE_THRESHOLD_TRIGGER`）。
- 複数回の条件成立は、候補抽出に複数回分の候補を生成することを意味しない。1回のイベントでCounterを更新した結果として成立する候補は、通常のPS候補抽出・発動済み制限・同時発動制限（`R-PS-02`〜`R-PS-08`）に従って1件ずつ処理する。

### R-EFF-12 再付与時の動的期間

- 効果定義は `duration.reapply` として、再付与時に初期残り回数を差し替える条件と回数を持てる。
- 差し替えは、同じ効果が付与対象に残っている場合だけ評価する。残っていない場合は `timeLimit.count` をそのまま使う。
- 「同じ効果」は、その効果自身の再付与規則が持つ同一性で判定する。再付与が状態種別単位で1インスタンスへ集約される状態異常（気絶＝R-STS-02、凍結＝R-STS-03）だけを状態種別で一致させ、付与元スキルは問わない。それ以外はすべて効果定義IDで一致させる。
- 集約されない状態異常・状態（暗闇はR-STS-04により複数インスタンスを独立して処理する。ステルス・回避・ダメージ無効なども個別インスタンスとして保持する）を状態種別で同一視してはならない。別の効果定義による同種の状態が残っているだけで差し替えが成立してしまうため。
- 一致インスタンスが複数ある場合は、残り回数が最大のインスタンスと比較する。
- 期間単位とownerは `timeLimit` のものを引き継ぐ。差し替えるのは回数だけとする。
- 差し替え後の回数は、その付与に関するすべての判定の正本になる。状態異常の再付与（R-STS-02「残り回数が長い方を一つだけ残す」）の比較も差し替え後の回数で行う。
- 差し替えの成立をイベント種別で区別しない。`EffectApplied` の初期残り回数、または状態異常の `StunDurationChanged` の差し替え後残り回数が、そのまま差し替え結果を表す。
- 再付与規則が新しい付与内容を一切反映しない効果（R-STS-03の凍結）と、`stack.policy` で再付与を解決するMarker（R-EFF-10）には宣言できない。

## 戦術演習（スコアアタック）

戦闘モードが `TACTICAL_EXERCISE` の場合だけ、本領域のルールを適用する。通常戦闘（`NORMAL`）の挙動と既存ルール（R-END、R-HEAL等）は変更しない。

### R-TEX-01 演習定義と編成制約

1. 戦術演習は、敵ユニット1体を相手に固定5ターン以内へ与えたダメージ総量（スコア）を競うモードである。
2. 味方編成にはR-FRM-01～05をそのまま適用する（1～5体、メモリー最大6件）。
3. 敵編成はちょうど1体とし、メモリーを指定できない。違反はリクエスト不備として戦闘開始前に検出する。
4. 規定ターン数は5で固定とし、APIリクエストでは指定できない。R-FRM等が参照する規定ターン数の検証（1～99）とは独立に、演習では常に5を使用する。

### R-TEX-02 スコア定義

1. スコアは、敵ユニットのHPへ向かったダメージの整数累計とする。
2. 各ヒットの計上量は、シールドおよびサブユニット耐久の消費分を除いた後の、HPへ向かうダメージ量とする。残HPによる切り捨ては行わず、ブレイク時のオーバーキル分を含める。
3. ダメージの発生源・種別は問わない。混乱による振り替え、反射、リンク、継続ダメージなど、敵の自傷にあたるダメージも敵HPへ向かうものは計上する。幻惑により回復へ変換されたダメージは計上しない。
4. スコアが増加するたびに `ExerciseScoreAccumulated` を発行する。計上量0の場合は発行しない。
5. スコアは単調増加とし、減算しない。

### R-TEX-03 ブレイク判定と撃破トリガー

1. 演習中の敵ユニットのHPが0に到達した場合、戦闘不能（`DEFEATED`）に代えてブレイクとして解決する。到達経路（攻撃、継続ダメージ、リソース操作等）は問わない。
2. ブレイクは撃破として扱い、「敵撃破時」を契機とするPS・メモリー効果の発動判定を行う。
3. `UnitDefeated` は発行せず、`UnitBroken` を発行する。勝敗判定、行動順キューからの除去、スキル解決の中断は発生しない。
4. ブレイク回数を1増やす。

### R-TEX-04 ブレイク時ステータス強化

1. 強化増分は `inc(n) = 20（n≤3）、17+n（n≥4）` パーセントポイントとする（nはブレイク回数）。
2. 各ステータスの累計倍率・加算値は次のとおりとする。
   - HP：`1 + Σ(k=1..n) inc(k) / 100`。上限なし、nが表の範囲（50）を超えても同式で外挿する。
   - 攻撃力・防御力：`1 + Σ(k=1..min(n,20)) inc(k) / 100`。21回目以降は増分0とし、累計653%で頭打ちとする。
   - 行動速度：`1 + 0.05 × n`。上限なし。
   - 会心率：原基準値 + `n` パーセントポイント（絶対値加算）。上限なし。
3. 会心ダメージボーナスと属性相性ボーナスは強化しない。
4. 強化は戦闘開始時に記録した敵ユニットの原基準値（編成補正・適性補正適用後の基礎戦闘ステータス）に対して毎回再計算し、複利にしない。R-STA-04の2層構造における基礎側（`baseCombatStats`）を書き換え、戦闘中割合補正・固定値補正は既存の再計算規則で強化後の基礎値へ合成する。
5. 各強化後ステータスは共通の数値規則（R-NUM-02）に従い小数部分を切り捨てる。

### R-TEX-05 復活時の状態処理

1. ブレイクした敵ユニットは、同一の解決ステップ内で復活する。
2. 復活時、敵ユニットに付与されたバフ・デバフ・マーカーをすべて解除する。ただしメモリー由来の効果（`sourceSide` を持ち `sourceUnitId` を持たない付与、R-MEM-04）は解除しない。
3. HPを強化後の最大HPまで全回復する。
4. 本復活は演習モード固有のライフサイクル機構であり、回復（R-HEAL系）にも致死ダメージ耐え（`APPLY_DEATH_SURVIVAL`／R-INT-01）にも該当しない。回復量補正・回復リンク・回復契機のトリガーを発生させない。R-HEAL-01の「蘇生は存在しない」は通常戦闘の効果体系に対する規則であり、本ルールはこれを変更しない。
5. 復活完了後に `UnitRevived` を発行する。

### R-TEX-06 復活の即時性と行動順

1. ブレイクから復活までを、HPが0に到達した解決ステップ内で原子的に完了する。敵ユニットが戦闘不能として観測されるタイミングを作らない。
2. AP・PP・EXゲージの現在値と上限、スキルクールタイム、チャージ状態、スキル・効果のRuntimeCounterを引き継ぐ。
3. 行動順キュー上の予約と位置を維持する。ブレイクを理由とする予約除去・行動順再計算を行わない。
4. 多段ヒットスキルの途中でブレイクした場合、残りのヒットは復活後（解除・強化適用後）の敵ユニットへ命中する。

### R-TEX-07 敵発生源効果の存続

1. 敵ユニットが発生源として味方ユニットへ付与済みの効果・マーカーは、ブレイクによって解除しない。
2. 発生源の戦闘不能を契機とする既存の解除規則（マーカーの発生源死亡時解除等）は、ブレイクでは作動しない。

### R-TEX-08 致死ダメージ耐えとの関係

1. 敵ユニット自身のスキルによる致死ダメージ耐え（R-INT-01）は、ブレイク判定に優先する。
2. 耐えが発動した場合、ブレイクは発生せず、ブレイク回数も増えない。
3. スコアには当該ダメージの全量（R-TEX-02の計上量）を計上する。

### R-TEX-09 演習終了条件

1. R-END-01と同じ判定タイミングで、次だけを評価する。
   1. 味方全滅：演習終了、終了理由 `ALLY_DEFEATED`
   2. 5ターン目の終了：演習終了、終了理由 `TURN_LIMIT_REACHED`
2. 敵のHP0はブレイクとして同一解決ステップ内で復活まで完了するため、判定タイミングで敵全滅は観測されない。R-END-02の勝敗優先順は演習では使用しない。
3. 終了確定後は、未処理のキュー、効果、PS候補を処理しない。

### R-TEX-10 演習結果

1. 演習結果は、終了理由、終了ターン、総スコア、ブレイク回数を持つ。勝利・敗北は持たない。
2. ブレイク履歴（ブレイク番号、発生ターン、その時点の累計スコア）は、`UnitBroken` イベントの投影として出力へ含める。
3. 総スコアは、発行された全 `ExerciseScoreAccumulated` の計上量の合計、および最終状態の累計スコアと一致する。

### R-TEX-11 演習ユニットのカテゴリと編成プール

戦術演習の敵ユニットは、プレイアブルユニットと同名でもステータス・スキル係数が異なる演習専用ユニットとして別途管理する（Q-TEX-09）。

1. ユニット定義はカテゴリ `PLAYABLE`（既定。定義書で省略された場合を含む）または `EXERCISE_ENEMY`（戦術演習専用）のいずれかに属する。
2. 戦術演習の編成プールは、味方が `PLAYABLE` のみ、敵が `EXERCISE_ENEMY` のみである。違反は戦闘開始前にリクエスト不備（422）として検出する。
3. 通常戦闘（`NORMAL`）の編成プールは両陣営とも `PLAYABLE` のみである。違反は同じく戦闘開始前に検出する。
4. `EXERCISE_ENEMY` ユニットは開催中フラグ（`exerciseActive`）を必ず持つ。これは現在開催中の演習ユニットを示す表示専用の情報であり、シミュレーションの受理条件には影響しない（開催終了ユニットの演習も受理する。Q-TEX-10）。
5. 編成の開始時ステータスプレビューにも同じ編成プール制約を適用する。プレビューリクエストの戦闘モード（省略時 `NORMAL`）でどちらの制約を使うかを決める（Q-TEX-11）。

## ルールテストの基準

### 編成・ステータス

- コミカルの割り当て候補から最上位役を選べる。
- クレバー3人で1～3人条件の補正を累積する。
- 重複あり効果をすべて加算する。
- 重複なし効果では同種最大の1件だけを採用する。
- 適正外配置のHP、攻撃力、防御力だけを5%減らす。
- 学園レベルのローテーション配分がレベル1（加算0）、2、3、4と50の境界で正しく切り替わる。
- 強化指定なしのリクエストが従来と同一の開始時ステータスになる。
- 陣営の強化指定なしのユニット強化指定と、成長値未定義ユニットへのレベル指定を拒否する。
- ギア効果表の全セル値と同一ステータス重複加算が算出式へ反映される。
- レベル指定の負方向でステータスが0、最大HPが1へクランプされる。

### 行動・ターゲット

- 同速時に味方、敵、前列、絶対左列の順になる。
- 速度再計算でAS／EX予約を維持する。
- マンハッタン距離、前列、絶対左列で対象順が一意になる。
- 列優先で指定列が不足したとき隣の列から補う。
- 必要数より候補が少なくても存在する対象へ発動する。

### スキル・PS

- AP不足または対象不在のASを飛ばして次のASを選ぶ。
- TargetBindingをsequence開始時に評価し、同じsequence内で再評価しない。
- ACTION / BRANCH / RANDOM_BRANCH / REPEAT を定義順に解決する。
- 同じイベントでは先制攻撃PSを通常PSより先に処理し、先制攻撃同士を速度・陣営・配置・定義順で並べる。
- 新しく誘発されたPSを既存候補より先に解決する。
- 同じPSを1解決スコープで2回発動しない。
- 同時発動制限から最上位の1件だけを選ぶ。
- 使用者の戦闘不能後に残りのヒット・対象を処理しない。
- Memory triggeredEffectsをAPI指定順、同一Memory内定義順で解決する。

### ダメージ・効果

- 攻撃力が防御力以下でも最低1ダメージになる。
- ダメージ無効でも1ダメージになる。
- 最終結果だけを切り捨てる。
- 与ダメージ補正、被ダメージ補正、Action内追加ダメージ倍率を定義順に依存せず同じ結果で合成する。
- shieldIgnoreRate分をHPへ直接適用し、残りをシールドへ適用する。
- 回復量にHealingModifierを適用し、最大HPを超えた分を破棄する。
- タイプあり、タイプなし、サブユニット、HPの順で適用する。
- リンク先全員へ同量を適用し、再リンクしない。
- 混乱中のAS攻撃だけが逆陣営へ振り替わり、EX・PSの対象は変わらない。
- 混乱中の攻撃力が実効防御力以下のとき、基礎ダメージが攻撃力の割合になる。
- 幻惑中の攻撃がダメージではなく回復として適用され、戦闘不能・反射・リンクを発生させない。
- 毒の割合ダメージを付与時攻撃力で上限制限する。
- 行動単位効果が付与行動では減らず、対象自身の次回行動終了から減る。
- 重複あり効果の期間を個別に減らす。
- 重複なしの最強効果失効後に、残存する次点効果が有効になる。
- ターン単位効果が付与ターンでは減らず、次のターン終了時から減る。
- 消費条件、特殊失効、linkedEffectGroupの順序で効果が二重失効しない。
- Nヒット回避が、自身が回避した被ヒットだけで消費し、同じ対象の他の被ヒット消費効果を消費しない。
- 回避に失敗して命中した被ヒットが、その回避効果の残りヒット数を減らさない。
- 必中効果を持つ使用者の攻撃が、対象の回避効果とNヒット回避のどちらも発動させない。
- Marker stackのADD、KEEP_EXISTING、REFRESH、REPLACEを区別できる。
- RuntimeCounter更新後の値でConditionを評価できる。

### 戦術演習

- シールド・サブユニット吸収分を除き、オーバーキル分を含んだ量がスコアへ累計される。
- ブレイク3回目と4回目、20回目と21回目、50回超で強化増分の境界が正しく切り替わる。
- 復活時にメモリー由来効果だけが残り、それ以外の効果・マーカーが解除される。
- 多段ヒット中のブレイクで残りのヒットが復活後の敵へ命中する。
- ブレイク時にAP・PP・EXゲージ・クールタイム・行動順予約が維持される。
- 味方全滅と5ターン終了だけで演習が終了し、敵のHP0では終了しない。
