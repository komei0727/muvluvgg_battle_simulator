# テスト戦略

## 目的

本書は、Battle Simulation Contextの仕様を継続的に検証するため、次を定義する。

- テストレベルと各レベルの責務
- ルールID、仕様確認ID、テストケースのトレーサビリティ
- 乱数、時刻、IDを制御した決定的なテスト方法
- ドメインルール、状態遷移、イベント、状態差分の検証方法
- API、Catalog、Worker Pool、負荷試験の範囲
- CIでの実行区分と品質ゲート

本書は [07\_戦闘ルール詳細.md](./07_戦闘ルール詳細.md) の110ルール、[08\_ドメインイベント.md](./08_ドメインイベント.md) 以降の設計、および [02\_仕様確認事項.md](./02_仕様確認事項.md) の決定・保留状況をテストへ対応づける。

## 品質目標

- 決定済みのドメインルールを変更時に即座に検知できる。
- 同じテスト入力と固定RandomSourceから同じ結果を得られる。
- 単独ルールの誤りと、複数ルールの接続順序の誤りを区別して診断できる。
- イベントログと状態差分から戦闘経過を一意に追跡できる。
- API、Worker、Catalogなど技術境界がドメインの意味を変えない。
- 性能劣化、無限連鎖、メモリー増大からサービスを保護できる。

## 基本方針

- 仕様の正本は設計書とルールIDであり、現在の実装結果をそのまま期待値にしない。
- ドメインルールは最も小さい責務のテストで詳細に検証する。
- Battle全体のテストでは、ルール間の順序、状態遷移、イベントを検証する。
- 外部ポートだけをテストダブルへ差し替え、Domain Entity同士を過剰にmockしない。
- 正常例だけでなく、境界値、不成立条件、順序逆転、再入防止を検証する。
- 大きなレスポンス全体のsnapshotだけに依存せず、意味のあるフィールドと不変条件をassertする。
- 発見した不具合には、修正前に最小の再現テストを追加する。
- 実行時間の長い負荷試験と、PRごとの高速な回帰テストを分離する。

## テストレベル

| レベル             | 主対象                                 | 外部依存                         | 主な目的                     | 実行頻度          |
| ------------------ | -------------------------------------- | -------------------------------- | ---------------------------- | ----------------- |
| Domain Unit        | 値オブジェクト、ポリシー、計算サービス | なし                             | 110ルールの個別検証          | 全PR              |
| Domain Scenario    | Battle集約、状態遷移、イベント連鎖     | 固定RandomSource                 | 複数ルールの接続順序         | 全PR              |
| Application Unit   | UseCase、事前検証、結果組み立て        | Portのfake／stub                 | ユースケース調整とエラー     | 全PR              |
| Catalog Contract   | JSON Schema、参照整合性                | テストCatalog／実Catalog         | 定義データの構造・意味整合性 | 全PR              |
| API Contract       | DTO、JSON Schema、HTTP変換             | Fastify inject、fake Worker Pool | 外部契約の互換性             | 全PR              |
| Worker Integration | ESM Worker、Piscina、キャンセル        | 実Worker Thread                  | スレッド境界と障害処理       | main／PR選択      |
| End-to-End         | HTTPからBattle完了まで                 | 実Catalog、実Worker              | 全経路の成立確認             | main／リリース    |
| Property／Model    | 比較器、差分、リソースなど             | 生成データ                       | 広い入力空間の不変条件       | 全PR／nightly     |
| Load／Soak         | HTTP、Pool、Battle、メモリー           | 配備相当環境                     | 容量・性能・耐久性           | nightly／リリース |

Domain UnitとDomain Scenarioをテストの中心とする。End-to-Endだけでルールの網羅を目指さない。

### 実際の配置（co-location + 横断テストのディレクトリ分類）

本 project は上記ツリーではなく **co-location 方式**を採用する。単一モジュールに属するテストは対象コード直下へ `<module>.test.ts` で置き（Unit／Scenario／Contract／Property を含む）、test 支援コードは `src/testing/`（`clock`／`id`／`random`／`traceability`／`fixtures`／`scenario`＝Builder・harness・assertion／`property`＝arbitrary。上記 `support/`＋`fixtures/` 相当）に集約する。

単一モジュールに属さない**横断テスト**は `src/__tests__/` 配下を**カテゴリ別サブディレクトリ**へ分類する。

```text
src/__tests__/
  architecture/        # レイヤー/モジュール境界の禁止import検査（layer-boundary・module-boundary）
  deploy/              # Cloud Run / Knative マニフェスト契約
  e2e/                 # HTTP→Worker→Battle の実経路（*.e2e.test.ts）
  load/                # 負荷・耐久 baseline（*.load.test.ts）
  scenario/            # SCN-BTL 全戦闘シナリオ（runScenario harness）
  golden/              # ユニット軸: production ユニットごとの golden battle（+ __snapshots__/）
  production-catalog/  # 機構固有の実データ結合（IT-CAP-*）
    units/             # ユニット効果軸: <UNIT_ID>.test.ts（IT-UNIT-*）
    memories/          # ユニット効果軸: <MEM_ID>.test.ts（IT-MEM-*）
```

vitest の各 config は `src/**/…` の再帰globのためサブディレクトリで動作する。`production-catalog/units`・`production-catalog/memories`（ユニット効果軸）、`golden`（完走軸）、`production-catalog/` 直下（機構固有の残置層）の関係は「production Catalog 結合テストの軸モデル」節を参照。

#### ファイル名から対象実装が辿れること（REF-013／Issue #316）

co-location の目的は「実装を開いたら隣にテストがある」探索性なので、**テストファイル名は必ず対象実装の
モジュール名で始める**。1モジュールのテストを観点で分割する場合は `<module>.<観点>.test.ts` と
**ドット区切り**にし、`<観点>-service.test.ts` のように**実在しないモジュール名を名乗らない**
（`poison-grant-service.ts` は存在せず実装は `continuous-damage-service.ts` にある、という状態を作らない）。
`.integration`／`.e2e`／`.load` は観点ではなく実行段の指定であり、`<module>.<観点>.integration.test.ts`
のように観点の後ろに置く。

観点で分割している現在のスイートは次の20件（`REF-015`時点の全件）。

### 共通テストビルダー（`src/testing/fixtures/`）

`production-catalog` テストが個別に持っていた同名ローカルヘルパ（`member`／`testUnitDefinition`／
`actorFor`／`definitionsWith`／`initialSnapshotFor`／`seedRecorder`／`contextFor` ほか）は
`src/testing/fixtures/` へ集約する。`scenario/`（合成Catalogで戦闘を組む Builder・harness）とは
役割が異なり、こちらは**実 `catalog/` から読んだ定義を素材に、戦闘途中の状態を直接組み立てる**
ためのものである。

| モジュール                 | 提供するもの                                                                        |
| -------------------------- | ----------------------------------------------------------------------------------- |
| `production-catalog.ts`    | `loadProductionSnapshot`／`unitFrom`・`skillFrom`・`effectActionFrom`・`memoryFrom` |
| `battle-actors.ts`         | `testPartyMember`／`testBattleUnit`                                                 |
| `unit-definitions.ts`      | `testUnitDefinition`                                                                |
| `battle-definitions.ts`    | `definitionsWith`／`definitionsForSkill`                                            |
| `battle-state.ts`          | `initialSnapshotFor`／`reconstruct`                                                 |
| `event-seed.ts`            | `seedRecorder`                                                                      |
| `effect-action-context.ts` | `effectActionGroupContext`／`completedTargetIdsOf`                                  |
| `markers.ts`／`random.ts`  | `testMarker`／`noMissNoCrit`                                                        |

ユニット効果軸のテストが共有するハーネスは `src/testing/production-unit/` に置く。

| モジュール                | 提供するもの                                                                                              |
| ------------------------- | --------------------------------------------------------------------------------------------------------- |
| `effect-manifestation.ts` | `observeEffectAction`／`manifestationBoard`／`EffectManifestationCase`（`-001` の効果発現テーブルの駆動） |
| `memory-manifestation.ts` | `observeMemoryGrants`／`mirroredForEnemyDeclaration`／`MEMORY_SLOTS`（Memory側の6スロット固定盤面）       |
| `passive-activation.ts`   | `openPassiveChain`／`activatedPassiveSkillIds`（`-002` 以降のPS発動連鎖）                                 |

ID は必ずこれらの型付きビルダー経由で組み、テストから branded type への `as never` キャストを
持ち込まない。定義の取得は `!` ではなく throw する getter（`skillFrom` 等）を使い、
Catalog 側の欠落をテスト失敗ではなく明示的なエラーとして表面化させる。

既定値は「会心なし・属性相性なし」の決定的ステータスとし、乱数消費と補正を検証対象の
検証対象の機能だけへ閉じる。テスト意図に関わる値だけを overrides で明示する。

`runProductionUnitBattle`（`testing/scenario/run-production-battle.ts`）の適用基準は
`src/testing/fixtures/index.ts` の冒頭コメントを正本とする。要約すると、実Catalogユニットの
固定1対1戦闘を実経路で完走させ最終結果だけを見るテストには適用し、戦闘途中状態の作り込み・
抽選単位の乱数制御・resolver 内部の中間産物の検証・固定1対1で表現できない編成を必要とする
テストには適用しない。

## テストケース識別子

テストケースへ次の形式の安定したIDを付ける。

```text
<LEVEL>-<SUBJECT>-<NUMBER>
```

例：

- `UT-R-NUM-01-001`：ルール単体テスト
- `SCN-BTL-006`：Battle複合シナリオ
- `APP-SIM-004`：Applicationテスト
- `API-SIM-012`：API契約テスト
- `INT-WRK-003`：Worker結合テスト
- `PROP-ORD-002`：行動順のプロパティテスト

テスト名にはケースIDと期待する振る舞いを含める。

```text
UT-R-ACT-03-004: AP0・EX満タン・行動不能ならEXを全量消費して待機する
```

ケースIDはファイル名に必須とせず、テスト定義またはメタデータから検索可能にする。

`<NUMBER>` は数字だけにする。`API-CONTRACT-015b` のような英小文字サフィックスや `API-ERR-PATH-escaping` のような語尾は、収集器（`test-case-definitions.ts` の `TEST_CASE_ID_PATTERN`）から見て別IDにも同一IDにもなり得ず、一意性検査をすり抜ける。同じ理由で、あるテストのタイトルに別テストのIDを書かない（参照は「上記の互換性検査」のように文章で示す）。

一意性は `UT-TRACEABILITY-005` が `UT`／`IT`／`SCN`／`E2E`／`PROP`／`API` の全レベルへ機械適用する。`it.each` のように1つの論理ケースを複数行で回すものだけ `INTENTIONALLY_SHARED_TEST_CASE_IDS` へ登録する。

## トレーサビリティ

### 追跡単位

次を相互に追跡する。

```text
仕様確認ID（Q-*）
  ↓
ルールID（R-*）
  ↓
テストケースID
  ↓
実装モジュール
```

通常のテストは `R-*` を直接参照する。複数ルールを確認するシナリオは、関連するすべてのルールIDをメタデータへ持つ。仕様決定の経緯確認が必要な場合だけ `Q-*` も関連づける。

### ルールカバレッジ台帳

機械判読可能な台帳をテストコード内に持つ。

```text
RuleTestCoverage {
  ruleId
  testCaseIds[]
  kinds: POSITIVE | NEGATIVE | BOUNDARY | PROPERTY | SCENARIO
}
```

CIは次を検証する。

- [07\_戦闘ルール詳細.md](./07_戦闘ルール詳細.md) から抽出した全ルールIDが台帳に存在する。件数の正本は[`17_残作業対応表.json`](./17_残作業対応表.json)の`current.rules.total`であり、本書と[13\_実装計画.md](./13_実装計画.md)が計画時点の値として書く「110ルール」ではない（M7・M8の実装中に8件を新設し、`REF-022`／Issue #351のEffect kind棚卸しで`R-DMG-06`を後追い新設して現在118件）。
- 台帳が未知または重複したルールIDを参照していない。
- テストケース未登録のルールは、[`17_残作業対応表.json`](./17_残作業対応表.json)で完了責任を持つTaskへ一意に割り当てられている。
- ルールの追加・削除時に台帳更新がない場合は失敗する。
- 残作業（Rule・不完全変換テーマ・未変換Memory）の割当先Taskが、`17_残作業対応表.json`の`tasks[].status`上で`OPEN`である。
- `13_実装計画.md`「M8：高度ダメージ 21件」の21ルールと、M8の実装中に新設した4ルールが、いずれも空でない`testCaseIds`を持つ。
- M8のTaskが未完了Rule・不完全変換テーマを1件も保持していない。

Feature Completeの最終ゲートでは、各ルールに少なくとも1件の実行対象テストがあり、残作業対応表の`ruleAssignments`が空であることを要求する。開発途中は未完了ルールを空の`testCaseIds`として明示し、`remaining-work.test.ts`が全件のTask割当を検証する。Markdownのチェックリストだけで管理せず、テスト実行と台帳をCIで照合する。

「所有者不在」（完了責任を持つIssueがcloseしても残作業だけが台帳へ残る状態）の検出は`M7-010`（Issue #177、M7完了監査）が`m7-completion-audit.test.ts`として追加したが、検証対象がCapability台帳だったため`REF-023`（Issue #352）のCapability廃止で同テストごと退役した。`remaining-work.test.ts`は引き続き件数と割当の一致を見る。

最後の項目は`DMG-011`（Issue #186、M8完了監査）が`m8-completion-audit.test.ts`（`UT-AUDIT-M8-001`〜`002`）として追加した。所有者不在とは別の壊れ方 — 件数は整合しているのに、そのマイルストーンが引き受けたRule・変換行が黙って次のマイルストーンへ滑り込む — を、マイルストーン単位の完了境界として固定する。`13_実装計画.md`の21ルール列挙をテスト側へ写して照合するため、計画側の列挙を書き換えただけでは通らない。

### Effect kind カバレッジ台帳

すべてのEffect kind（`effect-action-definition.ts`の`EFFECT_ACTION_KINDS`、現在26種）は、いずれかの戦闘ルール（`R-*`）に紐づき、単体テストでその効果を保証する。`src/testing/traceability/effect-kind-coverage.ts`の`EFFECT_KIND_COVERAGE`が正本で、`Record<EffectActionKind, { ruleIds, testCaseIds }>`型により kind の追加漏れ・削除余剰をコンパイルエラーとして検出する。CIは次を検証する（`UT-TRACEABILITY-006`〜`009`）。

- 台帳のキー集合が`EFFECT_ACTION_KINDS`と完全一致する（型強制のすり抜けに対する実行時の二重防御）。
- 各kindの`ruleIds`が非空で、全IDがルールカバレッジ台帳に実在する（`UT-TRACEABILITY-002`経由で`07_戦闘ルール詳細.md`の実在ルールへ連鎖する）。
- 各kindの`testCaseIds`が非空で、それぞれが実行対象テストちょうど1件へ解決される。
- 各kindの`testCaseIds`が、そのkindの`ruleIds`のいずれかの`RULE_COVERAGE.testCaseIds`に登録されている（kind→ルール→テストの三者チェーンが閉じており、証跡テストがどのルールの振る舞いを保証するか常に追跡できる）。

新しいEffect kindを追加するときは、規定するルール（無ければ`07_戦闘ルール詳細.md`へ新設）と、その効果を保証する単体テストを同一PRで台帳へ登録する。

### production 全ID網羅監査（ユニット効果軸の受け皿）

全Unit・Memoryの全Skill・全EffectActionは、ユニット単位の結合テスト（`src/__tests__/production-catalog/units/<UNIT_ID>.test.ts`／`memories/<MEM_ID>.test.ts`。標準形は`REF-024`／Issue #353で確立、以降バッチで拡大）が効果発現を検証する。移行の進捗は`src/testing/traceability/production-id-coverage.ts`のallowlist（`UNCOVERED_UNIT_IDS`／`UNCOVERED_MEMORY_IDS`）が台帳として持ち、CIは次を検証する（`UT-AUDIT-UNITCOV-001`〜`003`）。

- allowlist外の全定義に対応テストファイルが存在し、当該定義の全Skill IDと、Skillから到達可能な全EffectAction ID（payload経由のEffectAction間参照の閉包を含む）がファイル内で参照されている。
- allowlist掲載の定義には対応テストファイルが存在しない（カバー済み定義のallowlist残留を禁止し、台帳が縮小のみ許されることを機械的に強制する）。
- allowlistとカバー済み集合の合併がcatalogの全定義と過不足なく一致する（重複・catalog未知IDも拒否）。

導入時点（`REF-022`／Issue #351）はallowlist＝全件で、ユニット単位テストのバッチPRが対応分を縮める。allowlistは**縮む方向にしか編集してはならない**。新規Unit・Memoryの追加時はallowlistへ載せず、同一PRでユニット単位結合テストを書く。

### M8 ダメージpipelineの通し監査

`R-DMG-05`（ダメージイベント順）と`08_ドメインイベント.md`不変条件#6（ダメージ保存則）は、9手順・5項がそれぞれ4つの実装Task（`DMG-004`〜`DMG-007`）へまたがるため、各Taskは自分が追加したイベント・項の前後関係だけをunit levelで検証していた。`DMG-011`が`__tests__/audit/m8-damage-pipeline-audit.test.ts`（`IT-AUDIT-M8-001`〜`003`）として、実 `catalog/` の全production Unitの実戦闘に対する通し検証を追加した。

- `IT-AUDIT-M8-001`: 全ヒットが`R-DMG-05`の9段階を単調非減少の順で発行し、**かつヒット単位で終端に応じた必須部分列を持つ**。ヒットの窓は`skillUseId`で分けてから`UnitBeingAttacked`で開く（1ヒットの途中で発火したPS連鎖が自分のヒットを内側で完走させるため、発行順だけで切ると親ヒットの残り手順が子ヒットの後ろへ回り込む）。
  - 順序だけを見ると「そのヒットで`DamageCalculated`や`DamageApplied`が欠落しても、別のヒットが同じ段階を出していれば成功する」ため、終端を`MISSED`（`R-HIT-01`、#2で終わる）・`CONVERTED_TO_HEAL`（`R-DTH-01`が#7の適用段階だけを差し替える）・`APPLIED`の3つに分類し、それぞれの必須手順をヒットごとに要求する。
  - 必須部分列は「足りない」ことしか見ないため、終端の意味に反する余分なイベント（回避したヒットのシールド誤消費、回復変換前のサブユニット誤消費など）は**許可側の集合**で弾く。「現れてはならないイベント」の列挙では必ず取りこぼす — 実際に`MISSED`が`ShieldConsumed`・`DamageRedirected`・`UnitDefeated`を、`CONVERTED_TO_HEAL`が`ShieldConsumed`・`LethalDamageSurvived`を禁止できていなかった。許可側で書くことで、pipelineイベントを新設したときの既定が「途中終了する2終端では不許可」になる。
  - 9段階すべてと3終端すべてが実データで観測されることも要求し、空振りを防ぐ。`R-DMG-05`が持つもう一組の正当な途中終了 — PS連鎖によるヒットの取り消し（`UT-R-DMG-05-004`／`008`／`009`）と吸収中の中断（`UT-R-SUB-02-016`）— は現行のproduction定義では発生しないため、意図的に終端へ含めていない。発生した時点でこの検査が失敗し、「production Catalogにその経路が現れた」ことを監査結果として扱える。
- `IT-AUDIT-M8-002`: `DAMAGE_APPLIED`／`CONTINUOUS_DAMAGE_APPLIED`の全件で5項の保存則が成立する。5項それぞれが0でない実データを持つことも要求する。
- `IT-AUDIT-M8-003`: `isLinkedDamage`／`isReflectedDamage`が立った`DamageApplied`から、さらにリンク・反射が発生しない（`R-LNK-03`／`R-INT-03`第2項）。

### production Catalog 結合テストの軸モデル

実データに対する結合テストは、**ユニット効果軸 × golden（完走）軸**の2軸を主軸とし、機能軸は機構固有検証の残置層として位置づける。

- **ユニット効果軸（production 定義ごと）**（`src/__tests__/production-catalog/units/<UNIT_ID>.test.ts`／`memories/<MEM_ID>.test.ts`、ID接頭辞 `IT-UNIT-*`／`IT-MEM-*`）。対象定義が持つ**全Skill・全EffectActionが1件残らず効果を発揮すること**を、実 `catalog/` の未改変定義に対して宣言的に固定する、**網羅**の層。網羅そのものは`UT-AUDIT-UNITCOV-001`〜`003`が機械検証する。
- **golden（完走）軸**（`src/__tests__/golden/production-unit-golden-battle.test.ts`）。全 production ユニットが `it.each` で自動的に1件を持ち、完走・不変条件・イベント type 列 snapshot を固定する、**健全性**の層。
- **機能軸（機構固有の残置層）**（`src/__tests__/production-catalog/` 直下、ID接頭辞 `IT-CAP-*`／`IT-CAT-PROD-*`）。複数ユニットが共有する機構や、単一定義へ帰属させられない相互作用だけを残す。ID接頭辞の `CAP` は廃止したCapability概念に由来する歴史的な名残である（`INT-CTL-*` は使わない）。

#### ユニット効果軸の標準形

- 配置は上記のとおり1定義1ファイル（最終的にUnit 69件・Memory 32件）。テストIDは `IT-UNIT-<ID断片>-NNN`／`IT-MEM-<ID断片>-NNN`（定義IDから `UNIT_`／`MEM_` 接頭辞を落とし、アンダースコアをハイフンへ。`NNN`は数字のみ）。一意性は既存の `UT-TRACEABILITY-005` に自動的に乗る。
- **`-001` は明示テーブル駆動の効果発現テスト**。ファイル冒頭に `(SKL_ID, ACT_ID, 期待効果)` の表を宣言し、`it.each` で `loadProductionSnapshot` + `observeEffectAction`（`src/testing/production-unit/effect-manifestation.ts`）を駆動する。ハーネスは検証対象のEffectActionを1件だけ含む最小の合成スキルへ包んで実解決経路（`resolveSkillOrder`→`applyEffectActionGroups`）へ通し、**実際に動いた観測項目だけ**（イベント列・HP変動・効果付与/解除・リソース変動・マーカー・クールタイム）を返す。期待値との `toEqual` 完全一致が「宣言した効果が出ること」と「余計な副作用を出さないこと」を同時に固定する。`ACT_` IDは文字列リテラルで書き、網羅監査（`UT-AUDIT-UNITCOV-001`）の照合を成立させる。Memory側の `-001` は `observeMemoryGrants` で実 `startBattle`（`BattleStarted`）を通し、固定6スロット盤面の**どのスロットが受け取り、どのスロットが受け取らないか**を表で宣言する。
- **`-002` 以降は表で表現できない機構**を個別のitで検証する。PS発火条件は `openPassiveChain`（`src/testing/production-unit/passive-activation.ts`）＋`SequenceRandomSource`、分岐はrandom source固定、EX連鎖は実スキルを `resolveSkillUse` で通す、といった具合に、契機イベント・対象選択・複数対象間の配分など「単発のEffectAction観測では現れない」ことだけを対象にする。
- 相手役は実Catalogのユニットではなく `testUnitDefinition` の最小定義を使い、相手側のPS・特性が観測へ混ざらないようにする。

#### `IT-CAP-*` の retire 基準

1. retire対象が検証するproduction定義すべてが、ユニット効果軸のテストで**同等以上のアサーション**を持つこと。
2. `rule-coverage.ts` に残る参照は代替ID（`IT-UNIT-*` 等）へ差し替えてから削除する（漏れは `UT-TRACEABILITY-005` が検出する）。
3. 合成不能な機構検証（cross-unit相互作用、複数ユニットが共有する機構の代表検証など）は機能軸に残置してよい。
4. retire は対応するバッチと**同一PR**で実施する。

`REF-024`（Issue #353）の第1バッチでは、この基準を単一ユニットへ閉じた3ファイル（`suiran-chaos-ps3-position-relation`・`suiran-chaos-ex-distribute`・`elena-moodmaker-healing-link`）へ適用し、`IT-UNIT-SUIRAN-CHAOS-003`〜`008`／`IT-UNIT-ELENA-MOODMAKER-003`〜`005` へ移して retire した。同じバッチ対象ユニットを参照していても、複数ユニットで共有する機構の代表検証（`stat-mod`・`damage-mod`・`charge-restriction`・`cooldown-manipulation`・`memory-*` ほか）は基準3により機能軸へ残す。

なお `SCN-BTL-*`（シナリオ層）は従来どおり production 定義IDを参照してはならない。

[`15_Unit_Memory変換台帳.md`](./15_Unit_Memory変換台帳.md)の全不完全変換行は、[`17_残作業対応表.json`](./17_残作業対応表.json)で解消責任を持つTaskへ割り当て、対応する production-catalog テストで近似なしの実行結果を確認してから台帳の該当行を除去する（`COOLDOWN_MANIPULATION`／Issue #129と同じ運用）。Issue #143により`RUNTIME_COUNTER_MODULO`（9行）・`CUMULATIVE_DAMAGE_THRESHOLD_TRIGGER`（3行）の計12行は解消済み。`TRIGGER_POSITION_RELATION`（1行）・`TRIGGER_EXCLUSION_TIMING`（3行）はCondition APIをIssue #144で実装済みだが、イベント発行と`TRIGGER_TARGET`/`TRIGGER_SOURCE`解決を含むproduction完走を`RES-005`（Issue #172）が担当する。`RESOURCE_GAIN_MOD`（2行）は`M7-002`（Issue #185）が担当する。`TARGET_STATE_QUERY_BUFF_DEBUFF`（5行）は`M7-001E`（Issue #248）が`TARGET_HAS_EFFECT`／`TARGET_STATE.field: HAS_STATUS`で解消し、`IT-CAP-TARGET-EFFECT-QUERY-PROD-001`〜`005`・`IT-CAP-TARGET-STATE-FIELD-PROD-002`で近似なしの実行結果を確認した。`AOE_PER_TARGET_CONDITION`（1行）は`RES-004-STATUS-CONDITION`（Issue #224）が`STATUS`カテゴリへ炎上・毒を含める分類統一で解消し、`IT-CAP-TARGET-EFFECT-QUERY-PROD-007`〜`009`が`SKL_CHIYURU_MAZE_EX`のAOE対象別適用（Domain Event・StateDelta・独立Reducer復元を含む）と、同じ総称照会へ寄せた`SKL_MERU_FLATSPIN_AS2`・`SKL_NANAE_COMMANDER_PS1`を確認した。同Issueは`HAS_STATUS`の総称利用を解消したため`IT-CAP-TARGET-STATE-FIELD-PROD-001`を撤去し、`HAS_STATUS`自体の証跡はUnitテスト（`UT-R-SKL-06-064`/`065`）へ残した。

対象が保持する効果を照会する条件（`TARGET_HAS_EFFECT`／`HAS_STATUS`）のテストは、条件evaluatorが**評価時点の最新`BattleUnit`だけ**を読む契約を固定するため、次を必ず含める: 成立・不成立に加えて、(1) 絞り込み（`continuousDamageKinds`／`statKinds`）が別種別・別statへ一致しないこと、(2) 複数対象が混在する集合で対象ごとに判定が分かれること、(3) 直前に効果が解除・失効した対象では成立しなくなること、(4) step全体スコープ（BRANCH）で対象が0体なら不成立・2体以上なら例外になること。

## 決定的なテスト

### SequenceRandomSource

テスト用 `RandomSource` は、指定した値を順に返す。

```text
SequenceRandomSource {
  values: number[]
  consumedValues: number[]
}
```

規則：

- 値はDomainのRandomSource契約範囲内とする。
- 値が不足した場合は即時にテストを失敗させる。
- 余った値も原則としてテスト失敗にし、想定外に乱数消費が減ったことを検出する。
- 呼び出し回数と順序をassertできるようにする。
- 値不足時にランタイム乱数へfallbackしない。

確率境界では「判定値が閾値の直前」「閾値と同値」「直後」をテーブル化する。会心率ステータスが0未満または100超でも、判定時の実効値だけが0～100へ補正されることを確認する。

### ID生成器

`BattleId`、`ActionId`、`SkillUseId`、`EffectInstanceId` などを予測可能に生成するテスト実装を使用する。

```text
battle-1
action-1
skill-use-1
effect-1
```

ID文字列そのものを検証目的にしないテストでは、IDの一意性と参照整合性だけをassertする。

### Clockと期限

実時間のsleepで期限テストを行わない。手動で進められるClockまたは期限判定fakeを使用する。

- 期限直前は継続する。
- 期限到達で `EXECUTION_TIMEOUT` になる。
- タイムアウトを `TURN_LIMIT_REACHED` へ変換しない。
- HTTPの強制キャンセルはWorker結合テストで別に扱う。

## テストデータ設計

### Builder

次のBuilderを用意する。

- `UnitDefinitionBuilder`
- `SkillDefinitionBuilder`
- `EffectDefinitionBuilder`
- `MemoryDefinitionBuilder`
- `FormationInputBuilder`
- `BattleScenarioBuilder`
- `CatalogBuilder`

Builderの既定値は「最小で妥当、特殊効果なし」とし、テスト対象以外の要因を減らす。ただし重要な既定値を隠さないよう、生成結果を読みやすいfixture名で表す。

例：

```text
unit({ hp: 1000, attack: 200, defense: 100, actionSpeed: 50 })
activeSkill({ apCost: 1, effects: [physicalDamage({ power: 100 })] })
```

### テストCatalog

用途別に分ける。

| Catalog            | 用途                                   |
| ------------------ | -------------------------------------- |
| `minimal`          | 1対1の最小戦闘と単体シナリオ           |
| `scenarios`        | PS、チャージ、状態異常など複合シナリオ |
| `invalid`          | 参照切れ、重複ID、不正期間             |
| production Catalog | 実データ全体の構造・参照検証           |

ドメインルールテストをproduction Catalogの具体的なユニットへ依存させない。production定義の変更でルールテストの意図が変わることを防ぐ。

### 数値fixture

- 整数化前の端数が分かる値を使う。
- 0、1、最大値、最大値直前・直後を明示する。
- 浮動小数の途中値は必要に応じて許容誤差で比較する。
- 最終ダメージ、HP、AP、PP、EX、期間など整数値は完全一致で比較する。
- テスト期待値へproductionの計算関数を呼び出さない。

期待値の式をテストへ実装コードと同じ形で複製しすぎない。代表的な手計算例と、別形式の不変条件テストを組み合わせる。

## Domain Unitテスト

### 値オブジェクト

- 境界内の生成成功
- 境界外の生成失敗
- 等価性
- 不変性
- JSONやprimitiveへの変換境界

### 比較・選択ポリシー

行動順、PS順、ターゲット順は比較キーごとに独立したテーブルテストを作る。

```text
行動速度 desc
→ 陣営 ALLY before ENEMY
→ 前列 before 後列
→ column asc
```

同じ入力集合を並べ替えても結果順が同じになることをPropertyテストで確認する。入力配列順を暗黙のtie-breakerにしない。

### 計算サービス

- 各補正を一つずつ変えた例
- 複数補正を組み合わせた例
- 途中計算を丸めない例
- 最終値だけ切り捨てる例
- 最低値・上限値を適用する例
- 適用対象外の補正が混ざらない例

## PS連鎖テスト

PSは循環と順序の不具合が起きやすいため、専用のテスト群を持つ。

### 候補順

- 行動速度が異なる所有者
- 同速の味方と敵
- 同陣営同速の前列・後列
- 同じ列条件で絶対左列
- 同じユニットの複数PS定義順
- 先制攻撃候補を通常候補より優先し、先制攻撃同士へ全tie-breakerを適用すること
- 同時発動制限による1件選択

### 再確認

候補検出後、先行PSによって次を変化させる。

- 所有者が戦闘不能になる。
- PP不足になる。
- クールタイムが設定される。
- 発動条件が不成立になる。
- チャージ状態になる。

発動直前確認で候補が除外され、適切な診断理由を観測できることを確認する。

### RuntimeCounter条件（M6最小範囲・SkillRuntimeスコープ）

`R-EFF-11`のうち`SkillRuntime`スコープをM6で検証する。`Battle`／`BattleUnit`スコープは利用するproduction定義が存在しないためFeature Complete必須対象に含めず、Catalogロード時点で明示的に拒否する。`AppliedEffect`スコープは下記「RuntimeCounter条件（EFF-005・AppliedEffectスコープ）」で検証する。

- N回ごと発動（`modulo`）の直前・一致・次周期境界（Issue #143）
- 累計ダメージ閾値の直前・一致・超過、1回の被ダメージで複数閾値を超える場合、端数繰越（Issue #143）
- Counter更新イベントとPS候補検出の順序（Counter更新 → 候補抽出）。`RuntimeCounterChanged`のsequenceが原因イベントより大きく、かつ原因イベント自身の候補抽出より前に発行されること（[08\_ドメインイベント.md](./08_ドメインイベント.md)「複合処理と状態差分の所有」の例外）。`RuntimeCounterChanged`がcounterの`stateDelta`を単独で所有し、原因イベント自身の`stateDelta`にcounter変化を含まないこと

- `TriggerDefinition.eventType: RuntimeCounterChanged`／`RuntimeCounterReset`を持つPS/MemoryがCatalog検証を通過し、それぞれの発行直後に候補化・解決されること（原因イベント自身の候補抽出より先に`RuntimeCounterChanged`由来の候補が解決を終えること、`RuntimeCounterReset`由来の新規候補が生じた場合に解決スコープの終了を遅延すること）
- `RuntimeCounterReset`が、counterを破棄し`stateVersion`を進めた後に発行されること（FACTイベントは状態変更確定後に発行する一般規則どおりで、`RuntimeCounterChanged`のpre-matching例外とは順序が異なること）。`RuntimeCounterReset`由来の候補解決が同じスコープへcounterを再生成・更新した場合、そのcounterが残らなくなるまで破棄・発行・候補解決を繰り返してから解決スコープを終了すること

## 効果期間テスト

### 行動単位

- 付与された当該行動終了では減らない。
- 他ユニットの行動では減らない。
- 対象自身の次回行動終了で1減る。
- 残1から0になった直後に失効する。
- 待機も対象自身の行動終了として減算し、戦闘不能で予約を除去されて行動しなかった場合は減算しない。
- 同じ種別の複数インスタンスが別々の残回数を持つ。

### ターン単位

- 付与ターン終了では減らない。
- 次のターン終了から1減る。
- 残1から0になった直後に失効する。
- 同時に複数失効した場合のイベント順が決定的である。

### 重複なし

- 効果量が異なる複数インスタンスを保持する。
- 最大効果だけ `isEffective` になる。
- 最大効果失効後、次点が同じ終了処理内で有効になる。
- `EffectExpired` → `EffectiveEffectChanged` → `CombatStatChanged` の相対順を確認する。各イベントから誘発されたPSイベントの割り込みは許容し、隣接だけを要求しない。

### リソース獲得量Modifier（M7）

`RuntimeCounter`の`AppliedEffect`／`EffectSequence`スコープと同じM7効果期間モデルで検証する（`M7-002`／Issue #185）。

- EX獲得量+50%/-50%の単体テスト。
- 複数Modifier（増加と減少、同値効果）の重複／非重複合成。
- 行動単位Durationの適用開始・減算・失効境界。
- 基礎量確定 → Modifier適用 → capacity打ち止め → イベント発行、の順序。`ResourceChanged.baseDelta`（基礎量）と`delta`（Modifier適用後・capacity適用後の最終量）が両方とも観測できること。Modifier不在かつcapacity打ち止めなしの場合だけ両者が一致し、capacity打ち止めのみが発生する場合（Modifier不在）でも一致しないこと。
- capacity超過時のModifier適用後の破棄量と`ExtraGaugeOverflowDiscarded`payload（要求増加量がModifier適用後・capacity適用前の量と一致すること）。
- EffectActionを経由しない`EX_GAIN`（AP/PP消費起因）でも`baseDelta`/`delta`が観測できること。
- EXゲージが既に上限で正の`baseDelta`が全量破棄され`delta`が0になる境界。この場合`ResourceChanged`は発行されないが、`ExtraGaugeOverflowDiscarded`が`delta`が0でも発行され、payloadの`baseDelta`から基礎量を復元できること。

## イベントと状態差分

### イベント不変条件

- `sequence` が重複せず昇順である。
- 子イベントのsequenceが親より大きい。
- 同じ解決スコープでrootが一致する。
- 同じ行動・スキル解決でIDが一致する。
- 状態変更を所有するイベントが一つだけである。
- 内訳イベントに同じ差分を重複させない。
- TIMINGイベント後に親処理の前提を再検証する。
- DETAILEDからDIAGNOSTICを除いても状態履歴が変わらない。

### 独立した差分Reducer

テスト用に `StateTransitionResponse` を適用する小さなReducerを作る。productionのBattleObservationやResultAssemblerをそのまま呼び出さない。同じ不具合を期待値側でも再現することを防ぐ。

確認内容：

1. 初期 `stateVersion` が0。
2. 各差分でversionが1ずつ進む。
3. 前後versionが連続する。
4. `causedBySequence` が正規の内部イベント列に存在する主イベントを参照する。公開レベルでそのイベントが省略されることは許容する。
5. イベントの `stateTransitionIndex` が対応差分を指す。
6. 全差分適用後に最終状態と深い等価になる。
7. 差分を一件抜く、逆順にする、重複させると検証が失敗する。

### Snapshotの使用範囲

Snapshotを許容する対象：

- OpenAPI文書
- 小さく安定したイベント列の補助確認
- エラーレスポンスの代表例

Snapshotだけにしない対象：

- ダメージ計算
- 勝敗
- リソース消費
- PS順序
- 効果期間
- 状態差分復元

Snapshot更新時は仕様変更と単なる出力変化をレビューで区別する。

## Property／Modelテスト

ランダム生成にはテスト用seedを固定し、失敗時にseedと最小反例を記録する。再実行可能な形式でCIログへ残す。

### 主なProperty

- 任意の有効編成でHP、AP、PP、EX、シールド、期間が負数にならない。
- EXゲージがユニット固有最大値を超えない。
- 行動順比較器が反対称性、推移律、決定性を満たす。
- 入力配列順を変えても行動順結果が変わらない。
- 速度再計算でキューから行動済み者が復活しない。
- 速度再計算で予約済みAS／EXが変化しない。
- ターゲット距離が負にならず、マンハッタン距離の対称性を満たす。
- シールド吸収＋サブユニット吸収＋HPダメージが適用ダメージと一致する。
- リンク対象数を変えても各対象のリンクダメージ量が変わらない。
- 効果インスタンス追加・失効後も同一IDが重複しない。
- 初期状態へ全差分を適用すると最終状態になる。
- `COMPLETED` 後に状態が変化しない。

生成器はドメイン上有効な入力を基本とし、無効入力生成器は値オブジェクト・Command検証用に分ける。

## Applicationテスト

### Portのテストダブルと実行保護

実際に注入するPortは次で、テストダブルへ差し替える。

- `BattleCatalog`（Port）→ `CatalogBuilder`（`testing/scenario/catalog-builder.ts`）が生成する `TestBattleCatalog`。合成した定義グラフを返し `loadSnapshot` 呼び出し回数を記録する。UseCase単体テストで従来インライン定義していた `FakeBattleCatalog` はこれへ一本化する。
- `RandomSource`（Port）→ `SequenceRandomSource`（枯渇throw・余剰検出・消費列追跡）。
- `BattleIdGenerator`（Port）→ `FixedBattleIdGenerator`。
- `Clock`（Port）→ `ManualClock`。

一方、次は当初「Port」を想定していたが実アーキテクチャではPortではないため、テストダブルではなく実物＋決定的入力で検証する。

- **実行保護（ExecutionGuard）はPortではなくドメイン設定**。PS連鎖などの上限は `PassiveChainLimits`（`domain/battle/triggering/passive-chain-limits.ts`）とイベント上限で表現し、超過を `EXECUTION_LIMIT_EXCEEDED` として検証する。協調的な期限は `SimulationExecutionContext.deadlineEpochMs`＋`ManualClock` で与え、期限超過を `EXECUTION_TIMEOUT` として検証する（`ManualExecutionGuard` という差し替えPortは実装しない）。
- **Observationはポートではなく純関数** `buildBattleObservation`（`application/observation/battle-observation.ts`）。`InMemoryBattleObservation` という差し替えPortは存在せず、`SimulationResultAssembler` 経由で観測結果（イベント・状態差分）を検証する。

UseCaseの高速な単体テストではCatalogとClockを差し替える。Battleルール自体をmockして期待結果を捏造せず、正常系の主要ケースでは実Battleを使用する。

### 事前検証

- 複数のCommand違反を一度に収集する。
- Command違反時はCatalogやBattleを呼ばない。
- 不明なユニット・メモリーIDをpath付きで返す。
- 推移的参照切れを検出する。
- Catalogを戦闘中に再取得しない。
- 同一ユニット定義の参加枠へ別BattleUnitIdを付ける。

### エラー変換

- 既知の入力違反を `INVALID_COMMAND` にする。
- 期限切れを `EXECUTION_TIMEOUT` にする。
- 実行保護上限を `EXECUTION_LIMIT_EXCEEDED` にする。
- 内部不変条件違反を成功結果や敗北にしない。

## Catalogテスト

### 構造

- manifestと各JSONがSchemaに適合する。
- ID、列挙値、整数・割合、期間が許容形式である。
- ファイルハッシュがmanifestと一致する。
- 未知プロパティを拒否する。

### 意味

- IDが種類内で一意である。
- すべての参照先が存在し期待する型である。
- 定義順が一意に決まる。
- PSトリガーイベントと条件式を解釈できる。
- 不許可の循環参照がない。

production Catalogの全定義を起動時検証と同じvalidatorで検査する。エラーfixtureでは一つの意図した違反だけを入れ、診断箇所までassertする。

## API契約テスト

### Catalog一覧

- 全Unit・Memoryをdefinition ID昇順で返す。
- Skill、EffectAction、Formula、Condition、triggeredEffectsの完全定義をresponseへ含めない。
- 200でCatalog revision由来ETagとCatalog用Cache-Controlを返す。
- ETag一致の `If-None-Match`で304、本文なしを返す。
- 一覧read modelをHTTP requestごとに再構築しない。

### リクエスト

- 1～5体、0～6メモリー、1～99ターンの境界
- 数値文字列、小数、`null`、未知プロパティの拒否
- 配置のcolumn・rowと共通座標変換
- 同一ユニット定義の重複許可
- Content-Type、Accept、本文上限
- `options` 省略時のDETAILED既定値

### レスポンス

- `schemaVersion`、`catalogRevision`、Battle ID
- 勝敗と終了理由の組み合わせ
- 初期・最終状態のスキーマ
- 公開イベントの連番と因果参照
- `stateTransitionIndex` と差分配列
- SUMMARYでも全状態差分を保持
- エラーのcode、path、ruleId、diagnosticId
- スタックトレースや内部パスがない
- `Cache-Control: no-store` とRequest ID
- Catalog一覧だけはETagと短いpublic cacheを返し、戦闘POSTの `no-store`と混同しない。

### CORS

- 許可したGitHub Pages originのCatalog GET、戦闘POST、preflightを受理する。
- 未許可originにCORS response headerを返さない。
- `Origin`なしの既存requestを拒否しない。
- browserから `X-Request-Id`、`Retry-After`、`ETag`を参照できる。
- 不正な `CORS_ALLOWED_ORIGINS`を起動時に拒否する。

### OpenAPI

- OpenAPI 3.0.3として検証できる。
- 全ルートと全ステータスにSchemaがある。
- 実際の代表レスポンスが生成Schemaへ適合する。
- 保存された文書を採用する場合は再生成差分がない。
- 互換性検査で意図しない破壊的変更がない。

#### 実装（REL-004 / Issue #203）

3.0.3適合は、生成文書のSchema Objectが仕様「Schema Object」の採用keyword部分集合に収まっているかを走査して確かめる（`testing/openapi/openapi-303-conformance.ts`）。後発のJSON Schema（`const`・`prefixItems`など、OpenAPI 3.1系）が混ざると厳格なclient generatorが落ちるため、`openapi: "3.0.3"`と宣言している以上ここを固定する。走査器自体が素通りしないことは`API-OPENAPI-021`が既知の不適合入力で確かめる。

互換性検査は、凍結した`apps/api/openapi/v1-baseline.json`と生成文書を比較し、`10_API設計.md`「バージョニング」が破壊的と定めるものだけを失敗させる（`testing/openapi/openapi-breaking-change.ts`）。後方互換な追加（任意プロパティ・新イベント種別・新エラーコード・新列挙値）は通るので、追加のたびのbaseline更新は要らない。文書全体のsnapshot比較にしないのはこのためで、毎回更新を強いると「意図的な追加」と「うっかりの破壊」がレビューで区別できなくなる。

比較は`paths`と`components.schemas`の両方を見る。`$ref`は解決せず（自己参照する`ConditionDefinition`で無限再帰になる）、参照先の中身はcomponentsを名前どうしで突き合わせ、`paths`側では参照先の名前が変わっていないかだけを見る。

`oneOf`のvariantは配列indexではなく判別子（`type`／`kind`の単一値`enum`）で対応付ける。判別子は一意とは限らないため（`ConditionDefinition`の`kind=TARGET_STATE`は`field`と`value`の型の組み合わせごとに複数variantある）、同じ判別子のグループ内ではまず内容が完全に一致するものを消し込み、残りだけを出現順で対応付ける。indexや出現順だけで対応付けると、variantが1つ挿入されただけで以降が全部ずれ、後方互換な追加を大量の破壊的変更として誤報する。

レスポンス側の`required`縮小（プロパティは残す）は失敗させない。「バージョニング」がこれを条件付き（「緩めた後も従来から公開されていた変種では常に存在することを併せて示す」）でしか後方互換と認めておらず、その条件は文書だけからは判定できないため、緩和する側が設計書へ根拠を書く責任を負う。

baselineの更新は意図的な操作として扱う。`apps/api/scripts/write-openapi-baseline.mjs`で再生成し（スクリプトがPrettierを通すので`format:check`は追加操作なしで通る）、その差分をレビュー対象にする（本節「Snapshotの使用範囲」の「仕様変更と単なる出力変化をレビューで区別する」と同じ扱い）。

## Worker・インフラテスト

### Worker境界

- DTOと結果が構造化クローンできる。
- HTTPオブジェクトやDomain Entityを渡さない。
- コンパイル済みESMワーカーをproductionと同じパスで起動できる。
- ワーカーごとにCatalogを一度だけ読み込む。
- 期待Catalogリビジョン不一致を拒否する。
- 複数リクエストのBattle状態が混ざらない。

### 容量と障害

- `concurrentTasksPerWorker = 1` を維持する。
- Pool満杯を `503 CAPACITY_EXCEEDED` にする。
- 利用者別上限を `429 RATE_LIMIT_EXCEEDED` にする。
- 協調期限を `504 EXECUTION_TIMEOUT` にする。
- クライアント切断で外側のタスクをキャンセルする。
- ワーカー異常終了後にタスクを自動再実行しない。
- 障害ワーカーが補充される。
- Graceful Shutdownの受付停止、待機、強制終了順を守る。

Worker結合テストは共有状態と実時間依存を避け、各テスト専用Poolを生成して必ずcloseする。

### Container・Cloud Run境界

- production containerをLinux amd64向けにbuildできる。
- containerがnon-rootで起動し、注入した `PORT`へ `0.0.0.0`でlistenする。
- image内のCatalog、コンパイル済みWorker、OpenAPIを解決できる。
- SIGTERM受信後8秒以内に受付停止、Pool終了、process終了を完了する。
- Cloud Run設定のminimum 0、maximum 1、concurrency 2、timeout 40秒が宣言値と一致する。
- GitHub ActionsのCloud Run deployが長期service account keyを使用しない。

## End-to-Endテスト

最小限の代表経路に絞る。

1. HTTPから最小Catalogの基本戦闘を完了する。
2. GitHub Pages相当の別originから一覧GETと戦闘POSTを完了する。
3. PS連鎖と状態差分を含む戦闘を完了する。
4. 同一ユニット重複と最大編成人数を受理する。
5. Worker Pool容量不足をHTTP `503` で返す。
6. タイムアウトをHTTP `504` で返す。
7. 初期状態からレスポンス差分を復元して最終状態と一致する。
8. Cloud Run revisionの公開HTTPS URLでlive、ready、Catalog GET、最小simulationを完了する。
9. deployed GitHub Pages originからCloud RunへのCORS preflightと実requestを完了する。
10. 新revisionのsmoke test失敗時に直前の正常revisionへtrafficを戻せる。

End-to-Endでは全110ルールを個別に再検証しない。失敗時に原因を切り分けられる小さな下位テストを正本とする。

## モジュール境界のリファクタリング（`#132`）

M6〜M8に備えたDomain内部モジュール境界の再編（`#132`、PR1〜PR5）は、既存挙動を一切変更しない前提のArchitecture refactoringである。次のテスト方針で非回帰を保証する。

### Module境界テスト

- Layer間の禁止依存を検証している既存のESLint `no-restricted-imports` テスト（`layer-boundary.test.ts`）と同様の方式で、[04\_境界づけられたコンテキスト.md](./04_境界づけられたコンテキスト.md)「モジュールの依存順序」「モジュール依存規則」の禁止importをテストした（PR5で追加、`src/__tests__/architecture/module-boundary.test.ts`のUT-MOD-001〜028）。
  - `catalog` から `formation`／`battle` への import がないこと。
  - `formation` から `battle/model` 以外の `battle/*` への import がないこと。
  - `battle/model` から他のどの `battle/*` サブモジュールへも import がないこと。
  - `battle/events` から `battle/combat`・`battle/lifecycle`・`battle/triggering`・`battle/effects` への import がないこと。
  - `battle/effects` と `battle/combat` が互いを import していないこと。
  - `battle/*` の下位モジュールから `battle/lifecycle` への逆依存がないこと。
  - `presentation` から `domain` への直接importがないこと（既存規則の維持確認）。
  - 上記に加え、`battle/model`・`battle/lifecycle`を含む`battle/*`全サブモジュールから`formation`への逆依存がないこと（`formation`は`battle/model`にのみ依存される一方向）。
  - モジュール別の禁止import設定は、同一ファイルにマッチする既存のDomain Layer共通ルール（`application`／`infrastructure`／`presentation`／`bootstrap`およびNode.js組み込みモジュールの禁止）をFlat configの後勝ち置換で上書きしないこと（`domainRestrictedImports`ヘルパーで両方を常に合成し、`catalog`・`formation`・`battle/*`の全12モジュールパスで確認、UT-MOD-021・022）。
  - `battle/triggering`（M6で新設）と`battle/effects`（M7で新設）は`lifecycle`直下の同格ノードとして、互いを import していないこと、および`triggering`から`combat`への import がないこと（UT-MOD-023〜026）。
  - `domain/battle`・`application`直下に、認識済みサブモジュール以外のファイル・ディレクトリが存在しないこと（実ディレクトリを走査するarchitecture test。`no-restricted-imports`はimport文のみを検査しファイル配置自体は検査できないため、`#132`が解消した平坦化の再発を別の仕組みで防ぐ。UT-MOD-027・028）。
- 循環依存検査（`mise run check:circular` / `madge --circular`）を、移動後の新しいpathに対して実行した（PR5）。PR1時点で現行パスに対して実行済みであり、[04\_境界づけられたコンテキスト.md](./04_境界づけられたコンテキスト.md)「依存方向の検証結果」に記載のとおり、移行表は実際のimportグラフを1件ずつ確認して矛盾がないことを確認している。

### 移動時のcharacterization

機械的移動（PR2: Domain、PR4: Application/Presentation）と責務分割（PR3: Domain、PR4後半のSchema/Route分割）は、それぞれ次を満たしてからマージする。

- 移動前後で、Unit／Scenario／Contract／Integration／E2E／Loadの各テストレベルの実行件数（`it`/`test`の件数）が減っていないことを確認する。テストファイルの移動に伴うimport更新だけを行い、アサーション内容は変更しない。
- 移動対象のファイルと、対応する `*.test.ts` は同一コミット内で一緒に移動し、実装内容の変更（責務分割・ロジック変更）は別コミットへ分離する。
- 責務分割PR（PR3、PR4後半）では、分割前の1ファイルに対する既存テストが、分割後も（importパスの変更以外は）そのまま通ることを確認する。新しい公開境界を追加する場合は、境界を検証する最小限のテストを追加してよい。

### 乱数・イベント順序の非回帰条件

- 固定 `SequenceRandomSource` を用いた既存の `SCN-BTL-*` シナリオが、移動前後で同じ乱数消費回数・消費順を維持することを確認する。
- 既存イベントの `type`・`sequence`・`parentEventId`・`rootEventId` の順序が、移動前後で変化しないことを確認する（スナップショットまたは既存アサーションで検証）。
- `StateTransition`（`stateVersionBefore`/`stateVersionAfter`/`stateDelta`）の内容が変化しないことを確認する。
- `initialState + stateTransitions = finalState` の不変条件が、移動後も成立することを確認する。
- OpenAPI文書、Catalogレスポンス、CORS許可設定、ETag挙動、エラーマッピングが移動前後で意味的に同一であることを契約テストで確認する（PR4対象）。

## テスト基盤の整備状況（2026-07 更新）

シミュレート可能な production Unit が現れた段階で、本戦略書と実装の乖離を点検し、次を整備した。

### ルールカバレッジ台帳の実在照合

`rule-coverage.ts` の正例 testCaseId が「実在する実行対象テスト」に対応することを機械照合する（`rule-coverage.test.ts` の `UT-TRACEABILITY-004`／`005`）。照合ロジックは `remaining-work.test.ts` から `testing/traceability/test-case-definitions.ts` へ抽出して共有し、`it.skip`/`todo`/条件付き無効化・コメント内・文字列内を証跡から除外する。`it.each([...] as const)("%s: ...", ...)` のように ID がテーブル行に存在するパラメタライズドテストも収集対象に含める。

- `UT-TRACEABILITY-004`: 同一ルール内で testCaseId が重複しないこと（ルールを跨いだ共有は複数ルール確認テストとして許容）。
- `UT-TRACEABILITY-005`: 各正例 testCaseId が**ちょうど1件**の実行対象テストに対応すること（phantom ID＝実体0件と、採番衝突＝2件以上の双方を不合格とする）。あわせて、台帳掲載の有無によらず**リポジトリ内で収集された全 testCaseId に衝突がない**ことを検査する — 台帳外で生まれた重複が、後から台帳へ持ち込まれるのを防ぐ。

**合格条件は「ちょうど1件」**（REF-011／Issue #314 で引き上げ済み）。導入時に残っていた採番衝突（同一 ID を複数の別テストが使用）は同 Issue で一括リナンバーして解消した。意図的に1つの ID を複数テストで共有する場合は、`rule-coverage.test.ts` の許可リスト `INTENTIONALLY_SHARED_TEST_CASE_IDS` へ理由コメント付きで登録する — 現在の登録は `SCN-BTL-001` のみ（基準シナリオ「1対1の基本戦闘」1件を、決定性・lethal 経路・use-case lifecycle の複数テストで分担して検証するため）。`UT-R-STA-01-014〜017` の phantom ID は本整備で台帳から除去済み。

### Property テスト（fast-check）

Property/Model テストは fast-check（devDependency）で実装する。共通設定・arbitrary は `testing/property/`（`PROPERTY_ASSERT_CONFIG` は seed 固定・`numRuns` 指定、失敗時に fast-check が seed と最小反例を出力）。配置はこの project の規約（プレーンでないサフィックスは別 config・別 CI ステージを意味する）に合わせ、**専用サフィックスは使わず、対象モジュールの既存プレーン `<module>.test.ts` へ property の `describe` を統合**する（PR default suite で実行。§CIパイプライン「小規模Property test」）。識別は `PROP-*` ID と `describe(... properties (R-...))` タイトルで確保する。初期実装は次を検証し、台帳の該当ルールへ `PROP-*` ID で登録した（`kinds` の `PROPERTY` ラベルを実体化）。

- `R-POS-03`（`PROP-POS-03-*`）: マンハッタン距離の非負性・対称性・同一性・三角不等式。
- `R-ORD-02`（`PROP-ORD-02-*`）: 行動順比較器の決定性・反対称性・推移律・入力配列順非依存。
- `R-NUM-02`／`R-ACT-03`（`PROP-NUM-02-*`／`PROP-ACT-03-*`）: 最終切り捨ての冪等性、EXゲージ上限打ち止めと要求量保存則。
- `R-DMG-01`（`PROP-DMG-01-*`）: `calculateDamage` の finalDamage が整数・最低1・非負、攻撃力に対し単調非減少、実効防御=防御力×(1−無視率)（`damage-calculator.test.ts` へ統合）。
- `R-SHD-03`（`PROP-SHD-03-*`、`damage-application-service.test.ts` へ統合）: 任意のダメージ・`shieldIgnoreRate`・複数のタイプあり／なしプール・HPについて、`DamageApplied` の内訳が `typedShieldAbsorbed + untypedShieldAbsorbed + hitPointDamage + discardedDamage === calculatedDamage`（保存則、`08_ドメインイベント.md` 不変条件 #6）を満たし、各項が非負でHPが0未満にならないこと。あわせて各プールの吸収量が `min(プール合計, 残ダメージ)` に一致し、対応しないタイプありシールドが常に無傷であること（R-SHD-02末尾）。
- 全戦闘の不変条件（`PROP-BATTLE-001`、`testing/scenario/run-scenario.test.ts`）: 任意の有効編成（1〜5体・座標/速度/stats 可変・PREVENTED会心で乱数非消費）を `runScenario` で完走させ、HP/AP/PP/EX 非負・`COMPLETED`・stateVersion 連続・イベント単調を満たす。特定ルールに紐づかない model property のため台帳未登録（横断テスト）。

**Defer（別基盤要）**: シールド側の保存則 R-SHD-03 は `DMG-004`／Issue #194 で `PROP-SHD-03-*` として追加済み。サブユニット吸収を含む5項の保存則と、リンク量不変（R-LNK）・DoT（R-DOT）を含む全ダメージ経路の通し検証は、`DMG-011`（Issue #186）が `IT-AUDIT-M8-001`〜`003` として実 `catalog/` の全production戦闘に対して追加した（生成 property ではなく実データ全数を母集団にする形。合成入力の property 版への拡張は継続作業とする）。状態全復元（初期+全差分=最終）の property 版は StateDelta→snapshot の独立Reducer新規実装が必要で、現状は `state-restoration.test.ts` が response-level で example ベース検証済み。残る `PROPERTY` ラベル付きルールへの拡充も継続作業とする。

### Golden battle 回帰層

全 production Unit について、味方・敵に据えた1対1の決定的戦闘を完走させ、基本不変条件と「勝敗・終了理由・公開イベントの type 列」の小さな安定 snapshot を固定する（`__tests__/golden/production-unit-golden-battle.test.ts`、実行部は `testing/scenario/run-production-battle.ts`）。新たに追加された Unit は自動的にケースが増える（snapshot 未登録なら失敗する強制関数）。

retire の先例として、`UNIT_KEI_JACKKNIFE` の実戦闘完走を検証していた機能軸の `kei-jackknife-selectable-battle-production-catalog.test.ts`（`IT-CAP-BRANCH-REPEAT-PROD-005〜006`）は retire した。KEI は selectable でありこの golden 層が完走を包含し、maximumHp のゲージ境界整数化は domain 単体（`UT-BATTLE-UNIT-010`／`UT-R-STA-01-013`）が守るため。`CAP_RESOLUTION_BRANCH_REPEAT` の BRANCH 機構検証（`IT-CAP-BRANCH-REPEAT-PROD-001〜004`）は機能軸として `production-catalog/` に残る。

### Load/Soak baseline

空白だった Load/Soak レベルへ最小1本（`LOAD-SOAK-001`、`__tests__/load/battle-simulation.load.test.ts`）を追加した。catalog を一度だけロードし（`createProductionBattleRunner`）、production Unit の DIAGNOSTIC 戦闘を反復実行して、実行時間 p50/p95/p99、イベント数、`stateTransitions` 数、レスポンス相当 byte 数、heap 増加を測定し **baseline を CI ログへ JSON 出力**する。固定合格閾値は配備CPU・メモリとSLO確定まで設けず（戦略「baselineを保存し有意な回帰をレビュー対象にする」）、暴走検出のサニティ上限のみ assert する。`mise run test:load` で nightly／リリース前に実行。5対5・深いPS連鎖・複数効果インスタンス等の追加シナリオと固定閾値は継続作業。
