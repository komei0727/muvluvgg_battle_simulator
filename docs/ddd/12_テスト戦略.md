# テスト戦略

## 目的

本書は、Battle Simulation Contextの仕様を継続的に検証するため、次を定義する。

- テストレベルと各レベルの責務
- ルールID、仕様確認ID、テストケースのトレーサビリティ
- 乱数、時刻、IDを制御した決定的なテスト方法
- ドメインルール、状態遷移、イベント、状態差分の検証方法
- API、Catalog、Worker Pool、負荷試験の範囲
- CIでの実行区分と品質ゲート

本書は [07\_戦闘ルール詳細.md](./07_戦闘ルール詳細.md) の全ルール、[08\_ドメインイベント.md](./08_ドメインイベント.md) 以降の設計、および [02\_仕様確認事項.md](./02_仕様確認事項.md) の決定・保留状況をテストへ対応づける。

## 品質目標

- 決定済みのドメインルールを変更時に即座に検知できる。
- 同じテスト入力と固定RandomSourceから同じ結果を得られる。
- 単独ルールの誤りと、複数ルールの接続順序の誤りを区別して診断できる。
- イベントログと状態差分から戦闘経過を一意に追跡できる。
- API、Worker、Catalogなど技術境界がドメインの意味を変えない。
- 性能劣化、無限連鎖、メモリー増大からサービスを保護できる。

## 基本方針

- 仕様の正本は設計書とルールIDであり、現在の実装結果をそのまま期待値にしない。
- ドメインルールは最も小さい責務のテストで詳細に検証する。
- Battle全体のテストでは、ルール間の順序、状態遷移、イベントを検証する。
- 外部ポートだけをテストダブルへ差し替え、Domain Entity同士を過剰にmockしない。
- 正常例だけでなく、境界値、不成立条件、順序逆転、再入防止を検証する。
- 大きなレスポンス全体のsnapshotだけに依存せず、意味のあるフィールドと不変条件をassertする。
- 発見した不具合には、修正前に最小の再現テストを追加する。
- 実行時間の長い負荷試験と、PRごとの高速な回帰テストを分離する。

## テストレベル

| レベル             | 主対象                                 | 外部依存                         | 主な目的                     | 実行頻度          |
| ------------------ | -------------------------------------- | -------------------------------- | ---------------------------- | ----------------- |
| Domain Unit        | 値オブジェクト、ポリシー、計算サービス | なし                             | 全ルールの個別検証           | 全PR              |
| Domain Scenario    | Battle集約、状態遷移、イベント連鎖     | 固定RandomSource                 | 複数ルールの接続順序         | 全PR              |
| Catalog Contract   | JSON Schema、参照整合性                | テストCatalog／実Catalog         | 定義データの構造・意味整合性 | 全PR              |
| API Contract       | DTO、JSON Schema、HTTP変換             | Fastify inject、fake Worker Pool | 外部契約の互換性             | 全PR              |
| Worker Integration | ESM Worker、Piscina、キャンセル        | 実Worker Thread                  | スレッド境界と障害処理       | main／PR選択      |
| End-to-End         | HTTPからBattle完了まで                 | 実Catalog、実Worker              | 全経路の成立確認             | main／リリース    |
| Property／Model    | 比較器、差分、リソースなど             | 生成データ                       | 広い入力空間の不変条件       | 全PR／nightly     |
| Load／Soak         | HTTP、Pool、Battle、メモリー           | 配備相当環境                     | 容量・性能・耐久性           | nightly／リリース |

Domain UnitとDomain Scenarioをテストの中心とする。End-to-Endだけでルールの網羅を目指さない。

UseCase・事前検証・結果組み立てを検証するテストは `application/` 配下へ co-location するが、
独立したID接頭辞レベルは持たず `UT-*` を使う（Issue #594）。Portのfake／stubを外部依存として
許す点はDomain Unitと異なるが、目的（個別の振る舞いを最小責務で検証する）はDomain Unitと同じ
「個別検証」に属するため、識別子空間を分けない — 実際に `APP-*` を名乗る実行対象テストは
`APP-CATALOG-GEAR-001／002` `APP-CATALOG-MAP-001`〜`005` の7件のみで、application層の
他のテストはすでに `UT-*` を名乗っていた。この7件はリネームせずそのまま有効なテストとして
残すが、新規のApplication層テストは `UT-*` を採番する。

### 実際の配置（co-location + 横断テストのディレクトリ分類）

本 project は上記ツリーではなく **co-location 方式**を採用する。単一モジュールに属するテストは対象コード直下へ `<module>.test.ts` で置き（Unit／Scenario／Contract／Property を含む）、test 支援コードは `src/testing/`（`clock`／`id`／`random`／`traceability`／`fixtures`／`scenario`＝Builder・harness・assertion／`property`＝arbitrary。上記 `support/`＋`fixtures/` 相当）に集約する。

単一モジュールに属さない**横断テスト**は `src/__tests__/` 配下を**カテゴリ別サブディレクトリ**へ分類する。

```text
src/__tests__/
  architecture/        # レイヤー/モジュール境界の禁止import検査（layer-boundary・module-boundary）
  deploy/              # Cloud Run / Knative マニフェスト契約
  e2e/                 # HTTP→Worker→Battle の実経路（*.e2e.test.ts）
  load/                # 負荷・耐久 baseline（*.load.test.ts）
  scenario/            # SCN-BTL 全戦闘シナリオ（runScenario harness）
  golden/              # ユニット軸: production ユニットごとの golden battle（+ __snapshots__/）
  production-catalog/  # 直下にテストは置かない（機能軸は廃止済み・Issue #379）
    units/             # ユニット効果軸: <UNIT_ID>.test.ts（IT-UNIT-*）
    memories/          # ユニット効果軸: <MEM_ID>.test.ts（IT-MEM-*）
```

vitest の各 config は `src/**/…` の再帰globのためサブディレクトリで動作する。`production-catalog/units`・`production-catalog/memories`（ユニット効果軸）と `golden`（完走軸）の関係は「production Catalog 結合テストの軸モデル」節を参照。

`architecture/` の module-boundary テスト（`UT-MOD-*`）は [04\_境界づけられたコンテキスト.md](./04_境界づけられたコンテキスト.md) の禁止importの検査に加え、`domain/battle`・`application` 直下に認識済みサブモジュール以外のファイル・ディレクトリが存在しないことを実ディレクトリ走査で検査する（`UT-MOD-027`／`028`。`no-restricted-imports` はimport文しか検査できず、配置の平坦化はここで防ぐ）。

#### ファイル名から対象実装が辿れること（REF-013／Issue #316）

co-location の目的は「実装を開いたら隣にテストがある」探索性なので、**テストファイル名は必ず対象実装の
モジュール名で始める**。1モジュールのテストを観点で分割する場合は `<module>.<観点>.test.ts` と
**ドット区切り**にし、`<観点>-service.test.ts` のように**実在しないモジュール名を名乗らない**
（`poison-grant-service.ts` は存在せず実装は `continuous-damage-service.ts` にある、という状態を作らない）。
`.integration`／`.e2e`／`.load` は観点ではなく実行段の指定であり、`<module>.<観点>.integration.test.ts`
のように観点の後ろに置く。

観点で分割している現在のスイートは次の20件（`REF-015`時点の全件）。

| 対象モジュール                                            | 分割スイート                                                                                                                                                                                                                                                                                          |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `domain/battle/lifecycle/battle.ts`                       | `battle.memory-activation.test.ts`                                                                                                                                                                                                                                                                    |
| `domain/battle/lifecycle/continuous-damage-service.ts`    | `continuous-damage-service.poison.test.ts`                                                                                                                                                                                                                                                            |
| `domain/battle/lifecycle/effect-action-group-resolver.ts` | `effect-action-group-resolver.status.test.ts`／`.stat-mod.test.ts`／`.damage.test.ts`／`.heal.test.ts`／`.resource.test.ts`／`.modifier.test.ts`／`.absorber.test.ts`／`.continuous-damage.test.ts`（`effect-action-group-resolver.test.ts`はstep・EffectSequence走査とディスパッチャ共通契約を担当） |
| `infrastructure/worker/simulation-worker-pool.ts`         | `simulation-worker-pool.cancellation.integration.test.ts`／`.capacity.integration.test.ts`／`.crash-circuit.integration.test.ts`／`.poisoning.integration.test.ts`／`.shutdown.integration.test.ts`                                                                                                   |
| `presentation/http/build-server.ts`                       | `build-server.cors.test.ts`／`build-server.logging.test.ts`／`build-server.disconnect.integration.test.ts`                                                                                                                                                                                            |

| `apps/ui` `shared/api/response-validator.ts`              | `response-validator.simulation.test.ts`（`response-validator.test.ts`は`validateCatalogResponse`を担当）                                                                                                                                                                                              |

`bootstrap/index.integration.test.ts`と`infrastructure/worker/simulation-worker-pool.integration.test.ts`は
観点分割ではなく実行段だけを分けた `<module>.integration.test.ts` であり、上表には含めない。

`effect-action-group-resolver.*.test.ts`の観点はREF-015で切り出した`effect-action/`のkind別
ハンドラ群に対応する（`status`→`status-effect-action.ts`、`absorber`→`absorber-effect-action.ts`など）。
ハンドラは`applyEffectActionGroups`経由でしか駆動できないため、テストの対象実装はresolverのままであり、
ファイル名も`effect-action-group-resolver.<観点>.test.ts`に揃える。

単一モジュールへ紐づかない横断テストは原則 `src/__tests__/` のカテゴリ別サブディレクトリへ置く。
そこへ移すと検証できなくなるもの（対象ディレクトリ内の実装群を総なめする不変条件、`docs/` の台帳自体を
対象とする照合、実サーバー経由でしか観測できないHTTP契約など）だけを co-location 側へ残し、
**その場合はファイル冒頭のコメントで、対象モジュール名を名乗らない理由を明示する**。

この規約は `apps/api/src/__tests__/architecture/co-location-naming.test.ts`（API）と
`apps/ui/src/__tests__/architecture/co-location-naming.test.ts`（UI）が、`UT-MOD-027`／`028` と同じ
実ディレクトリ走査で機械検査する（REF-050／Issue #595）。対象モジュール名を名乗らない例外の一覧は
**コード側の `NAMING_EXCEPTIONS` が正本**であり、このドキュメントには重複させない。新しくこの形の
co-location テストを追加するときは、対象実装名で判別できない理由のコメント付きで `NAMING_EXCEPTIONS`
へ追記する。

### 共通テストビルダー（`src/testing/fixtures/`）

持ち込まない。定義の取得は `!` ではなく throw する getter（`skillFrom` 等）を使い、
Catalog 側の欠落をテスト失敗ではなく明示的なエラーとして表面化させる。

既定値は「会心なし・属性相性なし」の決定的ステータスとし、乱数消費と補正を検証対象の
検証対象の機能だけへ閉じる。テスト意図に関わる値だけを overrides で明示する。

`runProductionUnitBattle`（`testing/scenario/run-production-battle.ts`）の適用基準は
`src/testing/fixtures/index.ts` の冒頭コメントを正本とする。要約すると、実Catalogユニットの
固定1対1戦闘を実経路で完走させ最終結果だけを見るテストには適用し、戦闘途中状態の作り込み・
抽選単位の乱数制御・resolver 内部の中間産物の検証・固定1対1で表現できない編成を必要とする
テストには適用しない。

## テストケース識別子

テストケースへ次の形式の安定したIDを付ける。

```text
<LEVEL>-<SUBJECT>-<NUMBER>
```

例：

- `UT-R-NUM-01-001`：ルール単体テスト
- `SCN-BTL-006`：Battle複合シナリオ
- `API-SIM-012`：API契約テスト
- `INT-WRK-003`：Worker結合テスト
- `PROP-ORD-002`：行動順のプロパティテスト

テスト名にはケースIDと期待する振る舞いを含める。

```text
UT-R-ACT-03-004: AP0・EX満タン・行動不能ならEXを全量消費して待機する
```

ケースIDはファイル名に必須とせず、テスト定義またはメタデータから検索可能にする。

`<NUMBER>` は数字だけにする。`API-CONTRACT-015b` のような英小文字サフィックスや `API-ERR-PATH-escaping` のような語尾は、収集器（`test-case-definitions.ts` の `TEST_CASE_ID_PATTERN`）から見て別IDにも同一IDにもなり得ず、一意性検査をすり抜ける。同じ理由で、あるテストのタイトルに別テストのIDを書かない（参照は「上記の互換性検査」のように文章で示す）。この規則は `UT-TRACEABILITY-010` が「収集された全IDの末尾セグメントが数字だけである」ことを機械検査する（既存の非数字末尾を持つ意図的な集合ID — `it.each` の全行を束ねる `E2E-GOLDEN-PARTY` 等 — は `NON_NUMERIC_TERMINAL_TEST_CASE_IDS` へ理由コメント付きで登録する）。既存番号の直後へ挿し込む採番は行わず、そのプレフィックスの最大値の次番号を使う（並び順に意味はない）。区画（10／100刻みなどで番号帯を予約する採番）は正式な規則にしない — `UT-R-INT-01` の010番台・`UT-R-PS-01` の110番台のように既存コードへ残る区画は、この規則が定まる以前の設計判断の名残であり、今後の採番で模倣しない。

欠番（連番中の未使用番号）はそれ自体では意味を持たない。区画予約の名残、最初から使われなかった番号、後述する退役のいずれもあり得るため、欠番の有無や大きさから採番順や設計意図を読み取ってはならない。廃止されて欠番になったテストケースIDは `src/testing/traceability/retired-test-case-ids.ts` の `RETIRED_TEST_CASE_IDS` へ「ID・退役した経緯（Issue／PR）・理由」を登録する。番号の再利用は過去の証跡との衝突を生むため、台帳に載るIDは復活も再割当もしない（`retired-test-case-ids.test.ts` の `UT-TRACEABILITY-011` が実行対象テストとして復活していないことを機械検査する）。

一意性は `UT-TRACEABILITY-005` が `UT`／`IT`／`SCN`／`E2E`／`PROP`／`API` の全レベルへ機械適用する。`it.each` のように1つの論理ケースを複数行で回すものだけ `INTENTIONALLY_SHARED_TEST_CASE_IDS` へ登録する。

## トレーサビリティ

### 追跡単位

次を相互に追跡する。

```text
仕様確認ID（Q-*）
  ↓
ルールID（R-*）
  ↓
テストケースID
  ↓
実装モジュール
```

通常のテストは `R-*` を直接参照する。複数ルールを確認するシナリオは、関連するすべてのルールIDをメタデータへ持つ。仕様決定の経緯確認が必要な場合だけ `Q-*` も関連づける。

### ルールカバレッジ台帳

機械判読可能な台帳をテストコード内に持つ。正本は `src/testing/traceability/rule-coverage.ts` の `RULE_COVERAGE` である。

```text
RuleTestCoverage {
  ruleId
  testCaseIds[]
  kinds: POSITIVE | NEGATIVE | BOUNDARY | PROPERTY | SCENARIO
}
```

CIは次を検証する（`rule-coverage.test.ts`）。

- [07\_戦闘ルール詳細.md](./07_戦闘ルール詳細.md) から抽出した全ルールIDと台帳のルールID集合が完全一致する（`UT-TRACEABILITY-001`〜`002`）。件数の正本はこの照合そのものであり、ルールの追加・削除時に台帳更新がない場合は失敗する。
- 台帳内にルールIDの重複がない（`UT-TRACEABILITY-003`）。同一ルール内で testCaseId が重複しない（`UT-TRACEABILITY-004`。ルールを跨いだ共有は複数ルール確認テストとして許容する）。
- 各正例 testCaseId が**ちょうど1件**の実行対象テストに対応する（`UT-TRACEABILITY-005`。phantom ID＝実体0件と、採番衝突＝2件以上の双方を不合格とする）。あわせて、台帳掲載の有無によらず**リポジトリ内で収集された全 testCaseId に衝突がない**ことを検査する — 台帳外で生まれた重複が、後から台帳へ持ち込まれるのを防ぐ。意図的に1つの ID を複数テストで共有する場合は、許可リスト `INTENTIONALLY_SHARED_TEST_CASE_IDS` へ理由コメント付きで登録する（現在の登録は `SCN-BTL-001` のみ）。

照合ロジックは `testing/traceability/test-case-definitions.ts` が持ち、`it.skip`／`todo`／条件付き無効化・コメント内・文字列内を証跡から除外する。`it.each([...] as const)("%s: ...", ...)` のように ID がテーブル行に存在するパラメタライズドテストも収集対象に含める。`it.each(識別子)` のようにテーブルが名前付き `const` のときは、同一ファイル内の宣言を `TypeChecker` のシンボル解決で辿って配列リテラルへ解決し、解決できたときはテーブル行のIDも収集する。`let`／`var` や他ファイル由来・関数呼び出しの戻り値など静的に解決できないテーブルは、テーブル行の収集こそ行わないが、タイトル文字列のIDは収集対象から除外しない（`it.each` 自体が不可視になり、台帳外の重複が検査を素通りするのを防ぐ）。ID検査の対象レベルは `UT`・`IT`・`INT`・`SCN`・`E2E`・`PROP`・`API`・`APP` で、`INT`（Worker・Bootstrap統合テスト）・`APP`（アプリケーション層契約テスト）も一意性検査の対象に含む（`API` を含めた理由と同じ — 対象外だと同じIDを別のテストが名乗っても誰も気づかない）。収集器自体の検証は `test-case-definitions.test.ts`（`UT-TESTDEFS-001`）が持つ。走査対象拡張子（`.test.ts`／`.test.tsx`）とソースの`ts.ScriptKind`（拡張子から判定）は`UT-TESTDEFS-002`が持つ — UI（`apps/ui`）が`.tsx`のテストファイルを同じ収集器で走査するため、ID衝突検査は`06_UIテスト戦略.md`を参照。

実行可能テストを持たないRuleは、[07\_戦闘ルール詳細.md](./07_戦闘ルール詳細.md)の当該Rule節に保留理由と追跡Issueを明記したものだけを許す（現在は `R-TGT-06` の列距離順キーのみ、Issue #273）。保留Ruleは台帳上で空の`testCaseIds`として明示する。Markdownのチェックリストだけで管理せず、テスト実行と台帳をCIで照合する。

### Effect kind カバレッジ台帳

すべてのEffect kind（`effect-action-definition.ts`の`EFFECT_ACTION_KINDS`、現在26種）は、いずれかの戦闘ルール（`R-*`）に紐づき、単体テストでその効果を保証する。`src/testing/traceability/effect-kind-coverage.ts`の`EFFECT_KIND_COVERAGE`が正本で、`Record<EffectActionKind, { ruleIds, testCaseIds }>`型により kind の追加漏れ・削除余剰をコンパイルエラーとして検出する。CIは次を検証する（`UT-TRACEABILITY-006`〜`009`）。

- 台帳のキー集合が`EFFECT_ACTION_KINDS`と完全一致する（型強制のすり抜けに対する実行時の二重防御）。
- 各kindの`ruleIds`が非空で、全IDがルールカバレッジ台帳に実在する（`UT-TRACEABILITY-002`経由で`07_戦闘ルール詳細.md`の実在ルールへ連鎖する）。
- 各kindの`testCaseIds`が非空で、それぞれが実行対象テストちょうど1件へ解決される。
- 各kindの`testCaseIds`が、そのkindの`ruleIds`のいずれかの`RULE_COVERAGE.testCaseIds`に登録されている（kind→ルール→テストの三者チェーンが閉じており、証跡テストがどのルールの振る舞いを保証するか常に追跡できる）。

新しいEffect kindを追加するときは、規定するルール（無ければ`07_戦闘ルール詳細.md`へ新設）と、その効果を保証する単体テストを同一PRで台帳へ登録する。

### 攻撃前観測の通し監査（#480）

`R-ATM-03`の「スキル使用ごと・対象ごとにちょうど1回」（`08_ドメインイベント.md`不変条件#5後段）は、実 `catalog/` の全production Unitの実戦闘に対して`__tests__/audit/pre-attack-observation-audit.test.ts`（`IT-AUDIT-ATM-001`）が検証する。**多い方と少ない方の両方向**を見る。

- **重複しない**: 複数ヒット・複数DAMAGE step・`REPEAT`・サブユニット追加ダメージ・追撃はどれも同じ対象へ何度も攻撃を届ける形であり、そのどれかが観測を再発行すれば「攻撃される直前」のPSが1回の攻撃で複数回候補化して実行ガードを押し上げる
- **遅れない**: 観測が**そのスキル使用のどのヒットよりも前**であること（`R-ATM-03` #1）
- **欠落しない**: 実際にヒット列（命中判定）へ到達した対象が、同じスキル使用の観測を持つこと。重複と発行位置だけを見る検査は「ある経路（AS/EX・チャージ解放・PS）が観測を一切発行しなくなる」退行を通してしまうため、この逆向きの照合を併せて要求する。例外は引き寄せ・肩代わり（`DamageRedirected`）で途中から被弾したユニットだけで（`R-ATM-03` #6）、リンク・反射は確定済みダメージの転写でヒット列を通らず、`LAST_*_TARGETS` でDAMAGEを撃つ定義は現行production Catalogに存在しない
- 空振り防止は合計件数ではなく**スキル種別ごと**に立てる（AS・EX・PSのすべてで観測が発行されていること）

チャージ解放は `skillType` が元スキルのAS/EXのままでログから切り分けられないため、経路ごとの発行は engine level の3件が直接固定する — AS/EXは `UT-R-ATM-03-006`、PSは `UT-R-ATM-03-010`、チャージ解放は `UT-R-ATM-03-011`。いずれも「観測を発行すること」だけでなく「その観測を契機とするPSが実際に発動すること」まで見る（発行しても連鎖へ届かない配線漏れを弾く）。

### production Catalog 結合テストの軸モデル

実データに対する結合テストは、**ユニット効果軸 × golden（完走）軸**の2軸で構成する。機能軸（`IT-CAP-*`）は廃止済みで（Issue #379）、`production-catalog/` 直下は `units/`・`memories/` だけになっている。

| 層                                                                                                                       | 保証する                                                                                                                    | 保証しない                                           |
| ------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| **ユニット効果軸**（`production-catalog/units/<UNIT_ID>.test.ts`／`memories/<MEM_ID>.test.ts`、`IT-UNIT-*`／`IT-MEM-*`） | 実 `catalog/` 定義を**スキル使用1回**の単位で使ったときの、発動 / 対象 / 分岐選択 / 結果 / 付与効果が宣言する期間・消費条件 | 原文との一致（機械検証不能）、エンジン横断の不変条件 |
| **golden（完走）軸**（`golden/`）                                                                                        | 1対1ミラー戦と**混成編成戦**の完走・不変条件・イベント snapshot                                                             | 効果量・効果の正しさ                                 |

#### 機能軸は恒久層ではなかった（収束完了）

**機能軸は廃止し、`production-catalog/` 直下を空にした**（Issue #379）。「複数ユニットが登場する」ことは残置の理由にならない — 全 Unit・全 Memory がユニット効果軸に載った時点で、残る機能軸ファイルはすべて**移送待ち**であって恒久層ではなかった。**新しい機構を検証したくなっても `production-catalog/` 直下へファイルを足さない。** 下の判断がそのまま移送先の決め方になる。

- 例えば `specific-immunity`（Aoi の STUN 限定 immunity が Lily の STUN を弾く）の被験体は **Aoi の `EFFECT_IMMUNITY` 宣言**で、Lily は実在の STUN を供給しているだけ → Aoi のファイルへ移す。
- 再付与でしか差が出ない機構（`marker-stack-formula` の stack policy 等）も、「同じスキルを2回使う」はスキル使用単位の範疇なので表の行として書ける。
- どの単一定義にも帰属しない機構（`charge-restriction` の「チャージ中は回避しない」・`resource-gain-mod` の「獲得量補正を配る側と得る側」— 抑止する側と抑止される側が別ユニット）は、**関係する全ユニットのファイルへ複製して移送する**。重複は受け入れる。
- ルール自体は `UT-R-*` が合成定義で押さえており、機能軸の付加価値は「実データでも成立する」の一点。ユニット効果軸が全実定義を実行すればその付加価値も吸収される。

**効果軸ではないものは移動する**（廃止ではない）。HTTP DTO とログレベル投影を検証していた `log-level-projection-api` / `memory-granted-marker-api` / `response-doc-schema` は `production-catalog/` に置かれていること自体が分類の誤りで、`presentation/http/` 配下へ移した。

機能軸ファイルと移送先ユニットの対応表はIssue #379が持ち、12バッチへ分割して消化し終えた。いずれも合成定義（`UNIT_TEST_*`／`SKL_TEST_*`）や後続行動を使った機構検証だったため、移送には**ユニット効果軸へ `-004`以降を新規に書く**作業を伴った。合成定義であること自体は障壁ではない — `IT-UNIT-MAO-COMMITTEE-004` は合成の敵攻撃スキルをユニット軸ファイルの中で組み立てて実「ステルス」の対象逸らしと消費を固定しており、これが標準形である。

##### ハーネスの契機イベントは発行地点と同じ形にする

**ハーネスが実イベントより強い形を合成すると、実戦闘では成立しない契機表現を見逃す。** ユニット効果軸のハーネス（`trigger-events.ts`）が組み立てる契機イベントは、発行地点（`battle.ts` 等）が実際に発行するイベント形に揃える — たとえば `TurnStarted`／`TurnCompleting` は `sourceUnitId`／`targetUnitIds` を持たない。ターン境界は特定のBattleUnitに帰属しないグローバルイベントなので、`sourceSelector`／`targetSelector` のうち成立し得るのは `SELF`（帰属先が存在しないため所有者自身の視点で成立する）と `ANY` だけで、`ALLY`／`ENEMY`／`OTHER_ALLY` は常に不成立になる。

#### ユニット効果軸の標準形

**単位は EffectAction ではなくスキル使用1回**。EffectAction を1件ずつ単体実行する形では、分岐がどの腕を選ぶか・発動条件が成立するか・production の対象選択が誰に当たるかを一切見られない。

- 配置は1定義1ファイル（件数の正本は `catalog-src-inventory.test.ts` の期待値）。テストIDは `IT-UNIT-<ID断片>-NNN`／`IT-MEM-<ID断片>-NNN`（定義IDから `UNIT_`／`MEM_` 接頭辞を落とし、アンダースコアをハイフンへ。`NNN`は数字のみ）。一意性は `UT-TRACEABILITY-005` に自動的に乗る。
- **`-001` は振る舞い表**。`(SKL_ID, intent, 前提盤面, 期待する振る舞い)` を `it.each` で駆動する（ハーネスは `src/testing/production-unit/skill-behaviour.ts` の `observeSkillUse`）。AS/EXは `selectAsCandidate`／`isExUsable`→`resolveSkillUse`、PSは `PassiveActivationRuntime` を実際に通す。**`activationCondition` は行動選択層が評価する**ため、`resolveSkillUse` を直接呼ぶだけでは発動可否を見られない。
- 表が持つべき必須観点（「必要なテスト種別」の発動条件・連鎖・リソース・期間に対応）:
  1. **発動** — 成立と不成立の両方を行として持つ。
  2. **対象** — production の `targetBindings`/`filters`/`order`/`area` を実際に通し、当たる相手と当たらない相手を固定する。
  3. **分岐選択** — `BRANCH`/`RANDOM_BRANCH` の**全腕**について、その腕が選ばれる前提を盤面で作る。
  4. **結果と宣言** — 実行済みEffectActionの列と対象（`actions`）・HP変動・効果付与/解除・マーカー・リソース収支・クールタイム。付与効果の期間・消費条件は `AppliedEffect.duration.definition` から観測へ載るため、定義を別途 `toMatchObject` する必要はない。1回の使用では出ない payload 宣言（`stacking.max` 等）だけを行の任意欄で補う。
- 変化しなかった観測項目はキーごと落ちるため、`toEqual` の完全一致が「宣言した振る舞いが起きること」と「余計なことを起こさないこと」を同時に固定する。
- **`intent` 欄は原文の該当句を書く**。`raw/` は `.gitignore` 対象で CI に存在せず、原文と定義を突き合わせるテストはリポジトリに1件も無い。転記が正しいかをレビューできる接点はこの欄だけである（設計書が要求する authoring Markdown 層は未実装）。
- **`-002`** は表のスキル列が `UnitDefinition` の宣言と完全一致すること。**`-003` は実行ベース網羅監査** — `UT-AUDIT-UNITCOV-001` は「IDが文字列として書かれているか」しか見ないため、表に載っているだけで一度も実行されない定義を見逃す。定義から到達可能なEffectActionの閉包と、表を回して実際に実行された集合を突き合わせる。**集合へ入れるのは `EffectActionCompleted` の `resultKind` が `APPLIED` のものだけ**にする（`SKIPPED`/`MISSED`/`REJECTED`/`INTERRUPTED` は効果が一度も発現していないため、数えるとその定義やresolverが壊れていても監査を通してしまう）。前提状態を要する定義（`REMOVE_EFFECTS` 等）は、行の `precedingActions` で**実 production 定義を使って**前提を作る。ただし前提アクションはスキルの対象選択・分岐・発動条件を通さずEffectAction 1件を直接撃つものなので、**その実行を網羅の実績には数えない**（数えると「スキル使用単位で保証する」方針そのものを迂回できる）。到達不能な定義は理由付きの許可リストで除外する。
- **`-004` 以降**は1回のスキル使用で表現できない機構（PS連鎖・EX分配の等分と端数・回復リンクの転送・StateDelta の独立Reducer復元など）。
- 相手役は実Catalogのユニットではなく最小定義（`testUnitDefinition`）を使い、相手側のPS・特性が観測へ混ざらないようにする。

##### Memory 側の標準形

Memory はスキル使用を持たず、`triggeredEffects` が契機イベントから対象群へ EffectAction を配るだけなので、単位は「スキル使用1回」ではなく**契機1回**になる。`-001` は `MEMORY_SLOTS`（行・列・ロール・ユニット種別が互いに相関しない6スロット×両陣営の固定盤面）へ実 `startBattle` を通し、`(EffectAction ID, 当たったスロット, 効果量, sourceSide)` の表と `MemoryTriggered` の発火順を `toEqual` で固定する。`-002` は同じ Memory を相手陣営が宣言したときの鏡像（R-MEM-04 の source side と `side: "ENEMY"` の相対解決）、`-003` は実行ベース網羅監査、`-004` 以降が機構別。

Memory 固有の前提は2つある。

- **所属条件**（`AFFILIATION` TargetFilter）は静的 Catalog の `UnitDefinition.metadata.affiliations` を引くため、既定の「所属なし」6スロットのままでは対象0件になり効果が一度も発現しない。`AFF_*` は Memory ごとに異なり全所属を常設できないので、`MemoryBoardOverrides.affiliationsBySlot` で**そのMemoryのメンバーを1スロットだけ**にし、残る5スロットをそのまま非対象の検証に使う。`-004` は所属メンバーが盤面に1体もいない編成を作り、対象0件の `triggeredEffect` が `MemoryTriggered` 自体を発行しないこと（`08_ドメインイベント.md`「発動直前の再確認」）を境界として持つ。**属性条件**（`ATTRIBUTE` TargetFilter）も同じ扱いで、こちらは `UnitDefinition` ではなく編成時に決まる `BattleUnit.attribute` を読むため `MemoryBoardOverrides.attributesBySlot` で宣言する（盤面全体を実属性へ寄せると属性相性倍率が全ダメージ観測へ混ざるため opt-in）。
- **`TurnStarted` 発動**は `observeMemoryTurnStarts` が実 `advanceBattle` を回して観測する。ただし観測は**ターン開始の解決スコープへ閉じる** — `advanceBattle` は同じ呼び出しの中で行動フェーズまで進めるため、最終的なユニット状態では被弾で消費された効果（`consumption: NEXT_INCOMING_ATTACK`）が既に消えており「ターン開始時に何が配られたか」を表せない。`TurnStarted` イベント自身の `resolutionScopeId` に属する `EffectApplied` だけを拾って、配られた事実を行動フェーズの結果から切り離す。積み上がりのように最終状態で見るべき性質は、同じ観測が返す `battle` を使う。

この標準形は、原文（`intent` 欄）・Catalog定義・実挙動の三者を突き合わせることで実データとの不一致を検出する。検出済みの不一致はすべてCatalogリビジョンまたはDomain修正で解消済みで、現在も残る近似は次の2件である。

- `SKL_LAURA_MOUNTAIN_PS1` の「このスキルに続く自身の攻撃での攻撃力を最高7%上昇させる」は、同じPSが確率で撃つ隣接攻撃（`ACT_LAURA_MOUNTAIN_PS1_ADJACENT_DAMAGE`）に `NEXT_OUTGOING_ATTACK` の消費点を取られる近似が残る。消費点をASへ寄せるには隣接攻撃をAS側の追加stepとして表す構造変更が要る。`IT-UNIT-LAURA-MOUNTAIN-001` が現状の振る舞いを固定する。
- `SKL_JULIE_SNOW_PS2` の対象は「攻撃した敵単体」だが、`TRIGGER_TARGET` selector は `count` を取れないため（`SELECT` 専用）、**攻撃した敵全員**へ解決する近似が残る。単体へ絞る表現は selector 語彙の拡張を要する。

混乱（`R-CFS-01`）の陣営反転が `BINDING_DERIVED` の `base` binding へ再帰的に及ぶ規則は、`07_戦闘ルール詳細.md` の R-CFS-01 が正本である（証跡は `UT-R-CFS-01-009`／`010` と `IT-UNIT-OLGA-VETERAN-005`）。

#### `IT-CAP-*` の retire 基準

機能軸（`IT-CAP-*`）は全ファイルの移送を終えて廃止済みである（Issue #379）。移送時に適用した基準は次のとおりで、上記の移送先判断とあわせて、同種のテストを整理する際の規約として残す。

1. retire対象が検証するproduction定義すべてが、ユニット効果軸のテストで**同等以上のアサーション**を持つこと。
2. `rule-coverage.ts` に残る参照は代替ID（`IT-UNIT-*` 等）へ差し替えてから削除する（漏れは `UT-TRACEABILITY-005` が検出する）。台帳の照合器は静的テーブルを持たない `it.each` を実行対象と見なさないため、ユニット側の `-001` 振る舞い表は参照先にできず、参照先は `-004` 以降の plain `it`（Memory は plain `it` の `-001` も可）にする。
3. どの単一定義にも帰属しない機構は、**関係する全ユニットのファイルへ複製して移送する**（重複を受け入れる）。恒久残置は認めない。

なお `SCN-BTL-*`（シナリオ層）は従来どおり production 定義IDを参照してはならない。

対象が保持する効果を照会する条件（`TARGET_HAS_EFFECT`／`HAS_STATUS`）のテストは、条件evaluatorが**評価時点の最新`BattleUnit`だけ**を読む契約を固定するため、次を必ず含める: 成立・不成立に加えて、(1) 絞り込み（`continuousDamageKinds`／`statKinds`）が別種別・別statへ一致しないこと、(2) 複数対象が混在する集合で対象ごとに判定が分かれること、(3) 直前に効果が解除・失効した対象では成立しなくなること、(4) step全体スコープ（BRANCH）で対象が0体なら不成立・2体以上なら例外になること。

## 決定的なテスト

### SequenceRandomSource

テスト用 `RandomSource` は、指定した値を順に返す。

```text
SequenceRandomSource {
  values: number[]
  consumedValues: number[]
}
```

規則：

- 値はDomainのRandomSource契約範囲内とする。
- 値が不足した場合は即時にテストを失敗させる。
- 余った値も原則としてテスト失敗にし、想定外に乱数消費が減ったことを検出する。
- 呼び出し回数と順序をassertできるようにする。
- 値不足時にランタイム乱数へfallbackしない。

確率境界では「判定値が閾値の直前」「閾値と同値」「直後」をテーブル化する。会心率ステータスが0未満または100超でも、判定時の実効値だけが0～100へ補正されることを確認する。

### ID生成器

`BattleId`、`ActionId`、`SkillUseId`、`EffectInstanceId` などを予測可能に生成するテスト実装を使用する。

```text
battle-1
action-1
skill-use-1
effect-1
```

ID文字列そのものを検証目的にしないテストでは、IDの一意性と参照整合性だけをassertする。

### Clockと期限

実時間のsleepで期限テストを行わない。手動で進められるClockまたは期限判定fakeを使用する。

- 期限直前は継続する。
- 期限到達で `EXECUTION_TIMEOUT` になる。
- タイムアウトを `TURN_LIMIT_REACHED` へ変換しない。
- HTTPの強制キャンセルはWorker結合テストで別に扱う。

## テストデータ設計

### Builder

次のBuilderを用意する。

- `UnitDefinitionBuilder`
- `SkillDefinitionBuilder`
- `EffectDefinitionBuilder`
- `MemoryDefinitionBuilder`
- `FormationInputBuilder`
- `BattleScenarioBuilder`
- `CatalogBuilder`

Builderの既定値は「最小で妥当、特殊効果なし」とし、テスト対象以外の要因を減らす。ただし重要な既定値を隠さないよう、生成結果を読みやすいfixture名で表す。

例：

```text
unit({ hp: 1000, attack: 200, defense: 100, actionSpeed: 50 })
activeSkill({ apCost: 1, effects: [physicalDamage({ power: 100 })] })
```

Builder・harness の実装は `testing/scenario/` にある — 合成 Catalog 用の `CatalogBuilder`／定義Builder（`unitDefinition`・`attackSkill`・`damageEffectAction`・`exSkillDefinition`・`formationSlot`・`battleCommand`）と、`runScenario` harness（実 Formation／Battle／Observation を通し、HTTP／Worker を通さない）＋不変条件アサーション（`assertBattleInvariants` 等）。harness ベースのシナリオは `__tests__/scenario/battle-scenarios.test.ts` へ集約する。既存の散在する `SCN-BTL-*`（下位 Battle 直接構築を含む）の全面移行は、回帰リスクを避けるため段階的フォローアップとする。

### テストCatalog

用途別に分ける。

| Catalog            | 用途                                   |
| ------------------ | -------------------------------------- |
| `minimal`          | 1対1の最小戦闘と単体シナリオ           |
| `scenarios`        | PS、チャージ、状態異常など複合シナリオ |
| `invalid`          | 参照切れ、重複ID、不正期間             |
| production Catalog | 実データ全体の構造・参照検証           |

ドメインルールテストをproduction Catalogの具体的なユニットへ依存させない。production定義の変更でルールテストの意図が変わることを防ぐ。

### 数値fixture

- 整数化前の端数が分かる値を使う。
- 0、1、最大値、最大値直前・直後を明示する。
- 浮動小数の途中値は必要に応じて許容誤差で比較する。
- 最終ダメージ、HP、AP、PP、EX、期間など整数値は完全一致で比較する。
- テスト期待値へproductionの計算関数を呼び出さない。

期待値の式をテストへ実装コードと同じ形で複製しすぎない。代表的な手計算例と、別形式の不変条件テストを組み合わせる。

## Domain Unitテスト

### 値オブジェクト

- 境界内の生成成功
- 境界外の生成失敗
- 等価性
- 不変性
- JSONやprimitiveへの変換境界

### 比較・選択ポリシー

行動順、PS順、ターゲット順は比較キーごとに独立したテーブルテストを作る。

```text
行動速度 desc

→ 前列 before 後列
→ column asc
```

同じ入力集合を並べ替えても結果順が同じになることをPropertyテストで確認する。入力配列順を暗黙のtie-breakerにしない。

### 計算サービス

- 各補正を一つずつ変えた例
- 複数補正を組み合わせた例
- 途中計算を丸めない例
- 最終値だけ切り捨てる例
- 最低値・上限値を適用する例
- 適用対象外の補正が混ざらない例

## PS連鎖テスト

PSは循環と順序の不具合が起きやすいため、専用のテスト群を持つ。

### 候補順

- 行動速度が異なる所有者
- 同速の味方と敵
- 同陣営同速の前列・後列
- 同じ列条件で絶対左列
- 同じユニットの複数PS定義順
- 先制攻撃候補を通常候補より優先し、先制攻撃同士へ全tie-breakerを適用すること
- 同時発動制限による1件選択

### 再確認

候補検出後、先行PSによって次を変化させる。

- 所有者が戦闘不能になる。
- PP不足になる。
- クールタイムが設定される。
- 発動条件が不成立になる。
- チャージ状態になる。

発動直前確認で候補が除外され、適切な診断理由を観測できることを確認する。

### RuntimeCounter条件（M6最小範囲・SkillRuntimeスコープ）

`R-EFF-11`のうち`SkillRuntime`スコープをM6で検証する。`Battle`／`BattleUnit`スコープは利用するproduction定義が存在しないためFeature Complete必須対象に含めず、Catalogロード時点で明示的に拒否する。`AppliedEffect`スコープは下記「RuntimeCounter条件（EFF-005・AppliedEffectスコープ）」で検証する。

- N回ごと発動（`modulo`）の直前・一致・次周期境界（Issue #143）
- 累計ダメージ閾値の直前・一致・超過、1回の被ダメージで複数閾値を超える場合、端数繰越（Issue #143）
- Counter更新イベントとPS候補検出の順序（Counter更新 → 候補抽出）。`RuntimeCounterChanged`のsequenceが原因イベントより大きく、かつ原因イベント自身の候補抽出より前に発行されること（[08\_ドメインイベント.md](./08_ドメインイベント.md)「複合処理と状態差分の所有」の例外）。`RuntimeCounterChanged`がcounterの`stateDelta`を単独で所有し、原因イベント自身の`stateDelta`にcounter変化を含まないこと
- `SkillRuntime`スコープ（`resetScope: RESOLUTION_SCOPE`）の`RuntimeCounterReset`が`RuntimeCounterChanged`のpre-matching例外に含まれず、PS/Memory候補スタック全体が空になった後（解決スコープ終了時）にのみ発行され、そのスコープの`rootEventId`を`parentEventId`とすること。reset分の`stateDelta`を単独で所有すること（`EffectSequence`スコープのResetは当該EffectSequence完了境界で外側の候補スタックの状態を問わず発行される — 下記「RuntimeCounter条件（EFF-006・EffectSequenceスコープ）」と`08_ドメインイベント.md`の分類表参照）
- `TriggerDefinition.eventType: RuntimeCounterChanged`／`RuntimeCounterReset`を持つPS/MemoryがCatalog検証を通過し、それぞれの発行直後に候補化（抽出）されること。解決時機は解決コンテキストに従う（`R-ATM-01`、`08_ドメインイベント.md`「イベント発行と処理」手順5）: 即時解決コンテキスト（スキル効果処理の外）では原因イベント自身の候補抽出より先に`RuntimeCounterChanged`由来の候補が解決を終えること、保留コンテキスト（効果処理中）では`RuntimeCounterChanged`由来の候補が保留キュー内で原因イベント由来の候補より前に並び、発動は効果処理完了後の後段フェーズで行われること。`RuntimeCounterReset`の解決時機はスコープで異なること — `SkillRuntime`スコープ（`resetScope: RESOLUTION_SCOPE`）は解決スコープ終了時（スキル効果処理の外）に発行されるため即時解決であり、由来の新規候補が生じた場合に解決スコープの終了を遅延する。`EffectSequence`スコープ（EFF-006）は当該EffectSequenceの完了境界で発行されるため、候補は検出のみ行われ、完了イベント（`PassiveResolved`等）発行後の後段フェーズで発動する（`R-ATM-02`、`08_ドメインイベント.md`「RuntimeCounterイベント」の分類表）
- `RuntimeCounterReset`が、counterを破棄し`stateVersion`を進めた後に発行されること（FACTイベントは状態変更確定後に発行する一般規則どおりで、`RuntimeCounterChanged`のpre-matching例外とは順序が異なること）。`SkillRuntime`スコープでは、`RuntimeCounterReset`由来の候補解決が同じスコープへcounterを再生成・更新した場合、そのcounterが残らなくなるまで破棄・発行・候補解決を繰り返してから解決スコープを終了すること（`EffectSequence`スコープは解決完了で必ず破棄され、この再生成ループを持たない）

Issue #143実装メモ: 上記のうち`modulo`境界・累計ダメージ閾値の直前/一致/超過・複数閾値/端数繰越・Counter更新→候補抽出の順序（`RuntimeCounterChanged`のpre-matching例外含む）はUnit/Scenarioテスト（`runtime-counter-state.test.ts`／`runtime-counter-matcher.test.ts`／`trigger-condition-evaluator.test.ts`／`passive-activation-service.test.ts`のUT-R-EFF-11-001）で検証済み。`value`不変でも`carry`が変化した更新は`RuntimeCounterChanged`を発行する（`runtime-counter-matcher.test.ts`のUT-RCOUNTER-M-006）。

対象12行はいずれも戦闘終了までcounterを保持する設計（`resetScope`省略）だが、`resetScope: RESOLUTION_SCOPE`自体は実装・配線済み。`RuntimeCounterReset`のイベント種別・payload・`StateDelta`復元（`state-delta-reducer.test.ts`のUT-STATE-REDUCER-021〜026、`after: undefined`によるキー削除を含む）、pure関数（`resetRuntimeCounter`）に加え、「解決スコープ終了時にリセットする」呼び出し元（`PassiveActivationRuntime.finalizeResolutionScope`、discard→発行→候補解決の反復ループ）を`battle.ts`（TurnStarted）／`action-skill-use-resolver.ts`（AS/EX）／`action-charge-resolver.ts`（チャージ解放）の3つの解決スコープ終了処理全てへ配線し、`ActionCompleting`／Cooldown更新／`ActionCompleted`の発行後（`06_戦闘状態遷移.md`のCOMPLETING順序どおり）に呼び出すことを`passive-activation-service.test.ts`のUT-R-EFF-11-002で検証した。自身の`RuntimeCounterReset`を再生契機にする誤ったCatalog定義に対する反復回数上限は、UT-R-EFF-11-003（`finalizeResolutionScope`が決定的なエラーで停止すること）で検証した。`Battle`／`BattleUnit`スコープは利用するproduction Catalog定義が現れるまでCatalogロード時に拒否する（`UT-CAT-RCU-011`）。

### ネスト

```text
元イベント
├─ PS-A候補
├─ PS-C候補
└─ PS-A発動
   ├─ 効果処理（子イベント → PS-B候補を検出し保留）
```

イベントの `sequence`、`parentEventId`、`rootEventId`、候補スタック順を検証する。同じ解決スコープでPS-Aを再候補化しても2回目は発動しない。

## 効果期間テスト

### 行動単位

- 付与された当該行動終了では減らない。
- 他ユニットの行動では減らない。
- 対象自身の次回行動終了で1減る。
- 残1から0になった直後に失効する。
- 待機も対象自身の行動終了として減算し、戦闘不能で予約を除去されて行動しなかった場合は減算しない。
- 同じ種別の複数インスタンスが別々の残回数を持つ。

### ターン単位

- 付与ターン終了では減らない。
- 次のターン終了から1減る。
- 残1から0になった直後に失効する。
- 同時に複数失効した場合のイベント順が決定的である。

### 重複なし

- 効果量が異なる複数インスタンスを保持する。
- 最大効果だけ `isEffective` になる。
- 最大効果失効後、次点が同じ終了処理内で有効になる。
- `EffectExpired` → `EffectiveEffectChanged` → `CombatStatChanged` の相対順を確認する。各イベントから誘発されたPSイベントの割り込みは許容し、隣接だけを要求しない。

### リソース獲得量Modifier（M7）

`RuntimeCounter`の`AppliedEffect`／`EffectSequence`スコープと同じM7効果期間モデルで検証する（`M7-002`／Issue #185）。

- EX獲得量+50%/-50%の単体テスト。
- 複数Modifier（増加と減少、同値効果）の重複／非重複合成。
- 行動単位Durationの適用開始・減算・失効境界。
- 基礎量確定 → Modifier適用 → capacity打ち止め → イベント発行、の順序。`ResourceChanged.baseDelta`（基礎量）と`delta`（Modifier適用後・capacity適用後の最終量）が両方とも観測できること。Modifier不在かつcapacity打ち止めなしの場合だけ両者が一致し、capacity打ち止めのみが発生する場合（Modifier不在）でも一致しないこと。
- capacity超過時のModifier適用後の破棄量と`ExtraGaugeOverflowDiscarded`payload（要求増加量がModifier適用後・capacity適用前の量と一致すること）。
- EffectActionを経由しない`EX_GAIN`（AP/PP消費起因）でも`baseDelta`/`delta`が観測できること。
- EXゲージが既に上限で正の`baseDelta`が全量破棄され`delta`が0になる境界。この場合`ResourceChanged`は発行されないが、`ExtraGaugeOverflowDiscarded`が`delta`が0でも発行され、payloadの`baseDelta`から基礎量を復元できること。

## イベントと状態差分

### イベント不変条件

- `sequence` が重複せず昇順である。
- 子イベントのsequenceが親より大きい。
- 同じ解決スコープでrootが一致する。
- 同じ行動・スキル解決でIDが一致する。
- 状態変更を所有するイベントが一つだけである。
- 内訳イベントに同じ差分を重複させない。
- TIMINGイベント後に親処理の前提を再検証する。
- `DETAILED` は全イベントと全状態差分、`finalState` を返す。
- `SUMMARY` は `events`・`stateTransitions` を空にし `finalState` を省略する一方、`result`・`initialState`・`unitSummaries`（演習は `breaks` も）を完全に返す。
- ログレベルを下げてもAssemblerの状態復元検証は緩まない。`SUMMARY` 実行でも、復元できない `finalState` は `INTERNAL_INVARIANT_VIOLATION` として拒否される。
- 廃止済みの `DIAGNOSTIC` の指定は `422 INVALID_COMMAND`（`path: /options/logLevel`）で拒否される。

### ユニット別集計

`unitSummaries`（`10_API設計.md`「UnitBattleSummaryResponse」）は公開レベルの間引き**前**イベントから投影する。投影位置を誤って間引き後へ置くと `SUMMARY` で値が警告なく0になるため、次を固定する。

- 全ログレベル（`SUMMARY` / `DETAILED`）で `unitSummaries` が存在し、同じ値になる。
- HPへ向かった量（`hitPointDamage + discardedDamage`）を計上する。クランプで破棄された超過分（撃破時のオーバーキル、演習でブレイクを保留中（HP0）の敵へ命中したヒットの全量、致死耐えで適用されなかった分）は含め、シールド・サブユニット吸収分は含めない。
- 継続ダメージ（`ContinuousDamageApplied`）を攻撃ダメージと合算する。`sourceUnitId` を持たないMemory由来の継続ダメージは被ダメージにだけ計上する。
- 回復リンクの転送分（`HealingTransferred`）を回復者へ計上する。

合成イベント列を入力にできる純関数として実装し、Memory由来の継続ダメージのように現productionカタログへ存在しない経路も型どおり検証する。

### 独立した差分Reducer

テスト用に `StateTransitionResponse` を適用する小さなReducerを作る。productionのBattleObservationやResultAssemblerをそのまま呼び出さない。同じ不具合を期待値側でも再現することを防ぐ。

確認内容：

1. 初期 `stateVersion` が0。
2. 各差分でversionが1ずつ進む。
3. 前後versionが連続する。
4. `causedBySequence` が正規の内部イベント列に存在する主イベントを参照する。公開レベルでそのイベントが省略されることは許容する。
5. イベントの `stateTransitionIndex` が対応差分を指す。
6. 全差分適用後に最終状態と深い等価になる。
7. 差分を一件抜く、逆順にする、重複させると検証が失敗する。

### Snapshotの使用範囲

Snapshotを許容する対象：

- OpenAPI文書
- 小さく安定したイベント列の補助確認
- エラーレスポンスの代表例

Snapshotだけにしない対象：

- ダメージ計算
- 勝敗
- リソース消費
- PS順序
- 効果期間
- 状態差分復元

Snapshot更新時は仕様変更と単なる出力変化をレビューで区別する。

#### 実装（REL-004 / Issue #203）

3.0.3適合は、生成文書のSchema Objectが仕様「Schema Object」の採用keyword部分集合に収まっているかを走査して確かめる（`testing/openapi/openapi-303-conformance.ts`）。後発のJSON Schema（`const`・`prefixItems`など、OpenAPI 3.1系）が混ざると厳格なclient generatorが落ちるため、`openapi: "3.0.3"`と宣言している以上ここを固定する。走査器自体が素通りしないことは`API-OPENAPI-021`が既知の不適合入力で確かめる。

互換性検査は、凍結した`apps/api/openapi/v1-baseline.json`と生成文書を比較し、`10_API設計.md`「バージョニング」が破壊的と定めるものだけを失敗させる（`testing/openapi/openapi-breaking-change.ts`）。後方互換な追加（任意プロパティ・新イベント種別・新エラーコード・新列挙値）は通るので、追加のたびのbaseline更新は要らない。文書全体のsnapshot比較にしないのはこのためで、毎回更新を強いると「意図的な追加」と「うっかりの破壊」がレビューで区別できなくなる。

比較は`paths`と`components.schemas`の両方を見る。`$ref`は解決せず（自己参照する`ConditionDefinition`で無限再帰になる）、参照先の中身はcomponentsを名前どうしで突き合わせ、`paths`側では参照先の名前が変わっていないかだけを見る。

`oneOf`のvariantは配列indexではなく判別子（`type`／`kind`の単一値`enum`）で対応付ける。判別子は一意とは限らないため（`ConditionDefinition`の`kind=TARGET_STATE`は`field`と`value`の型の組み合わせごとに複数variantある）、同じ判別子のグループ内ではまず内容が完全に一致するものを消し込み、残りだけを出現順で対応付ける。indexや出現順だけで対応付けると、variantが1つ挿入されただけで以降が全部ずれ、後方互換な追加を大量の破壊的変更として誤報する。

レスポンス側の`required`縮小（プロパティは残す）は失敗させない。「バージョニング」がこれを条件付き（「緩めた後も従来から公開されていた変種では常に存在することを併せて示す」）でしか後方互換と認めておらず、その条件は文書だけからは判定できないため、緩和する側が設計書へ根拠を書く責任を負う。

baselineの更新は意図的な操作として扱う。`apps/api/scripts/write-openapi-baseline.mjs`で再生成し（スクリプトがPrettierを通すので`format:check`は追加操作なしで通る）、その差分をレビュー対象にする（本節「Snapshotの使用範囲」の「仕様変更と単なる出力変化をレビューで区別する」と同じ扱い）。

## Worker・インフラテスト

### Worker境界

- DTOと結果が構造化クローンできる。
- HTTPオブジェクトやDomain Entityを渡さない。
- コンパイル済みESMワーカーをproductionと同じパスで起動できる。
- ワーカーごとにCatalogを一度だけ読み込む。
- 期待Catalogリビジョン不一致を拒否する。
- 複数リクエストのBattle状態が混ざらない。

### 容量と障害

- `concurrentTasksPerWorker = 1` を維持する。
- Pool満杯を `503 CAPACITY_EXCEEDED` にする。
- 利用者別上限を `429 RATE_LIMIT_EXCEEDED` にする。
- 協調期限を `504 EXECUTION_TIMEOUT` にする。
- クライアント切断で外側のタスクをキャンセルする。
- ワーカー異常終了後にタスクを自動再実行しない。
- 障害ワーカーが補充される。
- Graceful Shutdownの受付停止、待機、強制終了順を守る。

Worker結合テストは共有状態と実時間依存を避け、各テスト専用Poolを生成して必ずcloseする。

### Container・Cloud Run境界

- production containerをLinux amd64向けにbuildできる。
- containerがnon-rootで起動し、注入した `PORT`へ `0.0.0.0`でlistenする。
- image内のCatalog、コンパイル済みWorker、OpenAPIを解決できる。
- SIGTERM受信後8秒以内に受付停止、Pool終了、process終了を完了する。
- Cloud Run設定のminimum 0、maximum 1、concurrency 2、timeout 40秒が宣言値と一致する。
- GitHub ActionsのCloud Run deployが長期service account keyを使用しない。

## End-to-Endテスト

最小限の代表経路に絞る。

1. HTTPから最小Catalogの基本戦闘を完了する。
2. GitHub Pages相当の別originから一覧GETと戦闘POSTを完了する。
3. PS連鎖と状態差分を含む戦闘を完了する。
4. 同一ユニット重複と最大編成人数を受理する。
5. Worker Pool容量不足をHTTP `503` で返す。
6. タイムアウトをHTTP `504` で返す。
7. 初期状態からレスポンス差分を復元して最終状態と一致する。
8. Cloud Run revisionの公開HTTPS URLでlive、ready、Catalog GET、最小simulationを完了する。
9. deployed GitHub Pages originからCloud RunへのCORS preflightと実requestを完了する。
10. 新revisionのsmoke test失敗時に直前の正常revisionへtrafficを戻せる。

End-to-Endでは全ルールを個別に再検証しない。失敗時に原因を切り分けられる小さな下位テストを正本とする。

## Golden battle 回帰層

全 production Unit について、味方・敵に据えた1対1の決定的戦闘を完走させ、基本不変条件と「勝敗・終了理由・公開イベントの要約」の小さな安定 snapshot を固定する（`__tests__/golden/production-unit-golden-battle.test.ts`、実行部は `testing/scenario/run-production-battle.ts`）。新たに追加された Unit は自動的にケースが増える（snapshot 未登録なら失敗する強制関数）。

3つのgolden（unit/party/exercise）はいずれもイベント列を `testing/scenario/event-sequence-fingerprint.ts` の `summarizeEventSequence` へ通し、`eventTypeCounts`（種別ごとの件数。差分の読める回帰検出）と `eventSequenceHash`（種別の集合は同じまま並びだけ変わる**順序**回帰を拾う1行のハッシュ）へ要約してsnapshotへ固定する（Issue #607）。全イベントの type 列をそのまま並べる旧方式は、production Unit が74件（Issue #607時点）まで増えたことで `production-unit-golden-battle.test.ts.snap` が34,949行に達し、DIAGNOSTICカテゴリのイベントを1種類追加しただけで74エントリ全件がchurnして差分の意味が読めなくなっていた——レビュアーが74件×470行を毎回読んで「意図した変化か」を判断する前提はもう成立しない。要約後は3,765行まで縮み、そうした変更はどのUnitの `eventTypeCounts` が増えたかだけが差分に現れる。ハッシュだけが変わった行は要約からは「何が変わったか」が読めないため、`pnpm run dump-golden-event-types -- <unit|party|exercise> ...`（`testing/scenario/dump-golden-event-types-cli.ts`）へsnapshot上の識別フィールド（`unitDefinitionId` / `ally`・`enemy` / `ally`・`enemyUnitDefinitionId`）をそのまま渡すと、そのケースが発行した公開イベントの type 列を発生順に出力する——このデバッグ経路は通常のsnapshotやCIには含めない。

**混成編成戦**（`production-party-golden-battle.test.ts`、`E2E-GOLDEN-PARTY-*`）は「異なる production ユニットの定義同士が同じ盤面で噛み合うか」を担う。1対1ミラー戦は同一ユニットを味方・敵に据えるため、この観点は他のどの層も見ていない（ユニット効果軸は1定義のスコープに閉じている）。N×N を避けるため、全ユニットIDをsortして5体ずつ（編成上限）のpartyへ分割し `party[k]` 対 `party[k+1]` を回す。**全ユニットが味方として1回・敵として1回**、必ず混成編成の中で実戦闘を経験し、ユニット追加時も自動的にケースが増える。行適性（`positionAptitudes`）は配置制限ではなく統計ペナルティ（`R-STA-01`）なので、任意の組み合わせを任意の位置へ置ける。

要約の `eventTypeCounts`・`eventSequenceHash` に加え、8手順のダメージパイプライン内の**順序**は全 production ユニットに対して `IT-AUDIT-M8-001` が既に検査している。混成編成ではミラー戦では起こらないPS連鎖の重なりが実行ガード（`maxEffectsPerScope`）へ届く組み合わせが実在しうる。**完走ケースで例外を成功として飲み込んではならない**（golden の契約は「完走・不変条件」であるため）。ガードへ到達する組み合わせは `E2E-GOLDEN-PARTY-GUARD-*` として明示的な既知テストへ分離し、到達しなくなったら失敗させて一覧の更新を強制する。`REL-005`で上限を50から100へ引き上げた結果、現在この一覧は空である（到達していた1件は暴走ではなく正常な効果解決だった）。

**戦術演習golden**（`production-exercise-golden-battle.test.ts`、`E2E-GOLDEN-TEX-*`）は `EXERCISE_ENEMY` ユニットを担う。ミラー戦・混成編成のgoldenは通常戦闘（`NORMAL`）で `PLAYABLE` ユニットだけを流すため（`allProductionUnitIds` は `R-TEX-11` により `PLAYABLE` へフィルタする）、`EXERCISE_ENEMY` ユニットの定義はこの層でしか実戦闘を経験しない。各演習ユニットを敵に据えた演習（`TACTICAL_EXERCISE`）を、`PLAYABLE` のID昇順先頭5体の固定パーティで完走させ、スコア・ブレイク履歴・イベント型件数をsnapshotへ固定する。演習ユニット追加時も自動的にケースが増える（`E2E-GOLDEN-TEX-000` が全 `EXERCISE_ENEMY` の網羅を強制する）。

**seed再現性**（`seeded-exercise-determinism.test.ts`、`E2E-SEEDDET-*`）は `SeededRandomSourceProvider`（`11_インフラストラクチャ設計.md`「SeededRandomSource」）が実Catalog・実エンジン上で再現性を満たすことを担う。上の3つのgoldenはconstant sourceで完走させるため、乱数値が実際に散る経路を一度も踏まない。ここでは散る乱数列を与えたうえで、同一 `(seed, runIndex)` が同一結果（スコア・ブレイク数・完了ターン・終了理由・イベント件数）を再現することを固定する。等値assertが空振りしていないこと——乱数列が結果を実際に左右すること——は、異なる `runIndex` が異なる結果へ到達することを併せて要求して担保する。

## Load／Soak baseline

Load/Soak レベルの baseline は `__tests__/load/` の4ファイルが分担して持つ。いずれも
**baseline を CI ログへ JSON 出力**し、固定合格閾値はSLO確定まで設けず（「負荷・耐久テスト」の

### 負荷試験で観測を成立させるための約束

測定が「観測できていないまま成功する」ことを防ぐため、次を守る。

- **上限の必要量は全編成から採る。** ミラー編成1つだけを二分探索すると必要量は40件と出るが、混成編成を含めた29編成では54件になる。1編成の測定値を運用値の根拠にしてはならない。
- **並行度・レイテンシは実 `listen()` ＋実 `fetch` で測る。** `app.inject()`（light-my-request）は実ソケットを介さないため、同時投入した request が Pool へ到達する時刻が実HTTPどおりに重ならない。
- **Pool飽和は HTTP ではなく `pool.execute` へ直接投げて作る。** 負荷生成側がサーバーと同じイベントループを共有する in-process 測定では、実 `fetch` で16並行投げても Worker 1本・待機1枠を飽和させられない（実測: 128件すべて成功）。`build-server.ts` は `pool.execute` の失敗をHTTP statusへ写す薄い層なので、容量の測定はこの境界で行う。
- **切断は、サーバーが `execute()` へ入ったことをlatchで確認してから起こす。** `fetch()` 直後に同期 `abort()` すると、サーバーへ届く前にクライアント側だけで取り消され、Poolが健全なのは当然になる。**サーバー側 cancellation signal の中断**まで観測する。
- **shutdownは、Worker内でタスクが実行中かつ未完了であることを確認してから開始する。** `execute()` 入口のlatch＋固定sleepでは、その間に戦闘が終わっていた可能性を排除できない（実測の `shutdownMs` は1.5msで、待った形跡が無かった）。`__fixtures__/deterministic-battle-worker.ts` はタスク開始をファイルで通知し解放まで待つlatchを持つので、これで「実行中・未完了」を直接観測してから `shutdown()` を呼ぶ。`close({force:true})` は未開始タスクを即座に reject するため、当該タスクが完走することが「実行中タスクを待った」ことの証明になる。
- **最大応答は乱数を固定して再現する。** production Worker の `SystemRandomSourceFactory` のままでは決着ターンが試行ごとに変わり、既知の最悪ケース（24.1 MB）を実経路へ流せない（同じ編成でも1.2 MB程度にしかならない）。同じfixture worker が RandomSource だけを定数へ差し替えるので、Worker境界・構造化クローン・HTTP直列化は production のまま最悪ケースを通せる。
- **乱数に依存する事象は期限の値で確定させる。** production Worker は `SystemRandomSourceFactory` を使うため決着ターンが試行ごとに変わり、`SIMULATION_TIMEOUT_MS=1` でも1ms未満で完走する試行が混ざる（実測: 5対5でも10回中2回）。タイムアウトの連続は `INT-WORKER-005` と同じく既に過ぎた期限を渡して確定させる。
- **メモリーは専用ファイルで測る。** Vitest は**ファイル単位**で別プロセスへ隔離する。同じプロセスで先に大量の in-process 戦闘を回すと、その残骸で RSS の絶対値が数百MB膨らみ（実測: 573 MB）、「1 GiB に収まるか」の判断材料にならない。

測定結果から確定した運用値は `docs/運用手順.md`「Cloud Run配備構成」が正本。
