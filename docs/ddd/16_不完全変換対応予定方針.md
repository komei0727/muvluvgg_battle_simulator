# 不完全変換対応予定方針

## 目的

`15_Unit_Memory変換台帳.md` の不完全変換一覧に、各項目をいつ・どの機能領域で解消するかを追跡できる情報を追加する。

不完全変換は、発見されたIssueや変換バッチ単位ではなく、解消可能になる最初のエンジン縦切りに紐づける。

## 追加する列

不完全変換の詳細表に、次の2列を追加する。

```markdown
| unitDefinitionId | 該当スキル | 変換できなかった内容 | 原因 | 対応予定 | 対応テーマ |
| ---------------- | ---------- | -------------------- | ---- | -------- | ---------- |
```

## 対応予定

`対応予定` には、原則として該当ギャップを解消できる最初のマイルストーンを記載する。

| 対応予定  | 対象                                                                                                                                                       |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `M2-DATA` | 所属条件、配置・属性・基礎ステータスなど、M2の開始状態生成に直接関わるデータ不備                                                                           |
| `M5`      | AP/EX消費、クールタイム開始・短縮・リセット、チャージ開始/解除など、行動ライフサイクルそのもの                                                             |
| `M6`      | PS発動条件、イベント照合、PP消費、PS発動回数、N回ごと発動、同時発動制限、発動除外条件                                                                      |
| `M7`      | 効果インスタンス、期間、重複、解除、状態異常、効果無効、ステータス再計算、高度ターゲット、Memory triggeredEffects、バフ/デバフ判定、リソース獲得量Modifier |
| `M8`      | ダメージpipeline、会心後分岐、防御貫通、シールド、サブユニット、リンク、反射、継続ダメージ、毒、HP割合スケール                                             |
| `M9`      | production Catalog 全体の最終承認、未実装Capability拒否の総点検                                                                                            |

`M6`のPS発動条件には、発動回数・N回ごと・累計ダメージ閾値を判定するための最小`RuntimeCounter`（`SkillRuntime`スコープ）を含む。`Battle`／`BattleUnit`スコープは当初M6の対象としていたが、利用するproduction Catalog定義が現れるまでFeature Complete必須対象に含めず、Catalogロード時点で明示的に拒否する契約とした（レビュー再レビュー[P2]、Issue #143）。必要な定義を追加する際は、そのproduction経路と同じTaskで実装・検証する。`AppliedEffect`スコープの`RuntimeCounter`（効果インスタンス自身に所有される汎用Counter管理）は`M7`のEFF-005（Issue #162）で実装した — `DurationDefinition.counterUpdates`（`APPLIED_EFFECT`スコープ）と`expiration.conditions`（R-EFF-08）からの参照で構成する。`EffectSequence`スコープの`RuntimeCounter`（`EffectSequence`自身は状態を持たない汎用Counter管理）は`M7`のEFF-006（Issue #212）で実装した — `EffectSequence.counterUpdates`（`EFFECT_SEQUENCE`スコープ）が更新契機を宣言し、実行時識別子には既存の`SkillUseId`を再利用する。`MarkerState`（consumption/expiration機構が別途未実装）はCatalogロード時点で`counterUpdates`／`RuntimeCounter`スコープを明示的に拒否する。いずれも同じ`RuntimeCounter`モデルの異なるスコープであり、モデル自体の追加マイルストーンではない。詳細は [`05_ドメインモデル.md`](./05_ドメインモデル.md)「RuntimeCounter」と [`13_実装計画.md`](./13_実装計画.md)「M6 PSイベントエンジン」を参照。

Unitスキルの不完全変換は、基本的に `M2` には割り当てない。現状の不完全変換は、M2の基礎Catalog項目には影響しないためである。

`TARGET_STATE_QUERY_BUFF_DEBUFF` 以降の16テーマは、Issue #54 の最終レビューで `15_Unit_Memory変換台帳.md` 全113行に本方針を適用した際、既存23テーマ（`TARGET_EXCLUDE_RESOLVED_UNIT`〜`UNREACHABLE_BRANCH_BY_RAW_DATA`）のいずれでも表現できなかったため追加した。

末尾3テーマは `M7-010`（Issue #177、M7完了監査）が既存テーマの再分類として新設した。「同じ技術的原因のものは同じ `対応テーマ` に寄せる」「複数マイルストーンにまたがる場合はCatalog近似を解除できる最終側のマイルストーンを優先する」という本書の運用ルールを、実装が進んだ後の実態へ適用し直した結果である。

- `TRIGGER_EXCLUSION_TIMING`（3行）と `TRIGGER_PAYLOAD_FILTER`（2行）は、`RESOLUTION_PHASE`（Issue #144）とtrigger payload条件のAPIが揃った時点で、5行すべての残ギャップが「`EffectApplied` のpayloadに分類情報が無く候補検出自体ができない」という単一原因へ収束していた。テーマ名が実際のブロッカーを指さなくなったため `EFFECT_APPLIED_CLASSIFICATION_PAYLOAD` へ統合した（担当 `M7-011` / Issue #265）。この統合先テーマは `M7-011`（Issue #265）が `EffectApplied` payloadへ `effectKind`／`categories` を追加して解消し、5行すべてを台帳から除去した（`17_残作業対応表.json` の `conversionThemeAssignments` からも除去済み。テーマ名自体は履歴として本表に残す）。
- `LINKED_EFFECT_GROUP`（3行）は、EFF-003（Issue #159）の `AppliedEffect` 同士・EFF-004（Issue #160）の `MarkerState` 同士のカスケード実装後も残っていた。うち2行（`UNIT_AOI_ELEGANT`・`UNIT_TARISA_TROUBLEMAKER`）の真のブロッカーは両者をまたぐcross-typeカスケード（当時はCatalogロード時点で `UNSUPPORTED_MARKER_LINKED_GROUP` として拒否されていた）であるため `LINKED_EFFECT_GROUP_CROSS_TYPE`（担当 `M7-013` / Issue #267）へ、残る1行（`UNIT_LILY_SINGER`）は `AppliedEffect` 同士のカスケード自体は実装済みで `APPLY_SHIELD` 本体だけが未実装であるため `M8` の `LINKED_EFFECT_GROUP_SHIELD`（担当 `DMG-004` / Issue #194）へ分けた。

`TARGET_STATE_QUERY_BUFF_DEBUFF`（5行）は `M7-001E`（Issue #248）が `ConditionDefinition.TARGET_HAS_EFFECT`（`CAP_TARGET_EFFECT_QUERY`）と `TARGET_STATE` の `HAS_STATUS`/`UNIT_TYPE`/`ROLE` 評価（`CAP_TARGET_STATE_EXTENDED_FIELD`）を実装して解消し、5行すべてを台帳から除去した（`17_残作業対応表.json` の `conversionThemeAssignments` からも除去済み）。分類軸は `REMOVE_EFFECTS`/`EFFECT_IMMUNITY` と同じ `effect-category-classifier.ts` を正本とし、毒・炎上は `continuousDamageKinds`、「対象の**攻撃力**がデバフ」は `statKinds` で絞り込むことで、いずれの行も「何らかのデバフ」への近似を残さずに変換した。

`DYNAMIC_DURATION_ON_REAPPLY`（1行）は `M7-014`（Issue #268）が `DurationDefinition.reapply` を追加して解消し、台帳から除去した（`17_残作業対応表.json` の `conversionThemeAssignments` からも除去済み）。同Issueはその表現契約を `R-EFF-12`「再付与時の動的期間」として新設した — 「既存効果の残存に応じて付与する期間を変える」という契約は、R-EFF-01（期間単位）でもR-STS-02（気絶の再付与規則）でも規定されていなかったためである。

`STACK_LIMIT_ON_STAT_MOD`（1行）は `M7-012`（Issue #266）が `APPLY_STAT_MOD.stacking` へ重複上限 `max` と重複なし `mode: NON_STACKABLE` を追加して解消し、台帳から除去した（`17_残作業対応表.json` の `conversionThemeAssignments` からも除去済み）。表現契約は既存の `R-EFF-05`「重複効果の期間」へ追記した — 重複あり／なしの宣言と同時保持数の上限は、同じルールが規定する「重複」の範囲に収まるためである。同Issueは所有者不在だった `R-EFF-05` 自体も完了させた（`stacking.mode` が `STACKABLE` しか取れず、resolverが `duplicate: true` 固定で付与していたため、最強選択・次点繰上げ・`EffectiveEffectChanged` へ実ライフサイクルから到達できなかった）。

`LINKED_EFFECT_GROUP_CROSS_TYPE`（2行）は `M7-013`（Issue #267）が `AppliedEffect` と `MarkerState` をまたぐカスケード（R-EFF-09第1項）を実装して解消した。`UNIT_TARISA_TROUBLEMAKER` の行は近似が完全に消えたため台帳から除去し、`UNIT_AOI_ELEGANT` の行は「「高揚」は付与者が倒れると同時に解除される」という**別機構**の残余だけが残ったため、新テーマ `MARKER_REMOVAL_ON_SOURCE_DEATH`（担当 `M7-020` / Issue #279）へ再分類した。既存テーマでは表現できないことを確認したうえでの新設である — `LINKED_EFFECT_GROUP` 系のテーマ名はいずれも `linkedEffectGroupId` を共有するメンバー間の連動を指すが、この残余のブロッカーは「Markerを解除する契機（付与者の戦闘不能）を宣言する手段がない」ことであって連動側ではない。同Issueは併せて所有者不在だった `R-EFF-09` 自体も完了させ、`catalog-integrity.ts` の `UNSUPPORTED_MARKER_LINKED_GROUP` を撤去した。

`MARKER_REMOVAL_ON_SOURCE_DEATH`（1行）は `M7-020`（Issue #279）が `DurationDefinition.removeOnSourceDefeated`（`APPLY_MARKER` 専用）を追加して解消し、台帳から除去した（`17_残作業対応表.json` の `conversionThemeAssignments` からも除去済み）。付与者の戦闘不能（`UnitDefeated`）を契機に `MarkerState.sourceId` 一致のMarkerを解除し（`MarkerRemoved`／`reason: SOURCE_DEFEATED`）、子効果はR-EFF-09のcross-typeカスケードがそのまま巻き込む。表現契約は既存の `R-EFF-10`（Marker）へ追記した — 「Markerを解除する契機」はR-EFF-10が規定する範囲であり、R-EFF-09が規定するのは解除**後**の連動側だからである。`expiration.conditions`（R-EFF-08）へ寄せる案は採らなかった: Marker側のexpiration機構自体が未実装（`UNSUPPORTED_MARKER_DURATION`）であり、Condition表現の導入は同機構ごとの実装を巻き込むため、Issueが定めた完了境界（付与者戦闘不能によるMarker解除そのもの）を超える。なお `UNIT_AOI_ELEGANT` の `selectable` 化に要していた `CAP_CONTINUOUS_DAMAGE` は `DMG-008`（Issue #189）が `IMPLEMENTED` にした。

`M9` の `UNREACHABLE_BRANCH_BY_RAW_DATA`（1行）も `M7-010` のレビュー指摘により `conversionThemeAssignments` へ登録した（担当 `REL-003` / Issue #200）。それまで `remaining-work.test.ts` のパーサーが `対応予定` 列の `M7`/`M8` だけを読んでいたため、この行は件数からも割当検証からも黙って外れていた。`M9` は「新規表現力の主担当には原則しない」が、**追跡対象から外してよいという意味ではない** — 到達不能と判断した分岐も、最終承認の時点で判断が維持されているかを確認して初めて台帳から除去する。

## 運用ルール

- `対応予定` は、発見されたIssueではなく、解消可能になる最初のマイルストーンを書く。
- Unitスキルの不完全変換は、原則として `M2` には割り当てない。
- 同じ技術的原因のものは、同じ `対応テーマ` に寄せる。
- 1つの不完全変換に複数原因がある場合は、主要なブロッカーを `対応テーマ` に書く。
- 複数マイルストーンにまたがる場合は、Catalog近似を解除できる最終側のマイルストーンを優先する。
- Capability実装時は、同じ `対応テーマ` の行をまとめて確認する。
- 対応テーマを新設する場合は、既存テーマで表現できないことを確認してから追加する。
- 解消した行は削除せず、必要なら別途「解消済み」扱いに移すか、該当PRで台帳から除去する方針を決める。
- `M9` は最終検証・承認用であり、新規表現力の主担当には原則しない。

`CONTINUOUS_DAMAGE_OR_POISON_ADVANCED`（台帳0行）は `DMG-008`（Issue #189）が解消した。台帳へ行が立っていなかったのは、raw原文が「毒は現在HPの10%」「炎上は攻撃力×30%」のように**そのスキル固有の量**だけを書き、上限・重複2倍・付与時snapshotといった規則を書かないためである（それらは `戦闘システム.md` が状態異常全体に対して定めるグローバル規則であり、`R-DOT-01`〜`R-DOT-04` がその表現契約にあたる）。したがって近似はスキル単位の変換ではなく、Catalogが炎上・毒・固定継続ダメージを区別できないこと自体にあった。`APPLY_CONTINUOUS_DAMAGE.payload.continuousDamageKind`（`FIXED` / `BURN` / `POISON`、省略不可）の追加と、production 24定義への種別付与でこれを解消した。
