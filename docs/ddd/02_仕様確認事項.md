# 仕様決定・保留事項

## 目的

本書は、[戦闘システム.md](./戦闘システム.md) の補足確認によって決まった仕様と、現時点で保留する仕様を一元管理する。

決定内容は、ユビキタス言語、ユースケース、ドメインモデルおよびテストの判断根拠として使用する。原文と本書の決定内容に解釈の差がある場合は、本書に記録された決定内容を採用する。

## 現在の状況

全論点は決定済み。確認待ち・保留は現時点でなし。

状態の意味は次のとおりとする。

- `決定済み`：設計と実装の前提として使用できる。
- `保留`：現時点では仕様を確定せず、未確定の振る舞いを推測して実装しない。
- `確認待ち`：元データをproduction Catalogへ変換する前に、採用方針の回答が必要である。

| Q-TEX-12 | 演習敵の「味方」の解釈         | 演習の敵陣営は単騎であるため、演習敵スキルの「味方」は自身を含むものとして変換する。プレイアブル版が自身を除いていた対象束縛・集計対象（`EXCLUDE_RESOLVED_UNIT SELF`／`targetSelector: OTHER_ALLY`）は演習版では外す。自身以外を優先する対象順（`SELF_LOWEST_PRIORITY`）は「自身を除外」ではないため自身へ解決され、「対象の味方と自身へEXゲージを1加算」は自身へ2加算になる。                                                                                                                                                                                                                                                                                                                                                 |
| Q-TEX-13 | 原文にない効果の扱い           | 演習敵はスクリーンショット原文を唯一の正本とし、プレイアブル版にあってもスクリーンショットに記載のない効果は搭載しない（`UNIT_SHOUKA_BEACH_TEX` のAS1+のダメージリンク解除、PS2+の味方全体へのダメージリンク）。到達不能な `EffectActionDefinition` を残さないため、`effects.json` からも当該定義を除く。                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Q-TEX-14 | 発動制限・表記の転記           | 発動回数の制限はスクリーンショットの「特性」欄と本文の記載だけを根拠とする。プレイアブル版が戦闘中1回だった `UNIT_ANIS_SWEETDEVIL_TEX` のPS3+は記載が無いため制限を持たせず、毎ターン開始時に再発動する（軽減バフは `STACKABLE` のまま追加付与され、各インスタンスが独立に3ヒットを消費する）。スキルの表示名はスクリーンショットの表記に従う（`UNIT_MAO_SUMMER_TEX` のAS2「うっかり大惨事」。プレイアブル版のwiki準拠表記は変更しない）。ただし**ユニットの表示名はプレイアブル版と同じ名**を使う（`UNIT_AOI_GUARDIAN_TEX` 以来の運用）— 演習の敵はゲーム内で「破壊：〇〇」と表示されるが、同一ユニットの演習版であることが `unitDefinitionId` の `_TEX` 接尾辞で区別できるうえ、UIのユニット画像は表示名で突き合わせるため。 |
| Q-TEX-15 | 非表示ステータスの扱い         | スクリーンショットに表示されないステータス（会心ダメージ・属性相性ボーナス）は演習敵の `baseStats` へ書かず省略する（`UNIT_AOI_GUARDIAN_TEX` 以来の運用）。`levelGrowth` も持たせない — 演習敵はLv200固定で、他レベルはR-ENH-05により拒否される。                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Q-TEX-16 | 編成候補の一括評価API          | スコア期待値の比較・最適編成探索をローカル分析ツールで行うため、専用エンドポイント `POST /api/v1/tactical-exercise-evaluations` を追加する。1リクエストで「共通の敵1体 × 味方編成候補K件 × 各n回」を実行し、**統計量は算出せず試行ごとの生値**（`totalScore`／ブレイク回数／完了ターン／終了理由）を配列で返す — どの統計を採るかは利用側が決める。スコアの定義・実行条件はQ-TEX-02/R-TEX-02のまま変えない（実行は単発の演習ユースケースをそのまま呼ぶ）。                                                                                                                                                                                                                                                                     |
| Q-TEX-17 | 一括評価のseedと乱数の共有     | リクエストは任意の `seed` を受け、省略時はサーバーが生成して応答へ載せる（同じ結果を再現できるようにするため）。試行ごとのサブシードは `(seed, runIndex)` だけから導出し、**候補indexを混ぜない** — 候補が違っても同じ `runIndex` は同じ乱数列で評価され（共通乱数法）、候補間比較の分散が下がる。                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Q-TEX-18 | 一括評価の期限と部分結果       | 期限（`SIMULATION_TIMEOUT_MS`）はリクエスト全体に掛ける。試行の途中で期限へ達した場合はエラーにせず、完了済みの試行だけを返し、候補ごとの `completedRuns` で不足を示す — 数百回規模の試行を全部捨てるより、得られた分を返すほうが利用価値が高い。                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Q-TEX-19 | 一括評価の公開制御             | ローカルの分析ツール向けの実行系であるため、`EVALUATION_ENDPOINT_ENABLED`（既定 `false`）で明示的に許可した配備だけで開き、本番Cloud Runでは `false` を明示する。無効な配備でもルート登録自体は行い `404 ENDPOINT_DISABLED` を返す — 公開されるOpenAPI文書の形を配備設定で変えないため。                                                                                                                                                                                                                                                                                                                                                                                                                                       |

### 基本ステータス強化

| ID       | 論点                         | 決定内容                                                                                                                                                                                                                                                                                                                                          |
| -------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Q-ENH-01 | 強化補正の位置づけ           | `baseStats` はレベル200・無強化時点の値とする（Q-CAT-01のMarkdown転記値の意味は変えない）。APIリクエストの強化指定がある場合に限り、学園レベル・タイプ装備・モジュール・ギアカスタム・レベル増加を適用した強化後基本ステータスを算出し、R-STA-01の基本値として使用する。強化指定がないリクエストは従来どおり `baseStats` をそのまま基本値とする。 |
| Q-ENH-02 | 強化指定の単位               | 陣営単位の指定（学園レベル）とユニット単位の指定（現在レベル、ギアカスタム）に分ける。陣営の強化指定があるとき、その陣営の全ユニットが強化計算の対象になる。ユニット単位の指定は陣営の強化指定があるときだけ許可し、陣営指定なしのユニット指定はリクエスト不備として拒否する。味方・敵陣営は独立に指定できる。                                    |
| Q-ENH-03 | 学園レベルの配分規則         | タイプ3系統（物理・EN・敏捷）と属性6系統の計9系統を持つ。各系統はレベル1から開始し、1レベル上がるごとにHP→攻撃力→防御力→HP…のローテーションで1ステータスへ加算する。1回あたりの加算量はタイプ系統がHP+120／攻撃力+90／防御力+50、属性系統がHP+240／攻撃力+180／防御力+100とする。                                                                 |
| Q-ENH-04 | タイプ装備・モジュールの適用 | どちらも全ユニット共通の固定内容とし、強化計算の対象ユニットには常時適用する。個別のON/OFFは設けない。タイプ装備はHP+19320／攻撃力+14340／防御力+7980。モジュールは固定加算HP+3628／攻撃力+2721／防御力+1515と、HP・攻撃力・防御力への割合補正9%を持つ。                                                                                          |
| Q-ENH-05 | ギアカスタムの効果表         | 1ユニット最大9個。各ギアは対象ステータス（7種）、種別（ギアⅡ／ギアⅢ）、ランク（D〜S）を持ち、補正割合は効果表（R-ENH-04）で確定する。ギアⅢ・ランクCの会心ダメージ増加は8.5で確定とする。同一ステータスのギアは重複指定でき、補正割合は単純加算する。                                                                                              |
| Q-ENH-06 | レベル増加の算出             | ユニット定義はレベル1あたりの成長値 `levelGrowth`（HP・攻撃力・防御力・行動速度）を任意フィールドとして持つ。現在レベルLの指定時は `(L − 200) × 成長値` を加算し、L < 200 の負方向も同式で扱う。`levelGrowth` を持たないユニットへ L ≠ 200 を指定した場合はリクエスト不備として拒否する。                                                         |
| Q-ENH-07 | 成長値の仮値                 | 成長値の実測データが存在しないため、仮値（HP・攻撃力・防御力は200レベル値×0.9%を四捨五入した整数、行動速度は2）を `catalog-src` へ明示的に投入し、目視確認で実測値へ順次更新する。仮値は生成スクリプトで注入せず、実データとして保持する。                                                                                                        |
| Q-ENH-08 | 丸めと値域                   | 強化後基本ステータスは途中値・最終値とも丸めず全精度で保持する（R-NUM-01）。算出結果が負になる場合は0へ、最大HPが1未満になる場合は1へ切り上げる。現在レベルと学園レベルは1以上の整数とし、上限を設けない。                                                                                                                                        |

## 管理規則

- 新たな不明点が見つかった場合は、一意な論点IDを付けて「確認待ち事項」または「保留事項」の節を設けて追加する。
- 保留事項が確定した場合は「決定事項」の該当領域へ移動する。
- 決定内容を変更する場合は、ユビキタス言語、ユースケース、境界づけられたコンテキストへの影響を同時に確認する。
- 保留事項に依存する実装では振る舞いを推測せず、仕様確定まで差し替え可能なポリシーまたは未対応として扱う。
- 保留仕様を仮の0%、100%などで実装してはならない。仕様が確定するまでCatalogへ定義を追加しない。
