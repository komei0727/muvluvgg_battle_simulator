# UI要求・画面設計

## 1. 目的

利用者が戦闘条件を設定し、APIへ1回のシミュレーションを依頼し、結果をサマリと詳細データの両方から検証できるUIを提供する。

本UIはゲームプレイ画面ではなく、戦闘ルールとCatalogを検証するデータ分析基盤である。

## 2. 対象利用者

- 戦闘ルールを設計・検証する開発者
- Catalog定義の挙動を確認する担当者
- 実装マイルストーンの受け入れ確認を行うレビュアー

初期版では一般ゲーム利用者向けの説明や演出より、入力と結果の追跡可能性を優先する。

## 3. ユースケース

### `UI-UC-001` 戦闘条件を設定する

1. UIは一覧APIからUnit・Memoryと選択可否を取得する。
2. 利用者は味方と敵のユニットを各陣営1～5体選択する。
3. 各ユニットを前衛または後衛の空き枠へ配置する。
4. 利用可能なメモリーを各陣営0～6件選択する。
5. ターン上限1～99とログレベルを設定する。
6. UIは入力違反を戦闘開始前に表示する。

画面には各陣営6枠を表示するが、APIが受理するユニット数は最大5体である。6枠目まで埋めようとした場合は選択を確定せず、「1陣営に設定できるユニットは5体までです」と表示する。

### `UI-UC-002` 戦闘を実行する

1. 利用者が「戦闘を開始」を押す。
2. UIは入力を再検証し、違反がなければAPI DTOへ変換する。
3. 実行中は重複送信を防ぎ、進行中表示とキャンセル操作を提示する。
4. 成功時は戦闘サマリと詳細データを表示する。
5. 失敗時は入力違反、混雑、タイムアウト、サーバー障害を区別して表示する。

### `UI-UC-003` 戦闘サマリを確認する

成功結果から次を表示する。

- 勝敗
- 終了理由
- 終了ターン / 設定ターン上限
- Battle ID
- Catalog revision
- 各ユニットの与ダメージ、被ダメージ、回復、生存状態

### `UI-UC-004` 詳細データを確認する

利用者は次のタブを切り替えられる。

- 時系列イベント
- 状態遷移
- レスポンスJSON

イベントは機械コードだけでなく日本語の要約を表示する。未知イベントは除外せず、汎用表示へフォールバックする。

### `UI-UC-005` 条件を変更して再実行する

- 「条件を編集」で条件設定領域へ戻れる。
- 前回の条件と結果は、再実行を開始するまで保持する。
- 「再実行」は現在の条件を再送する。乱数を含むため同じ結果になるとは限らない。
- 新しい実行が成功した時点で前回結果を置換する。
- 新しい実行が失敗した場合、前回成功結果は残し、その上にエラーを表示する。

### `UI-UC-006` 戦術演習を実行する

1. 利用者はページ上部のモードタブで「通常戦闘」と「戦術演習」を切り替える。初期表示は「戦術演習」とする。
2. 戦術演習モードでは、敵編成は通常戦闘と同じ前衛3枠・後衛3枠の盤面を表示し、そのうち1枠だけを埋める。敵メモリー枠・敵の強化（学園レベル、ユニット強化）・ターン上限入力は表示しない。ターン上限は「5ターン固定」と明示する。敵が1体でも配置した位置は結果を変える（`POSITION_ROW`／`POSITION_COLUMN`条件、前後列優先の対象順が参照する）ため、どの枠へ置くかは利用者が選ぶ。一方で演習の敵は定義どおりの1体を相手にするものであり（`R-TEX-01` #1）、学園レベルは利用者自身の育成情報だから、体数と強化は入力させない。
3. 敵の配置は、空いている枠でユニットを選ぶか、味方と同じ移動操作（ドラッグ&ドロップ、移動ボタン）で変更する。既に1体が居る状態で別の枠を選んだ場合は2体目にせず、その枠へ移す。
4. 味方編成の操作は通常戦闘と同じとする（1～5体、メモリー0～6件）。
5. 実行成功時は、勝敗の代わりに総スコア、ブレイク回数、終了理由（ターン上限／味方全滅）とブレイク履歴（ブレイク番号、発生ターン、その時点の累計スコア、発生源）を表示する。発生源は誰の攻撃でブレイクしたかであり、どのユニットがスコアを伸ばしているかを編成の判断材料にできる。発生源ユニットを持たないブレイク（メモリー由来の継続ダメージなど）は「メモリー効果」と表示する。
6. 詳細データ（イベント、状態遷移、JSON）は通常戦闘と同じタブ構成で表示し、演習イベント（スコア加算、ブレイク、復活）を含める。
7. モードを切り替えても、各モードの編成条件と直近の結果は再実行または新しい成功まで保持する。

## 5. 条件設定領域

### 5.1 編成枠

各陣営は以下の順で表示する。

```text
FRONT / 前衛: column 0 | column 1 | column 2
REAR  / 後衛: column 0 | column 1 | column 2
```

- 空き枠は追加操作であることを `＋` とラベルで示す。
- 選択済み枠は画像またはフォールバック、表示名、属性、ロールを表示する。
- 枠を押すとユニット選択ダイアログを開く。
- 選択済み枠では変更と解除ができる。
- 同じユニット定義を複数枠へ配置できる。
- 同一陣営の同じ座標へ複数配置できない構造にする。
- 適性外の前後列にも配置できる。サーバーが適性補正を適用するため、UIは警告を表示するが禁止しない。
- 選択済み枠はドラッグ&ドロップで同一陣営内の別枠へ移動できる。移動先が空なら移動、選択済みなら入れ替えとする。ユニット単位の強化入力（レベル・ギア）はユニットに追随する。
- 陣営を跨ぐドロップは受け付けない。空き枠はドラッグ元にならない。実行中（disabled）はドラッグできない。
- キーボード代替として選択済み枠に「移動」ボタンを置く。押下で移動モードに入り、別枠の起動で配置・入れ替え、Escapeまたは再押下で中止する。進行状態は`aria-live`で通知する。タッチ操作でのドラッグは対象外とし、従来のダイアログでの選び直しを代替手段とする。

### 5.2 ユニット選択ダイアログ

必須機能：

- 表示名・定義IDの部分一致検索
- 属性による絞り込み
- ロールによる絞り込み
- 前後列適性の表示
- 現在選択中のユニットの識別
- 枠を空にする操作

Unit一覧と表示情報は `GET /api/v1/battle-simulation-catalog` の値を使用する。UIがCatalogファイルやIDから内容を再計算しない。

候補は枠の編成プール（`R-TEX-11` #2 #3）で絞る。戦術演習の敵枠は `category: "EXERCISE_ENEMY"` のユニットだけ、それ以外（通常戦闘の両陣営・戦術演習の味方）は `PLAYABLE` のユニットだけを出す。`category` を持たない定義は `PLAYABLE` として扱う（`R-TEX-11` #1。この項目を返さない旧APIとの互換のため）。

演習専用ユニットには開催状況を `開催中`／`開催終了` のチップで示す。これは表示専用の情報であり、開催終了のユニットも選択できる（`R-TEX-11` #4）。開催状況で候補を絞ったり選択を止めたりしない。

### 5.3 メモリー

- 各陣営に6枠表示する。
- 空き枠を押すとメモリー選択ダイアログを開く。
- 表示名・定義IDで検索できる。
- 同じメモリーIDの重複はAPI契約上許容されるため、UIでも禁止しない。
- production Catalogの32件すべてを選択できる。
- Memory一覧と表示情報は一覧APIの値を使用する。

### 5.4 実行パラメータ

| 項目         | UI               | 既定値     | 制約                       |
| ------------ | ---------------- | ---------- | -------------------------- |
| ターン上限   | number input     | `10`       | integer、1～99             |
| ログレベル   | select           | `SUMMARY`  | `SUMMARY`、`DETAILED`      |
| API endpoint | 読み取り専用表示 | ビルド設定 | 利用者が画面上で変更しない |

ログレベルは用途そのものを表す2択とする。`SUMMARY`は「編成を比べるための通常実行」で、必要なのは勝敗とユニット別集計（`unitSummaries`）だけである。`DETAILED`は「効果発動を追うための詳細ログ」であり、レスポンス肥大の説明を付ける。`DIAGNOSTIC`は`DETAILED`と同一挙動になったうえで廃止された（[08\_ドメインイベント.md](../ddd/08_ドメインイベント.md)「公開レベル」）ため選択肢から外す。保存済みドラフトの`DIAGNOSTIC`は`DETAILED`として復元する — そのまま送るとAPIが`422 INVALID_COMMAND`で拒否するためである。

既定を`SUMMARY`にするのは、既定の用途が編成比較であり、詳細ログを既定にすると毎回数MBのレスポンスを受け取ることになるためである。

#### 戦術演習の実行モード

戦術演習モードでは、ログレベルの選択を**実行モードの切替**が置き換える。

| 項目       | UI           | 既定値   | 制約                                                |
| ---------- | ------------ | -------- | --------------------------------------------------- |
| 実行モード | select       | `SINGLE` | `SINGLE`（単一実行）、`STATISTICS`（統計実行）      |
| 実行回数   | number input | `100`    | integer、1～2,000。統計実行のときだけ表示・検証する |
| シード     | text input   | 空       | 任意文字列。空は「自動生成に任せる」                |

演習でログレベルを選ばせない理由は、2つの選択肢が実行モードへ吸収されるためである。`SUMMARY`を選ぶ動機は「大量に実行して集計だけを見る」であり、これは統計実行が正面から担う。残る`DETAILED`は単一実行そのものの用途なので、単一実行は常に`DETAILED`で`POST /api/v1/tactical-exercises`へ送る（保存済みドラフトに残る`logLevel`は演習の送信内容へ影響しない）。通常戦闘モードのログレベル選択は従来どおりとする。

実行回数の上限2,000は、1リクエストの上限（`EVALUATION_MAX_TOTAL_RUNS`）ではなく画面が受け付ける総試行数である。これを超える分の分割送信は統計実行基盤が担う。上限を置くのは、桁を打ち間違えた実行が延々とブラウザを占有するのを防ぐためである。実行回数の値域違反は統計実行のときだけ送信前検証で止める — 単一実行でも検証すると、統計実行を一度も選んでいない利用者が入力途中の値で実行できなくなる。違反の`path`は評価API（`TacticalExerciseEvaluationRequest`）の`runsPerCandidate`へ合わせ、サーバー違反も同じ入力欄へ出せるようにする。

シードは`STATISTICS`のときだけ送信へ効くが、モードを往復しても入力し直さずに済むよう実行回数ともども`SINGLE`の間も保持する。

##### 統計実行の分割送信

統計実行は1リクエストでは終わらない。評価API（`POST /api/v1/tactical-exercise-evaluations`）は1リクエストの総試行数に上限（`EVALUATION_MAX_TOTAL_RUNS`、既定300）を持つため、指定回数を300試行ずつのチャンクへ割り、**1リクエストずつ直列に**送る。詳細は[03_API・データ連携設計.md](03_API・データ連携設計.md) §2.6。

- 実行中は「完了試行数 / 要求試行数」と現在のチャンク番号を進捗として出し、実行ボタンを「実行中…」に変える。
- 「中断して結果を見る」で止められる。中断は**完了済みチャンクまでで結果を確定する**（失敗ではない）——大量実行の途中で傾向が見えた時点で切り上げる使い方が主だからである。
- 期限到達でチャンクが要求より少ない試行数しか返さない場合（`Q-TEX-18`）も再送せず、実際に集計へ入った試行数として示す。要求数と並べて出し、「要求どおり終わった」と読ませない。
- 1試行も完了しなかった場合は結果なしとしてエラーを出す。統計を出す標本が無いためである。
- 統計の表示（サマリ・キャラ別統計・CSV）は §7.4・§8.5 の可視化パネルが担う。

### 5.5 戦闘開始ボタン

次を満たすと有効にする。

- 味方が1～5体
- 敵が1～5体
- ターン上限が1～99の整数
- ログレベルが許容値
- 実行中でない

無効時はボタンだけで理由を表現せず、設定領域上部に不足条件を表示する。

### 5.6 陣営強化（学園レベル）

M11（基本ステータス強化、`ENH-001`）で実装予定の機能である。

- 各陣営のメモリー枠の並びに「強化」トグルと学園レベル入力パネルを表示する。
- トグルはOFFを既定とする。OFFの陣営では学園レベル入力とユニット強化（§5.7）を無効化し、`enhancement`をリクエストへ含めない（後方互換）。
- トグルONの陣営は全ユニットが強化計算の対象になる（タイプ装備・モジュールの固定補正が常時適用される）。
- 学園レベルは次の9項目とし、各項目は1以上の整数（上限なし）、既定値1とする。
  - ユニットタイプ: `PHYSICAL`、`ENERGY`、`AGILE`
  - 属性: `AGGRESSIVE`、`SHY`、`CUTE`、`SMART`、`COMICAL`、`CLEVER`
- 入力と違反表示は実行パラメータ（§5.4）と同じパターンとし、サーバー違反もfield単位で該当入力へ表示する。

#### レベルリンク（`UI-AC-035`）

ゲーム側の育成は全ユニット横並びで進むため、レベルが上がるたびに枠を1つずつ開いて「現在レベル」を打ち直す操作がまるごと重複する。陣営強化パネルへレベルを1つ指定すると、その陣営のユニットレベルがすべてその値になる「レベルリンク」を置く。

- 学園レベルと同じ陣営強化パネル（同一レイヤー）へ、リンクのトグルとリンクレベル入力を置く。自陣・敵陣それぞれに持たせ、パネルを左右対称に保つ。
- リンクは既定OFF、リンクレベルの既定は200（ユニットレベルの既定値と同じ）とする。ONにしただけでは送信内容が変わらない。
- リンクレベルは1以上の整数（上限なし）とし、入力と違反表示は学園レベルと同じパターンとする。
- リンクレベルが1以上の整数でない間（打ち直しのために消した状態を含む）は送信を止めるが、レベルの解決にはリンクを使わず各枠の値を使う。ステータスプレビュー（§5.8）は送信前検証を経ずに送るため、入力を消した瞬間にその陣営の全枠のプレビューがまとめて落ちるのを避ける。
- 陣営の強化トグルOFF時は操作できない。強化そのものを送らない陣営でリンクだけを設定できても送信内容へ影響しないためである。
- リンクONの陣営では、その陣営の全ユニットのレベルをリンクレベルとする。**強化入力を一度も開いていない枠（§5.7のダイアログを開いていない枠）も対象**とする。対象から外すと「ユニットを置いただけの枠は200のまま」となり、枠ごとに開く手間を消すという目的そのものを満たさない。
- 反映は**参照時に解決**する。真実の値はリンクレベル1つだけで、各ユニットの「現在レベル」は保持したままリンク中は無視する。リンクをOFFへ戻すと各ユニットが元の手動レベルへ戻る。リンクレベルを各枠へ書き写す方式にすると、値の置き場が二重化して書き写しの取りこぼしでズレが起きる。
- レベルリンクは「各枠へどの値を載せるか」をUI側で決める仕組みであり、送信DTO（`03_API・データ連携設計.md` §5.1）も戦闘ルールも変えない。
- 戦術演習モードの敵陣は強化パネル自体を表示しない（`UI-UC-006`）ため、リンクの影響を受けない。

### 5.7 ユニット強化ダイアログ

M11（基本ステータス強化、`ENH-001`）で実装予定の機能である。

- 選択済みユニット枠から開く（選択ダイアログと同じ起動パターン）。
- レベル入力を持つ。1以上の整数（上限なし）、既定値200とする。
- ギア9枠を持つ。各枠はstat（`MAXIMUM_HP`、`ATTACK`、`DEFENSE`、`ACTION_SPEED`、`CRITICAL_RATE`、`CRITICAL_DAMAGE_BONUS`、`AFFINITY_BONUS`の7種）、tier（`II`、`III`）、grade（`D`、`C`、`B`、`A`、`S`）の選択で構成し、空枠を許容する。同一statの重複指定を禁止しない。
- 陣営の強化トグルOFF時は編集を無効化し、トグルONを促す。
- 成長値（levelGrowth）を持たないユニットへの200以外のレベル指定はAPIが422で拒否する。UIは事前検証せず、サーバー違反として該当入力へ表示する。
- tier・gradeの選択肢へその組み合わせの上昇値を併記する。値は一覧APIの `gearEffects`（R-ENH-04 #3の効果表）をそのまま表示し、UIは効果表も換算式も持たない。
  - 割合補正（`application: RATIO`。HP・攻撃力・防御力・行動速度）は `%`、ポイント加算（`application: POINT`。会心率・会心ダメージ・属性相性）は `%pt` と表記して区別する。同じ「+3.33%」でも意味が異なるため一律表記にしない（R-ENH-06）。
  - もう一方の軸が未選択の間は、その軸を跨いだ範囲（例: `+1〜3.33%`）を示す。
  - 応答が `gearEffects` を持たない場合はランク名だけの表示へフォールバックする（効果表を公開しない旧APIと組み合わせても壊さない）。

#### リンクから外す（`UI-AC-036`）

- 陣営のレベルリンク（§5.6）がONの間、レベル入力は編集できない読み取り専用とし、適用中のリンクレベルを表示する。`disabled`にはしない——focusできなくなると、その入力へ結びつけたサーバー違反の文言が読み上げから外れるためである。
- ダイアログへ「リンクから外す」を置く。外した枠だけが従来どおり個別のレベル指定で送られる。
- **外した瞬間、その枠のレベルをその時点のリンクレベルでシードする。** シードしないと、外した途端に枠が保持していた古い値（多くは200）へ跳ね戻り、外す操作が破壊的に見える。外すたびにシードし直すため、いったん「リンクへ戻す」を選んでから再度外すと、その間に入力した手動値ではなくその時点のリンクレベルが入る。「外す」は常に**いま適用されている値から編集を始める**操作へ揃える。
- 「リンクへ戻す」では枠の現在レベルを書き換えない。参照時解決なので、書き換えなくても表示と送信はリンクレベルへ切り替わる。
- 成長値（levelGrowth）を持たないユニットへの200以外のレベル指定はAPIが422で拒否する。レベルリンクはこの422の発生確率を上げる——従来は「そのユニットのレベルを自分で打った」ときだけ起きたが、リンク導入後は「リンクを250にしたら編成中の1体が該当した」でも起きる。それでもUIは事前検証しない方針を変えない（UIはユニット定義の成長値を持たない）。
  - リンク中でレベル入力を編集できない状態でも、サーバー違反の文言はその入力へ表示する（`UI-API-019`の対応づけを維持する）。
  - あわせて「リンクから外し、そのユニットのレベルを200に戻す」という解決手段が機能内にあることをヒントとして示す。

### 5.8 編成枠のステータスプレビュー

選択済みユニット枠へマウスオーバーまたはキーボードフォーカスすると、その枠の**開始時ステータス**を表示する。

- 表示値は `POST /api/v1/formation-stat-previews` の応答をそのまま使う。UIは学園レベル・ギア・編成ボーナス・配置適性の計算を持たない（算出の正本はサーバー側の1か所）。
- 表示項目は最大HP、攻撃力、防御力、行動速度、会心率、会心ダメージ、有利属性ボーナスとする。割合値はパーセントポイントで返るためそのまま `%` を付けて表示する。
- 編成・強化指定を変更すると表示値が追随する。強化トグルOFFの陣営では強化なしの値を表示する。
- マウス操作を持たない利用者へも同じ情報を届けるため、枠のフォーカスでも表示し、枠のbuttonから `aria-describedby` で関連づける（`05_非機能・アクセシビリティ設計.md` §5・§6）。
- プレビューの取得失敗・取得中は戦闘実行の失敗として扱わない。実行ボタンの有効・無効へ影響させず、枠には取得できない旨だけを示す。
- 戦闘中のバフ・デバフ適用後の値、およびメモリー由来の `triggeredEffects` は含まない（開始時ステータスに限る）。

#### 補正前ステータスへの切り替え（`UI-AC-034`）

用途によっては属性編成ボーナス・前衛後衛適正補正が乗る**前**の値を確認したいため、表示を切り替えられるようにする。

- 切替は**両陣営・全枠で1つ**のチェックボックス「補正前のステータスを表示」とする。編成レイアウト（`BattleSetupLayout`）の外側・上に置く。陣営ごとの `FormationEditor` へ置くと味方・敵で2つになり、枠ごとに持つと枠間で表示がばらつくためである。
- プレビューのpopover内には置かない。`UnitStatPreview` は `pointer-events: none` で、枠から離れると閉じるためクリックできない。
- 補正前の値は `POST /api/v1/formation-stat-previews` の `enhancedBaseStats`（`R-ENH-06` の強化後基本ステータス）をそのまま表示する。UIは補正量の逆算も再計算も行わない。
- 見出しを「開始時ステータス」／「補正前ステータス」で出し分け、後者には「編成ボーナス・配置適性の補正なし」と添える。行動速度・会心ダメージ・有利属性は編成ボーナスの対象外、適性補正は最大HP・攻撃力・防御力にしか及ばないため、**切り替えても値が変わらない項目がある**。これは仕様であり、補足文言でそれと分かるようにする。
- 強化（学園レベル・レベル・ギア）は補正前の値にも**適用済み**である。強化トグルOFFの陣営ではユニット定義の基本ステータスと一致する。
- `enhancedBaseStats` を返さないAPIの応答を受け取った場合は、補正後の値へ黙って差し替えず「補正前ステータスは取得できませんでした」と示す（`03_API・データ連携設計.md` §9.1）。
- 切替状態は編成の内容ではなく見え方なので、`mlgg:last-draft` などの保存対象に含めない。

### 5.9 入力の保存とリセット

編成のたびに学園レベル・ユニットレベル・ギアを入力し直す負担をなくすため、ブラウザの localStorage へ入力を保存する（`UI-ADR-012`）。サーバーへは保存しない。

保存先はライフサイクル・モードの異なる3キーへ分ける。

| キー                       | 内容                                                                                                                | 役割                                             |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `mlgg:player-data`         | 味方の学園レベル9項目・レベルリンク（`levelLink`）と、`unitDefinitionId` ごとの `{ level, gears[9], linkExcluded }` | 長寿命の「手持ちデータ」。編成を組み直しても残る |
| `mlgg:last-draft`          | 通常戦闘モードの編成draft全体（両陣営の配置・メモリー・強化入力・ターン上限・ログレベル）のスナップ                 | 前回セッションの続き。リロードで直前の画面へ戻す |
| `mlgg:last-draft:exercise` | 戦術演習モードの編成draft全体（同上に実行モード・実行回数・シードを加えたもの）のスナップ                           | 同上。モードごとに独立させる                     |

- 起動時に両モードのdraftキーをそれぞれ復元する。一覧API取得後、Catalogに存在しなくなったユニット・メモリーIDを**その枠だけ**空にし、残りの入力は活かす。
- 味方の空き枠へユニットを配置すると、そのユニットの手持ちデータ（レベル・ギア）をプリフィルする。記録がなければ既定値（レベル200・ギア9枠すべて空）とする。配置し直しても再入力を要さない。
- 味方の学園レベル・ユニットレベル・ギアの編集は手持ちデータへ書き戻す。未入力（空文字）の項目は書き戻さない。
- 手持ちデータはユニット定義ID単位だが、同じ定義は複数枠へ配置でき（§5.1）、枠ごとに異なるレベル・ギアを指定できる。書き戻しは**直近に編集した枠**の値だけを記録する。同じユニットを持つ他の枠の値で上書きしない。
- **敵陣営はプリフィルも書き戻しもしない**（都度入力とする）。`mlgg:last-draft` の復元では敵側も前回値のまま戻る。
- 保存は利用者操作を伴わない自動保存とする。保存に失敗しても（`QuotaExceededError`、プライベートモード、storage無効化など）通知や実行停止を行わず、保存以外の全機能を継続する。
- 保存データが壊れている、`schemaVersion` が現行と異なる場合は破棄して初期状態から開始する。
- 手持ちデータ（学園レベル・ユニットレベル・ギア）は**モードに依らない味方の育成情報**とする。どのモード（`UI-AC-018`）で編集しても `mlgg:player-data` へ書き戻し、どのモードでもプリフィルへ使う。学園レベルは陣営に1組しかない値なので、編集を全モードのdraftへ同時に反映し、モードを切り替えても同じ値が出る。
- 書き戻しは**編集操作でだけ**起こす。モードを切り替えただけでは書き戻さない——切替先のdraftが持つ古い値で、直近に編集した値を上書きしてしまうためである。
- draftの保存先は**モードごとに別キー**とする。1つのキーへ両モードのdraftを入れると、後から保存した側でもう片方の編成が消え、既に `mlgg:last-draft` へ書かれている単一draft形式との互換も切れる。孤児IDのクリアも各モードのdraftごとに判定する — 枠のキー（`slotKey`）はモード間で同じ文字列であり、他モードの判定を混ぜると無関係な枠を空にしてしまう。
- 味方のレベルリンク（`levelLink`）は学園レベルと同じ「陣営に1組しかない育成情報」なので、`mlgg:player-data` へ保存し、編集を全モードのdraftへ同時に反映する。枠ごとの「リンクから外す」（`linkExcluded`）はレベル・ギアと同じ枠の値であり、ユニット定義ID単位の手持ちデータへ書き戻してプリフィルへ使う（書き戻すのは直近に編集した枠だけという規則も同じ）。敵陣営はどちらも書き戻さず、draftキーにだけ残る。
- `levelLink` と `linkExcluded` は**3キーすべてで任意項目**とし、`PERSISTENCE_SCHEMA_VERSION` は 1 のまま据え置く。版を上げると保存データの破棄条件（`schemaVersion`の完全一致）に掛かり、既存利用者の手持ちデータ（ユニット別レベル・ギア・学園レベル）まで巻き添えで消える。新項目が欠けている保存データは破棄せず、既定値（リンクOFF・リンクレベル200・除外なし）として読む。
- 任意項目化は `mlgg:player-data` だけの話ではない。強化入力は draftキー（`mlgg:last-draft`／`mlgg:last-draft:exercise`）へも陣営・枠ごとに保存済みであり、既に手元にある draft は `levelLink`・`linkExcluded` を持たない。ここを必須として読むと「1項目でも契約から外れれば保存データ全体を破棄する」規則に掛かり、全既存利用者の編成draft（配置・メモリー・ギア・ターン上限・ログレベル）が丸ごと消える。
- 演習の実行指定（`exerciseExecution`: 実行モード・実行回数・シード）も**draftキーで任意項目**とし、`PERSISTENCE_SCHEMA_VERSION` は 1 のまま据え置く。理由は `levelLink`・`linkExcluded` と同じで、版を上げれば既存利用者の手持ちデータごと破棄されるためである。この項目を持たない保存データは破棄せず既定値（単一実行・100回・シード空）として読む。保存済みの`logLevel`は書き換えずそのまま残す — 通常戦闘のdraftは引き続きその値で実行し、演習はモードに依らず`DETAILED`で送るためである。
- `mlgg:player-data` には**未知キーを拒否する外部の読み手**がいる（`tools/exercise-lab`。`extra="forbid"` と `SUPPORTED_SCHEMA_VERSION = 1`）。版を据え置く以上、版チェックでは弾かれず未知キーで落ちるため、UIが新項目を書き始める前に読み手側を新項目へ対応させる必要がある。UI側の互換だけでは足りない。

リセット操作を2つ用意する。

| 操作                       | 消す対象                                                                                                | 残す対象                                            |
| -------------------------- | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| 編成をクリア               | 現在のモードの編成draftと、そのモードの保存キー                                                         | 手持ちデータ（`mlgg:player-data`）と他モードのdraft |
| 保存した育成データをクリア | `mlgg:player-data` と、画面上の味方育成入力（学園レベル・レベルリンク・各枠のレベル・ギア・リンク除外） | ユニット配置・メモリー・敵側入力・実行パラメータ    |

「保存した育成データをクリア」が画面上の味方育成入力も初期化するのは、両者が同じ値の2つの置き場であり、保存側だけを消しても画面の値から即座に書き戻されるためである。「編成をクリア」の直後は、手持ちデータの学園レベルとレベルリンクを味方側へプリフィルする。

### 7.4 統計実行の演習統計サマリ（`UI-AC-043`）

統計実行のときは、演習サマリ（Panel 02）を「演習統計サマリ」へ差し替える。単一実行の表示（`ScoreSummaryHeader`・ブレイク履歴・ユニット別表）は変えない —— 1回の結果と標本の統計は別の読み方をするものであり、同じ枠へ混ぜると「このスコアはいつのものか」が読めなくなる。

出すものは4つに分ける。

| ブロック           | 内容                                                                          |
| ------------------ | ----------------------------------------------------------------------------- |
| スコア統計         | 完了run／要求run、平均（95%信頼区間つき）、中央値、標準偏差、min/max、P05/P95 |
| 日次ベスト指標     | E[best-of-5]、日次ベスト中央値、75%／90%保証ライン、有効サンプル              |
| スコア分布         | 単発ヒストグラムと日次ベスト分布の重ね描き。中央値・E[best-of-5]の縦線、凡例  |
| 完走内訳・ブレイク | `completionReason`の割合（pill）とブレイク回数分布（平均つき）                |

ブレイク回数分布の目盛りは、回数の種類が増えたら間引いて両端を残す。1試行あたりの総ブレイクが20〜30回に達すると棒が15本以上並び、全部に数字を置くと重なって読めなくなる。
日次ベスト指標を別枠へ強調して置くのは、スコアアタックが1日k回の最大で決まるためである。平均だと向きが2つ狂う——上振れ（ベスト勝負では資産）が評価されず、稀な崩壊（k回中1回無駄になるだけ）を実際以上に恐れることになる。指標の定義と計算は `tools/exercise-lab` のPython実装が正本であり、UIはその移植を使う（[02\_フロントエンドアーキテクチャ設計.md](02_フロントエンドアーキテクチャ設計.md)）。

有効サンプル `n(2k−1)/k²`（k=5 で n の36%）が10未満のときは、値の下に実行回数を増やすよう警告する。重みが上位2割前後へ集中するため、試行数をそのまま信頼度として読むと過大評価になる。

日次ベスト分布は単発ヒストグラムと同じビン・同じ縦軸（割合）で重ねる。経験CDF `F(x)` をビン境界で `F(x)^k` へ累乗し、その差分をビンの割合として出す。件数のまま重ねないのは、2つが同じ標本から出た別の量（1試行あたりと1日あたり）だからである。標本の外へは外挿しない。

再現に要る条件（seed・チャンクサイズ・Catalog revision）を結果と同じ画面へ出す。実行の再現キーはseed単独ではなく（seed, チャンクサイズ, 実行回数）である（§5.4「統計実行の分割送信」）。

中断・期限到達の部分結果でも表示は成立させ、要求試行数と実試行数を並べて「要求どおり終わった」と読ませない。ここで「要求」として出すのは**利用者が入力した実行回数**である。中断すると送信済みチャンクの合計は要求を下回るため、そちらを要求として読むと、中断した実行が「要求どおり完走した」表示になり、同じ画面の実行結果（`StatisticsRunFeedback`）と食い違う。要求・送信・完了の3つは別物として扱い、統計サマリJSONにも3つとも残す。

## 8. 戦闘詳細

### 8.1 時系列イベント

- `events`の配列順ではなく `sequence` 昇順で表示する。
- 欠番を許容する。
- 表示項目は sequence、turn/cycle、type、source、targets、要約、state versionとする。
- イベントを展開すると `details` と因果参照を表示する。
- `stateTransitionIndex`がある場合、対応状態遷移へ移動できる。
- SUMMARYで省略された親イベントの参照があってもエラーにしない。

### 8.2 状態遷移

- `stateTransitions`の配列順で表示する。
- version before/after、causedBySequence、対象、deltaを表示する。
- deltaはツリー表示とJSON表示を切り替えられる。
- `EntityCollectionDelta`は件数だけでなく、追加・更新・削除された各エンティティを名指しする（DMG-010、Issue #191）。
- 全差分のクライアント側復元は初期必須機能にしないが、テスト用の純粋関数として検証可能にする。

### 8.3 レスポンスJSON

- APIレスポンスを改変せず整形表示する。
- コピー操作を用意する。
- 大きなレスポンスでもDOMノードをフィールドごとに大量生成しない。`pre`または遅延構築されたJSON viewerを使う。
- JSON内のIDや数値を翻訳しない。

### 8.4 ユニット状態

- `finalState.units[]`をbattleUnitId単位で敵味方別に一覧する。
- AP/PP/EX、クールタイム、チャージ（M5）、効果・状態異常（M7-009）、シールドプールとサブユニット（M8／DMG-010）を表示する。
- サマリ表の列を無制限に増やさず、内訳はこのタブへ置く。
- 対応する配列を持たないレスポンス（契約より前に録取したfixture）は「なし」と断定せず不明として表示する。

### 8.5 統計実行のキャラ別統計（`UI-AC-043`）

統計実行のときは、演習詳細（Panel 03）を「キャラ別統計」へ差し替える。単一実行の詳細タブ（§8.1〜§8.4）は変えない。統計実行の応答はイベント列も状態遷移も持たない（試行ごとの数値だけが返る）ため、そこに出せるものが無い。

- **ベストスコア比較セレクタ**: 上位 10 / 25 / 50 run（既定10）。切り替えは手元の生値の再集計だけで、評価APIを呼び直さない —— 同じseedで送り直しても同じ試行をやり直すことになり、待ち時間だけが増える。試行数がNに満たないときは要求Nのまま実数を添える。
- **キャラ別与ダメージ表**: 平均（全run・寄与率つき）、上位N平均（全run平均との増減%つき）、分布バー（min–P25–中央値–P75–max、◆＝上位N平均）。分布バーは全ユニット共通スケールで描く。行ごとに伸縮させると、寄与の小さいユニットの箱が最大の列と同じ幅に見える。
- **ユニット別ブレイク回数表**: 平均（全run）、その枠が1回もブレイクを起こさなかった試行の割合、上位N平均、分布バー（与ダメージと同じ min–P25–中央値–P75–max、◆＝上位N平均）。ブレイク回数を少数のバケット（0/1/2/3+）へ畳まないのは、1試行あたりの総ブレイクが20〜30回に達し、しかも枠によって数回と20回以上に分かれるためである —— 畳むと、多く取る枠がすべて同じ「3回以上」に見えて枠ごとの差が消える。スケールは与ダメージとは別に、ブレイク回数の全ユニット共通で取る（桁が違うので同じ図には載せない）。
- **0回の割合を数値で出す理由**: 共通スケールは最も多く取る枠に合わせて伸びるため、数回しか取らない枠の箱は潰れて0との差が読めなくなる。「関与しなかった試行がどれくらいあるか」は分位点から復元できないので、割合として別に出す。
- **帰属しないブレイクの脚注**: ユニット列の平均の合計と全体平均の差を出す。差には発生源ユニットを持たないブレイク（`R-MEM-04`）と、敵の枠自身が起こしたブレイク（`R-CFS-01`）の両方が入るため、起源を一つに断定した名前を付けない。
- **エクスポート**: 全run生データのCSVダウンロードと、統計サマリJSONのコピー。CSVは `tools/exercise-lab` の `runs.csv` と同じ8列で始め、ユニット別の列（`unit_<n>_damage` / `unit_<n>_break_count`、編成順の1始まり）を後ろへ足す。列名に定義IDを使わないのは、同じ定義を複数の枠へ置けて列名が衝突するためである。列と定義IDの対応は統計サマリJSONの `units` が持つ。行数は実際に完了した試行数であり、要求数まで埋めない。

ユニット別の列に名前を付けられるのは**送信時の編成**だけである。実行後も編成は編集できるため、表示のたびに現在のdraftから引くと別のユニット名が列へ付く。応答の列数が送信した編成の枠数と食い違う場合も表そのものは出し、名前を付けられない列は位置で示す。

チャートは外部の作図ライブラリを使わず、CSS Modules と SVG属性だけで描く。`index.html` の CSP が `style-src 'self'` であり、inline styleを持つ図はブラウザで描画されないためである。図には `role="img"` と説明を付け、同じ数値を `<table>` としても出す（図だけが持つ情報を作らない）。

### 8.6 効果トレース（`UI-AC-045`）

順序で対象が決まる効果が、実際に誰へ届いたかを追うtabである。時系列イベントにも同じ事実は出ているが、
1つの効果インスタンスの一生（付与 → 消費 → 失効／解除）が全イベント列の中に散っていて読めない。
通常戦闘・戦術演習の両方の詳細タブに出す（演習専用にしない）。**APIの契約は変えない** ——
`DETAILED`のログが返す`EFFECT_APPLIED`／`EFFECT_CONSUMPTION_CHANGED`／`EFFECT_EXPIRED`／
`EFFECT_REMOVED`と共通エンベロープだけを読む。

- **スイムレーン**: 行は**保持ユニット**、列はターン。デバフは敵が保持し消費者は味方になるため、行は保持者に置き、消費者はバーの中へ出す。バーの色は終了理由で分ける（消費された／ブレイクで解除／未消費で失効／消費を残して終了／継続中／その他の失効・解除）。色だけが持つ情報を作らないよう、同じ文言をバーの中にも書く。
- **ロスを2種に分ける理由**: 調整で潰せるロスは「1度も消費されずに終わった」と「消費を残したまま終わった」の2つである。どちらも消費条件をそもそも持たない効果の自然な終わりとは別物なので、同じ警告色の系統に置きつつ塗り分ける（べた塗り＝未消費、斜線＝残量あり）。原因が違う —— 前者は付与先か発動順の問題、後者は寿命と上限の噛み合わせの問題である。
- **「消費された」の判定に消費回数を使わない理由**: `R-EFF-07`は消費条件と時間制限を別に保持し、両方が同じイベントで成立した場合にだけ消費を先に評価する。したがって`consumption.maxCount`が2以上の効果は、使い切る前に時間制限が先に効いて`TIME_LIMIT`で終わり得る（本番Catalogの`ACT_KATE_PALADIN_AS2_SELF_EVASION`は`INCOMING_HIT maxCount:2`に対し寿命が`ACTION 1`であり、これが例外ではない）。「消費回数が1以上なら消費された」と判定すると、この残量ロスが成功扱いの色に隠れ、しかも「消費された（TIME_LIMIT）」という自己矛盾した文言になる。使い切りの正本は`EffectExpired.reason === CONSUMPTION`であり、消費イベントが公開レベルで間引かれていてもこの理由は残る。
- **消費の数を出す**: 明細表に「消費回数/上限」を出す。上限が読めない付与（消費条件なし、または`consumptionMaxCount`を持たない応答）は数を出さない —— 分母を1と決め打つと、使い切ったのか残したのかを取り違える。
- **ブレイクで解除の判定**: `EffectRemovalReason`は`REMOVED`／`LINKED_GROUP_CASCADE`しか持たず、ブレイク由来を理由の語彙で名指しできない（`R-TEX-05` #2）。解除イベントの祖先（`parentSequence`）に`UNIT_BROKEN`があることで判定する。ブレイクの解除は`UnitBroken`から直列に連なるため、直接の親だけでは足りない。
- **消費者の帰属**: `EFFECT_CONSUMPTION_CHANGED`の`sourceUnitId`は**保持ユニット**であって消費者ではない。同じ`skillUseId`を持つ先行イベント（`SKILL_USE_STARTED`／`PASSIVE_ACTIVATED`）が行動主体を名指しするのでそこから引き、無ければ`parentSequence`の祖先を遡る。どちらも無ければ帰属不能として`-`を出す（`R-MEM-04`のメモリー由来。時系列イベントの`resolveOrigin`と同じ規約）。
- **明細表**: 付与`sequence`・ターン・効果・保持・付与元・終了理由・消費回数/上限・消費者。同じ効果が同じ保持者へ何度も付与されるログ（1試行で同一定義が19インスタンスに達する実測がある）では、ターンと定義IDだけの行が見分けられないため`sequence`を出す。
- **追跡対象の選択**: ロジックへ効果IDを焼き込まない。投影はログに現れた全インスタンスを総称的に扱い、表示する対象は選択層が決める。注目効果プリセット（`ACT_SUIRAN_CHAOS_AS1_DEBUFF`／`ACT_ELENA_MOODMAKER_EX_ATK_UP_HIGH`）は定義IDを並べた表であり、分岐を持たない。ログに現れた効果は一覧から追加・削除できる。将来Catalogから自動列挙へ広げても投影は変わらない。
- **粒度**: ターン単位で描く。ターン内の行動順は`sequence`として保持し、後から細分できる余地を残す。
- **0件のとき**: 「効果の付与は記録されていません」／「選択した効果は付与されませんでした」と明示する（`BreakTimeline`と同じ方針）。

スイムレーンは外部の作図ライブラリもinline styleも使わず、CSS Modulesと`colSpan`だけで組む。
`index.html`のCSPが`style-src 'self'`であり、inline styleを持つ図はブラウザで描画されないためである。

### 8.7 解決時点の候補比較（`UI-AC-046`）

効果トレース（§8.6）は「誰に付いたか」までを示す。調整するには「**次点との差がいくらか**」が要る。
順位セレクタ由来の付与から、その解決時点の候補一覧を開けるようにする。

- **開始時ステータスの順位では代用できない**: `HIGHEST_ATTACK`はバフ込みの戦闘中攻撃力で解決される。エレーナEXは+35%、翠蘭PS2は+30%の割合バフである一方、ギア1枚が動かす攻撃力は最大3.33ptにすぎない。解決時点の順位は開始時と**別の順位**になる。
- **実効値の出所は`stateTransitions`であって`COMBAT_STAT_CHANGED`のdetailsではない**: R-NUM-01によりDomainは割合を`1.0 = 100%`で持ち、公開境界の`CombatStatsResponse`だけがパーセントポイントへ直す。差分は同じ変換を通っている（クライアントが`ValueChange.before`を現在値と突き合わせられるようにするため）が、イベントのdetailsは通っていない —— 実応答では同じ会心率が`initialState`で`20`、`COMBAT_STAT_CHANGED`で`0.2`になる。イベント側を折り畳むと桁違いの値になる。初期値は応答の`initialState.units[].combatStats`（と`hp.maximum`）を使い、`POST /api/v1/formation-stat-previews`は呼ばない。
- **候補は「解決の起点」で比べる**: `targetBindings`の対象決定はスキル解決の起点で1度だけ行われ、以降のstepは同じbindingを使い回す。付与ごとの時点で比べると、同じ解決の前段が起こしたバフを織り込んでしまう（実測: エレーナEXの`ACT_ELENA_MOODMAKER_EX_DMGUP_LOW`は付与時点だと6件中0件しか一致せず、解決起点だと6/6一致する）。同じ`skillUseId`を持つ最初のイベントを起点とする。
- **内訳**: 候補ごとに「開始時の値」と「その時点で効いている効果の純増減」を出す。「素の攻撃力では別のキャラが上だが、バフ差で覆っている」が読めることが目的である。付与と失効が打ち消しあった効果は適用中ではないので内訳に残さない。寄与の帰属は`COMBAT_STAT_CHANGED`の`parentSequence`を遡って求める（実測で124/124が帰属した）。
- **差の出し方**: 次点との差を絶対値と割合の両方で出す。割合の分母は向きに依らず**次点の値**にする —— 分母を選択側にすると、`HIGHEST_*`と`LOWEST_*`で同じ差が別の数字になり読み比べられない。
- **値が読めないとき**: 誤った値を出さない。差分の`before`が手元の折り畳み値と食い違った系列は、それ以降「読めない」として扱い、順位にも混ぜず末尾へ置いたうえでその旨を示す。

#### 逆算であることの限界

**対象決定を表すイベントは存在しない**（`SkillUseStarted`はスキル・コスト・クールタイムしか持たない）。したがってこの比較は`EffectApplied`の付与先からの**逆算**であり、サーバーが実際にどう比較したかの直接の証拠ではない。

- 候補の母集団は「実際に選ばれたユニットと同じ陣営の全ユニット」と仮定している。セレクタが絞り込みを持つ場合はここに現れない。
- 同点の解決順・戦闘不能ユニットの除外といった細部は再現していない。
- 復元した1位が実際の付与先と食い違った場合は、黙って「これが選ばれた理由です」と言い切らず、一致しなかったことを画面へ出す。

この限界は画面上にも常に表示する。必要になった時点で、対象決定イベントをAPIへ追加することを別途検討する。

扱う順位キーは`combatStats`で比較できるもの（`HIGHEST_ATTACK`／`LOWEST_ATTACK`／`HIGHEST_MAX_HP`／`LOWEST_MAX_HP`／`FASTEST`）に限る。HP割合・EXゲージ割合は比較に要る系列が`combatStats`に無い。

#### どの効果に比較を出すか

比較を出せるのは、**その効果を適用しうる全ての経路**が単一勝者の順位セレクタである場合だけである。「順位セレクタの経路が1つでもあれば出す」ではない —— 1つでも別種の経路があると、付与を見ただけではどちらで選ばれたのか分からず、単一勝者として比較すると正しく選ばれた対象に「一致しません」と誤警告を出す。

実例として`SKL_SUIRAN_CASINO_AS1`は、同じ`ACT_SUIRAN_CASINO_AS1_DAMAGE`を`MARKER_SUIRAN_CASINO_THREE_CARD`の有無で`count: 3`の binding と`count: 1`の binding へ振り分ける。`count: 1`の経路だけを見て表へ載せると、上位3体すべてが正当な対象であるのに2件が誤警告になる。こうした効果は表から除外し、比較そのものを出さない。

複数体が同時に選ばれる順位セレクタ（`count`が2以上）自体も扱わない。比較が単一勝者を前提にしているためである。

## 9. 画像の扱い

- `imageUrl`はUI向けCatalog DTOの任意項目とする。
- ユニット画像とメモリー画像は同じ画像コンポーネントを使わず、用途別アスペクト比を許容する。
- URLなし、ロード失敗、空文字列ではフォールバックを表示する。
- フォールバックは表示名から生成した2文字、属性色、種別ラベルで構成する。
- 画像が操作名の唯一の情報になってはならない。
- 外部画像ホストを使用する場合は利用権、CSP、可用性を別途確認する。初期版は同一GitHub Pages成果物内の画像を推奨する。
