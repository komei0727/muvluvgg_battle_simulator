# UIテスト戦略

## 1. 目的

UIの見た目だけでなく、API DTO変換、battleUnitId単位の集計、未知イベントへの耐性、GitHub Pages配備を継続的に検証する。

テストは実装詳細ではなく、[01_UI要求・画面設計.md](./01_UI要求・画面設計.md) の受け入れ条件と本書のTest IDへ紐づける。

## 2. テストレベル

| レベル            | 対象                                                            | 実行頻度              |
| ----------------- | --------------------------------------------------------------- | --------------------- |
| Pure unit         | validator、request mapper、summary projector、formatter、filter | PRごと                |
| Component         | slot、dialog、form、summary、tabs、error表示                    | PRごと                |
| Contract fixture  | 実OpenAPI/response fixtureとの互換                              | PRごと                |
| E2E mock API      | browser上の主要フロー                                           | PRごと                |
| E2E deployed API  | Pages相当originからCORSを含む縦切り                             | mainまたは手動        |
| Visual regression | 採用モックとの主要viewport比較                                  | UI変更PR              |
| Accessibility     | 自動検査＋keyboard/screen reader手動                            | PR自動＋release前手動 |

### 統計実行の統計量（Issue #540）

- `UI-UT-STS-003`: 空のスコア・完了理由・ブレイク回数を契約違反としてthrowする。
- `UI-UT-STS-004`: `ALLY_DEFEATED`の割合がPython実装と一致し、未知の終了理由もコードのまま内訳へ数える。
- `UI-UT-STS-005`: ブレイク回数分布を回数の昇順で返し、平均を併せて出す。
- `UI-UT-STS-006`: ヒストグラムのビン数がSturges（1〜60へクランプ）でPython実装と一致し、等幅ビンが全試行を覆う。

### 統計実行の分割送信（Issue #541）

`tools/exercise-lab`の`runner.py`と同じ分割規約であること自体が要件なので、チャンク計画・集約は純関数として押さえる。

- `UI-UT-EVL-001`: 1,000試行が300×3＋100へ割れ、各チャンクが`<seed>#<runOffset>`を持つ。300ちょうど・1試行の境界と、非正の実行回数・チャンクサイズの拒否を含む。
- `UI-UT-EVL-002`: シード未入力のとき実行seedを自動生成し、実行ごとに異なる値になる。
- `UI-UT-EVL-003`: チャンクの応答を送信順に連結し、部分結果を埋めずに短い標本として積む。チャンク間の`catalogRevision`不一致とユニット別配列の列数変化を集約せず報告する。
- `UI-UT-EVL-004`: 指定回数がチャンクへ割れて逐次送られ（同時in-flightは常に1件）、進捗が更新される。同じseed・同じ実行回数なら同じリクエスト列になる。
- `UI-UT-EVL-005`: 部分結果を再送しない。中断は完了済みチャンクまでで確定し、完了0試行は結果なしとして失敗にする。unmountで実行中のチャンクを中断する。
- `UI-UT-EVL-006`: `404 ENDPOINT_DISABLED`（判定は`code`のみ。codeを持たない404は汎用のAPI失敗）・`429`（`Retry-After`付き）・チャンク間のCatalog切替・列数変化・seedの不一致・その他のAPI失敗で再試行せず中断する。汎用のAPI失敗は§13の種別文言・生message・violations・送信時のslot対応表を残す。
- `UI-UT-EVL-007`: 評価APIの422 pathから`/candidates/0`を落として送信時のslot・ギア枠へ対応づけ、`/runsPerCandidate`と共有の敵編成のpathはそのまま扱う。対応づかないpathは枠を推測しない。表示するpathはサーバーが返した形へ戻す。

### 統計の投影とエクスポート（Issue #542）

表示用の投影（`statistics-report.ts`）と持ち出す形（`statistics-export.ts`）は、統計量そのものを
計算しない層である。ここで押さえるのは並べ直し・列の名前づけ・列の並びであり、数値の定義は
`UI-UT-STS-*` が持つ。

- `UI-UT-STR-001`: 応答の列へ送信時の編成から名前を付け、Catalog未取得では定義IDへ落ちる。同じ定義を複数の枠へ置いた場合は枠の順番を添えて読み分けられるようにする。
- `UI-UT-STR-002`: スコア統計・日次ベスト指標・完走内訳・ブレイク回数分布を1つの投影へまとめ、要求試行数と実試行数の差を部分結果として残す。「要求」は利用者が入力した実行回数であり、中断で送信済みチャンクの合計が要求を下回る場合も部分結果として扱う。
- `UI-UT-STR-003`: キャラ別の全run統計と上位N部分集計を同じ行へ並べ、分布バーの共通スケールと、ユニット列に帰属しないブレイクの残差を出す。送信時の編成が名前を付けられない列は位置で示す。
- `UI-UT-STR-004`: 単発ヒストグラムと日次ベスト分布が同じビン・同じ縦軸（割合）に載り、日次ベスト側が経験CDFの`F(x)^k`のビン境界差分になる。全試行同値の縮退した標本も1本のビンとして出す。
- `UI-UT-CSV-001`: 連結後の標本からは復元できない試行ごとの出所（チャンク番号・チャンクseed・チャンク内試行番号）を、連結と同じ場所で残す。
- `UI-UT-CSV-002`: 生データCSVが`runs.csv`（`stats.py:RUNS_CSV_COLUMNS`）と同じ8列で始まり、ユニット別の列を後ろへ足す。seedのような任意文字列はRFC 4180でquoteする。
- `UI-UT-CSV-003`: 統計サマリJSONがexercise-labの`summary.json`と同じ再現条件・同じキーを持ち、日次ベスト指標・ユニット別統計・上位N集計を足す。

## 10. Coverage方針

- line coverageの数値達成だけを目的にしない。
- request mapper（`features/formation/request-mapper.ts`）、validator（`shared/api/response-validator.ts`）、summary projector（`features/summary/summary-projector.ts`）、error normalizer（`shared/api/error-normalizer.ts`。REF-056（Issue #601）で`features/simulation/`から`shared/api/`へ移動——`shared/api/api-client.ts`だけが参照する共通API infrastructureのため）、roster選択（`entities/roster.ts`）はbranch coverage 100%を目標とする。`vite.config.ts`の`coverage.thresholds`にper-fileで実測値を下限として設定し、退行を機械的に検知する（Issue #593時点: request-mapper 94% ／ response-validator 88% ／ error-normalizer 91% ／ summary-projector 100%。`entities/roster.ts`はREF-055（Issue #600）でsummary-projector.tsから`selectRoster`を切り出した際に追加、100%）。100%未達の3ファイルは目標のまま残り、埋める作業は別Issueとする。
- componentは主要利用者操作とfailure stateを網羅する。
- CSSとAPI contract fixtureをcoverage対象から除外してよい。
- snapshot testだけでcomponent挙動を保証しない。

計測は`@vitest/coverage-v8`で行い、`mise run ui:test:coverage`（PR CIと同等）が下限を検証する。

- 対象は`src/**/*.{ts,tsx}`全体。テストファイル・`src/test/`・`src/main.tsx`・型宣言のみのファイルは除外する。
- 下限はAPI側（`apps/api/vitest.config.ts`）と対称に、実測baselineから約3pt引き下げた値（切り捨て）。Issue #593時点の実測（lines 93.50%／branches 87.60%／functions 96.98%／statements 93.59%）から、lines 90／functions 93／branches 84／statements 90へ引き上げた（導入時は80%固定だった）。
- 下限はbaselineと重要度を確認しながら段階的に引き上げる。退行を許容するための引き下げは行わない。
